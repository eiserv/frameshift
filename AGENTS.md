# Agent Guidance

These instructions are binding for every agent working on Frameshift, whatever the tool or vendor.

- **Before starting any work,** read this file completely, then work through the documentation in `docs/` and look for everything relevant to your task: specifications, decisions, conventions, limits, and open questions. Do not start from assumptions when the documentation answers the question. If documents contradict each other or the code, report it and resolve it rather than picking one silently.
- **Keep the documentation and this file current at all times.** Whenever a change affects anything described in `docs/`, `README.md`, or `AGENTS.md` (behavior, commands, architecture, conventions, decisions, limits, file locations), update the affected documents in the same change. Outdated documentation counts as a defect.
- **At the end of every run,** check whether your changes made any statement here or in `docs/` outdated, or whether information important for future work is missing, and fix it in the same run.
- Record only what is true for the repository as it is. Never describe planned code, files, or commands as if they already exist. Keep this file compact.

- **Architectural invariants (binding for future implementation).**
  - All migration logic lives in the engine. The CLI only parses arguments, calls the engine, renders results, and maps exit codes.
  - Analysis is read-only, planning is a pure function, execution writes only to staging and the output location, and verification runs external tools only with explicit authorization.
  - Source repositories are untrusted. Never modify them, never execute their code without authorization, never write outside the output location.
  - Fail closed. Anything not positively handled by a rule is `unknown` or `unsupported`, never reported as migrated. No percentage claims behavioral equivalence.
  - Determinism. The same input, options, and versions produce byte-identical plans, output, and reports, except for the report's `run` section.
  - No network access and no LLM in normal operation.

## Working Practices

- **Source project model (`D-095`).** `frameshift_engine::project` assembles selected-package inventory, App Router facts, per-module bindings and source-spanned JSX/environment evidence, and on-demand runtime closures rooted in routes and convention chains (IMPLEMENTATION.md section 44). Reuse its strict-tree visitor, including `project::build_with` for composed consumers (`D-100`); never reparse source just to collect binding or JSX facts. Extension kinds and JSX uses are not unit classifications or copying permissions. Preserve unparsed modules and every unresolved edge. Query work is bounded by `modules.max-work`. `project::build` takes the detected configuration file (`None` establishes absence) and composes the fact extraction of `D-097`. The project-model golden changes only through `cargo test -p frameshift-engine --offline --locked --test project -- --ignored update_project_golden`.

- **Feature catalog and detection (`D-099`).** The catalog in `frameshift-catalog` must equal the tables of MIGRATION_SPEC.md section 17 (the `features` facade test enforces it); change both together, and list every status an entry's notes allow in its V1 column. `features::detect` assigns only the status of single-status entries; never choose among several statuses outside an assessment rule. Recognize APIs only through the binding-proven, graph-confirmed provenance of `D-097`, and emit `source.unknown` with a `Cause` for every construct the catalog does not describe or analysis cannot establish; a missing occurrence never establishes compatibility. Its golden changes only through `cargo test -p frameshift-engine --offline --locked --test features -- --ignored update_features_golden` (IMPLEMENTATION.md section 50).

- **M5 analysis (`D-100`).** `frameshift_engine::analysis` owns read-only assessment, counting/file accounting, transitive readiness, knowledge, exact metrics, and `frameshift.analysis` v1. Reuse `project::build_with`; no identifier-spelling inference or source execution. Unknown preconditions stay unknown, and assessment predicates never count as transformation coverage. Stored reports are bounded, validated data and never authorize reading their paths or executing operations. The CLI exposes `analyze`, stored `report`, `explain`, and assessment `rules`; explicit analysis report outputs are new files outside the source. Golden updates use `cargo test -p frameshift-engine --offline --locked --test analysis -- --ignored update_analysis_golden`. Corpus and reference-fixture commands, limits, current inference boundaries, and validated weights are in IMPLEMENTATION.md section 51.

- **Migrate v0 (proposed `D-101`).** Do not merge code that depends on `D-101` before the owner accepts it. `frameshift_engine::migrate` plans only from `analysis::analyze_parts` (the analysis plus its snapshot, project model, and manifest); never read the source again or write outside `frameshift-output`. Convert only units with status `auto` or `review` and strategy `astro` or `preact-static`; preserve everything else below `.frameshift/unmigrated/` with a manual task, and keep the preservation fixed point so the output never imports a file that was not written. Every rule refusal is a preserved file with a reason, never a guessed conversion. Fixtures are in `fixtures/migrate/` (IMPLEMENTATION.md section 52).

- **Component graph (`D-096`).** `frameshift_engine::project::Project::components` resolves render sites through bindings and the module graph's own edges (IMPLEMENTATION.md section 45). Recognize wrappers (`memo`, `forwardRef`, `lazy`, `next/dynamic`) only through binding provenance of their imports, confirmed by the import edge's package resolution, never by callee spelling; every other call is a `Call` reason. Follow `export *` with ECMAScript's rules and keep several or unknowable providers `AmbiguousStar`. Linking charges `modules.max-work` and returns no partial graph. Its golden changes only through `cargo test -p frameshift-engine --offline --locked --test components -- --ignored update_components_golden`.

- **Environment classification (`D-096`).** `Project::environment` classifies modules from render contexts, with prerendering stopping at browser-only `next/dynamic` imports, and records `process.env` reads (aliases, destructuring, whole-object escapes), Node.js modules and globals, and browser globals (IMPLEMENTATION.md section 46). Count a global only when binding analysis proves it unbound and a built-in module only through the graph's resolution or a binder-proven `require`; never read environment files. Change `NODE_BUILTINS` or `BROWSER_GLOBALS` only with evidence from the pinned Node.js release.
