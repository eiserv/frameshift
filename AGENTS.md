# Agent Guidance

These instructions are binding for every agent working on Frameshift, whatever the tool or vendor.

- **Before starting any work,** read this file completely, then work through the documentation in `docs/` and look for everything relevant to your task: specifications, decisions, conventions, limits, and open questions. Do not start from assumptions when the documentation answers the question. If documents contradict each other or the code, report it and resolve it rather than picking one silently.
- **Keep the documentation and this file current at all times.** Whenever a change affects anything described in `docs/`, `README.md`, or `AGENTS.md` (behavior, commands, architecture, conventions, decisions, limits, file locations), update the affected documents in the same change. Outdated documentation counts as a defect.
- **At the end of every run,** check whether your changes made any statement here or in `docs/` outdated, or whether information important for future work is missing, and fix it in the same run.
- Record only what is true for the repository as it is. Never describe planned code, files, or commands as if they already exist. Keep this file compact.

## Orientation

- **Identity.** The project is named Frameshift, with exactly this capitalization. The CLI executable and command is `frameshift`. Do not introduce other names, temporary branding, or package identities. Naming conventions are in `docs/ENGINEERING.md` (section 8).
- **Purpose.** A deterministic, rule-based engine that analyzes software projects and migrates them between frameworks while preserving behavior, with transparent reporting. The first migration path is Next.js (App Router) to Astro with Preact islands, as static output (`docs/MIGRATION_SPEC.md`). The product is a CLI. The engine is independent of it.
- **Current state: M0 and M1 complete, M2 in progress.** A Cargo workspace, immutable source-text primitives, parser-directed JavaScript trivia, string, numeric, punctuation, template, identifier, and regular-expression literal scanners, complete regular-expression literal validation (including Annex B), identifier classification from generated Unicode 18.0.0 tables, character reference decoding with generated WHATWG and XHTML tables, a JavaScript parser with an arena tree for complete Script and Module source text (all statements, functions, classes, and modules, with sloppy mode, Annex B, and all early errors) with explicit JSX, TypeScript, TSX, and declaration-file dialects (the complete JSX specification grammar, and the TypeScript grammar of the pinned 6.0.3 compiler with structured type nodes, declarations, and extensions), a deterministic span edit core with provenance and tests, an Astro component printer with React JSX conversion and multi-source provenance, a development-only E2 driver with three fictional fixtures and golden files (`D-048`), a development-only E1 measurement harness with generated corpora and a directory mode for an approved real-world sample kept outside the repository (`D-043`), a development-only coverage-guided fuzzer (`D-044`), and a development-only processor-time helper in Go (`D-046`) exist. Rust 1.98.0 is pinned. A standard-library-only CLI shell provides help and version output (`D-050`). Native CI and gated release and packaging workflows exist (`D-051`, `D-052`); there is no migration engine pipeline or published release. All M1 foundation contracts are implemented (through `D-061`), and the owner accepted M1 on 2026-10-19 under `D-063`. M2 has started with read-only discovery and Git-compatible `.gitignore` matching (`D-064`, `D-065`), the first product fixtures in `fixtures/discovery/`, a read-once snapshot store with a framed snapshot identity (`D-067`), a JSON and JSONC parser (`D-068`), and the package model: npm versions and ranges with node-semver's semantics, the `package.json` model, package manager detection, and npm and Bun lockfiles (`D-069`, `D-070`). E1 and E2 passed (`D-047`, `D-049`), `P-002` and `P-003` are accepted, and M0 is complete; the branch-protection policy requires green CI and PR integration (`D-051`). See `docs/IMPLEMENTATION.md` for actual code and contracts; the other documents still specify the remaining product. The remote `origin` is `eiserv/frameshift` (`D-026`), default branch `main`; preparation for public visibility and AGPL licensing is accepted in `D-066`, but the owner made the repository public on 2026-10-17. Work on branches and integrate through pull requests, subject to the explicit one-run exceptions in `D-010`.
- **Implementation language.** Rust is the primary language for engine and CLI (`D-018`). Other languages are allowed only for specific, important tasks with a demonstrable quality advantage, a decision record, and the requirements in `docs/ENGINEERING.md` section 2.7 (`D-019`); the current uses are the development-only processor-time helper (`D-046`) and release archive helper (`D-052`), both in Go. Effort and time are not arguments against quality (`D-020`). The M0 workspace used the Rust standard library only (`D-032`). The reviewed runtime SHA-256 dependency and its exact transitive graph are recorded in `D-058` and `.github/dependencies.json`. Do not add dependencies or bypass the E1/E2 experiment gates without the required decisions.

- **Architectural invariants (binding for future implementation).**
  - All migration logic lives in the engine. The CLI only parses arguments, calls the engine, renders results, and maps exit codes.
  - Analysis is read-only, planning is a pure function, execution writes only to staging and the output location, and verification runs external tools only with explicit authorization.
  - Source repositories are untrusted. Never modify them, never execute their code without authorization, never write outside the output location.
  - Fail closed. Anything not positively handled by a rule is `unknown` or `unsupported`, never reported as migrated. No percentage claims behavioral equivalence.
  - Determinism. The same input, options, and versions produce byte-identical plans, output, and reports, except for the report's `run` section.
  - No network access and no LLM in normal operation.
- **Actual modules.** `crates/frameshift-core` provides dense key tables with slot-addressed results (`D-060`), run limits and atomic budgets (`D-061`), allocation-free bounded SHA-256 streaming and canonical digest values (`D-058`, `D-059`), bounded finding records and deterministic report-local numbering (`D-057`), stable catalog and unit identifiers (`D-055`, `D-056`), immutable UTF-8 text, half-open spans, one-based Unicode-scalar positions, and explicit text limits. `crates/frameshift-syntax` scans JavaScript trivia (with Annex B HTML-like comments in scripts), quoted strings and numeric literals (with an explicit mode for the legacy octal forms of sloppy code), punctuation, template segments, identifier or private names with reserved words, and regular-expression literals, as well as JSX names, attribute strings, and text (`src/jsx.rs`), at caller-selected offsets with explicit context. It validates regular-expression flags and patterns, classifies identifier characters with pinned Unicode tables, and provides a recursive-descent parser in `src/parser/` for complete Script and Module source text and single expressions, with JSX, TypeScript, TSX, and declaration files only in an explicitly selected `JsDialect` (`D-041` to `D-043`), whose TypeScript productions live in `src/typescript.rs` and `src/parser/typescript.rs` and follow the pinned `typescript` 6.0.3 oracle, compared outside the repository, backed by flat node, child, and template-part arenas, which reinterprets cover-grammar nodes as patterns in place (`D-038`) and checks early errors with transient scopes (`D-039`). Its `src/value.rs` compares decoded StringValues of scanned tokens for early errors, and its `src/lookup.rs` wraps the only hash tables in non-iterable lookups (`D-060`). Its `src/reference.rs` decodes character references with JSX and HTML semantics, and `src/json.rs` parses JSON and JSONC with exact values (`D-068`). Its `src/unicode_tables.rs` is generated by the development-only `tools/frameshift-unicode-gen` and its `src/entity_tables.rs` by `tools/frameshift-entity-gen`; never edit them by hand, and change the Unicode version or the entity sources only through a decision (`D-036`, `D-041`). `crates/frameshift-input` is the input layer and the only product crate that reads the source filesystem (`D-064`, `D-065`, `D-067`): `src/gitignore.rs` matches `.gitignore` patterns with Git's semantics, `src/walk.rs` walks a root read-only through a private filesystem abstraction (`src/native.rs`, `std::fs` only), following no link or reparse point and opening only `.gitignore` files, `src/inventory.rs` holds the result, and `src/snapshot.rs` reads admitted files on demand, at most once, and computes the framed snapshot identity. `crates/frameshift-package` (`D-069`, `D-070`) models npm versions and ranges (`src/version.rs`, `src/range.rs`, node-semver 7.8.5 semantics), dependency specifiers (`src/spec.rs`), `package.json` (`src/manifest.rs`), `packageManager` and detection (`src/manager.rs`), and npm and Bun lockfiles (`src/lockfile.rs`), and `src/load.rs` reads one package directory through `Snapshot::read` with findings. `crates/frameshift-transform` applies validated span edits and records provenance. `crates/frameshift-emit` holds the Astro component model and printer, the conversion of React JSX into it (`src/jsx.rs`, which fails closed outside the verified subset and returns value-dependent assumptions), and emitted text with multi-source provenance. `crates/frameshift-engine` exposes these APIs through the `foundation`, `input`, `package`, `syntax`, `transform`, and `emit` namespaces, retaining the M0 root imports for existing consumers; its `limits` module bundles every subsystem limit type with checked relations and a canonical list (`D-061`). Apart from discovery and the snapshot store, the library APIs have no runtime I/O (the package loader reads only through the snapshot store); only the printer crate knows React's JSX semantics and Astro's template syntax. Tests live in the core and engine crates, plus unit tests of the package and printer crates and the development tools and the E2 golden fixture test. `tools/frameshift-corpus` is a development-only library with the deterministic generated JavaScript, JSX, and TypeScript corpora and the parser and empty-edit contract checks. `tools/frameshift-bench` measures parser throughput and peak heap on these corpora, and with `--dir` the parse rate, throughput, and memory on the files of a directory outside the repository (`D-040`, `D-043`); `--check` validates generated parser and empty-edit contracts without timing. It writes nothing and executes nothing. Workspace lints forbid unsafe code and wildcard arms over closed enums, and require public API docs; only `tools/frameshift-bench` relaxes `unsafe_code` to `deny` for its counting allocator module (`D-040`), and `tools/frameshift-fuzz` for its coverage runtime module and `tools/frameshift-fuzz-sections` for two Windows section markers (`D-044`). Never add unsafe code elsewhere without a decision. Reviewed third-party SHA-256 dependencies contain their own unsafe implementations (`D-058`); this does not relax workspace lints. `tools/frameshift-fuzz` fuzzes the program and expression parsers, the regular-expression and lexical scanners, the character reference decoders, the edit core, the JSX conversion with Astro printing, and source/output path values (`paths`, D-054), stable catalog and unit identifiers (`identifiers`, D-055, D-056), SHA-256 streaming/digest contracts (`hashes`, D-059), key tables, dense slots, and budgets (`collections`, D-060, D-061), `.gitignore` matching (`gitignore`, D-065), JSON and JSONC parsing (`json`, D-068), npm ranges, versions, and specifiers (`semver`, D-070), and the package manifest and lockfile models (`package`, D-069) in a coverage-instrumented build (`instrument.toml`); a supervising process saves crashes, hangs, and contract violations below the run directory and starts only its own worker. `tools/frameshift-e2` is the development-only E2 driver (`D-048`): it migrates the fictional fixtures in `tools/frameshift-e2/fixtures/` by hand-wired transformations, checks determinism, provenance, and comment preservation, and compares the outputs with golden files, which change only through its `update` command; the fixtures are `-text` in `.gitattributes`. `tools/frameshift-cputime` is a development-only Go program (`D-046`), standard library only and outside the Cargo workspace, that measures the processor time of a program and its descendants for fuzzing budget runs.

## Working Practices

- **Deterministic collections (`D-060`).** The root `clippy.toml` disallows `HashMap` and `HashSet` everywhere. Iterate only ordered collections or sorted vectors; assign identities before parallel work with `KeyTable` and collect results with `DenseSlots`, which reject duplicates, foreign identities, and missing results. A lookup-only hash table needs a justified `#[expect(clippy::disallowed_types)]`. Contracts are in IMPLEMENTATION.md section 20.

- **Limits (`D-061`).** Every resource limit is an explicit size or count. `RunLimits` holds the discovery input bounds; `Budget` charges are all-or-nothing and must be made in canonical order by one owner. A new limit field must appear in `frameshift_engine::limits::Limits::entries` (the compiler enforces it), and new relations between limits belong in `validate`. Contracts and defaults are in IMPLEMENTATION.md section 21.

- **Product fixtures (`D-062`).** Follow the root `fixtures/` layout in TESTING.md section 4: human-written `fixture.json` (schema `schemas/fixture.schema.json`) and `labels.json`, a byte-exact `source/`, and `expected/` goldens that change only through an explicitly ignored update test. The discovery cases exist; fixture sources contain `.gitignore` files, so add fixture files with `git add -f`.

- **Discovery and snapshot (`D-064`, `D-065`, `D-067`).** Only `frameshift-input` touches the source filesystem. Never follow links or reparse points; discovery opens only `.gitignore` files, and later stages read file content only through `Snapshot::read`, which opens each admitted file at most once and treats any change after listing as a run-stopping error. Keep built-in ignores and environment files closed, charge budgets in canonical order in the walker alone, and report every skipped entry or reached limit with an FS1xxx finding (MIGRATION_REPORTING.md section 8.2). Contracts are in IMPLEMENTATION.md sections 22 to 24.

- **JSON (`D-068`).** Parse `package.json` and `package-lock.json` with `JsonDialect::Json`, and `tsconfig.json`, `jsconfig.json`, and `bun.lock` with `JsonDialect::Jsonc`. Keep numbers as exact text (no floating point), report `duplicate_keys()` as findings, and treat every `JsonError` as an unanalyzed file. Contracts are in IMPLEMENTATION.md section 25.

- **Package model (`D-069`, `D-070`).** Read package files only through `load_package` or `Snapshot::read`. Interpret ranges only with `VersionRange` (node-semver 7.8.5 semantics, never loose) and exact versions with `Version::parse`; a specifier that only loose ranges accept is invalid. Reject lockfiles of unread format versions or with structural deviations as a whole, report every problem with the FS1010, FS1020 to FS1028, or FS2001 to FS2003 codes, and never put package names or values in finding prose. Package fixtures name only fictional packages, because the public repository's manifests are scanned for advisories. Contracts are in IMPLEMENTATION.md section 26.

- **SHA-256 (`D-058`, `D-059`).** Use `Sha256Digest`, `Sha256Hasher`, and `HashLimits` through `frameshift_engine::foundation`. They hash exact bytes, reject over-limit updates without changing state, and expose no external types. Digests serialize as `sha256:` plus 64 lowercase hex digits; hashes do not authenticate content. Future snapshot and plan formats must define framing and domain separation. Contracts are in IMPLEMENTATION.md sections 18 and 19.

- **Findings (`D-057`).** Core finding records use project, file-only, or validated `TextLocation` scopes and optional unit/feature/rule associations. Build text coordinates from the corresponding immutable `SourceText`. `FindingCollector` fails explicitly at size/count/allocation limits, preserves duplicates, and assigns IDs only through a finalized sorted list. IDs are report-local; prose and paths require escaping before rendering. Contracts are in IMPLEMENTATION.md section 17; facade tests are in `crates/frameshift-engine/tests/findings.rs`.

- **Stable unit identities (`D-056`).** `UnitKind` and `UnitId` in the core distinguish file, route/endpoint, and config subjects. Build from original source text, never a pre-encoded ID; `SourcePath` is preserved. Unit ID bytes use uppercase percent encoding with explicit serialized-size limits. Full contracts are in IMPLEMENTATION.md section 16. The `identifiers` fuzz target checks catalog grammar and unit encoding against independent models.

- **Stable catalog identifiers (`D-055`).** `FindingCode`, `RuleId`, and `FeatureId` in the core, exposed through `frameshift_engine::foundation`, validate exact catalog spelling in memory. `IdentifierLimits` bounds storage; errors never echo input. Identity syntax does not establish catalog membership or supported migrations. Contracts are in IMPLEMENTATION.md section 15; facade tests are in `crates/frameshift-engine/tests/identifiers.rs`.

- **Canonical paths (`D-054`).** `frameshift_core::{SourcePath, OutputPath, PathLimits, PathError}`, exposed through `frameshift_engine::foundation`, validate canonical root-relative UTF-8 in memory. Never normalize ambiguous input or use source paths where portable output names are required. Source names and Unicode spelling are preserved; path text needs escaping before rendering. These values do not resolve links, prove containment, or detect collisions. Native conversion and filesystem safety remain future boundaries. Contracts and limits are in IMPLEMENTATION.md section 14; public-facade tests are in `crates/frameshift-engine/tests/paths.rs`.

- **CI and release tooling.** `.github/workflows/ci.yml` runs native tests, checks Cargo boundaries and commit conventions, compares E2 hashes, and calls the read-only `package.yml` for all six targets. `release.yml` creates release PRs with a repository-scoped App token whose key is stored only in the `main`-only `release` environment; that workflow is on main, and release PR automation was re-enabled and verified with Release run `39257581853` on 2026-10-19 (`D-066`); repository settings allow only GitHub-owned Actions and Release Please, pinned to full SHAs; tags, releases, and asset upload are disabled until `FRAMESHIFT_M1_RELEASE_READY=true`. `tools/frameshift-release` is a Go 1.25.5 standard-library-only development tool for deterministic archives and SHA-256 lists, not a product dependency. Run `go -C tools/frameshift-release test ./...`, `go -C tools/frameshift-release vet ./...`, `gofmt -l tools/frameshift-release`, and `pwsh -NoProfile -File .github/scripts/check.ps1`. The release helper requires LICENSE and writes only new files in the explicit existing output directory. `version.txt` and `.release-please-manifest.json` mirror the workspace version and change only through Release Please. Third-party code and table notices are in `THIRD_PARTY_NOTICES.md`. After `cargo fetch --locked` prepares the local dependency cache, builds and tests remain offline and locked. `.github/dependencies.json` pins the reviewed external package versions, features, and build-script inventory. Run `pwsh -NoProfile -File .github/scripts/test-check.ps1` for policy regressions. Dependency auditing uses development-only `cargo-audit` 0.22.2 (`cargo install cargo-audit --version =0.22.2 --locked --no-default-features`, then `cargo audit --deny warnings`); these preparation and advisory checks use the network, product runtime does not. Release Please updates only the explicitly named Frameshift lockfile entries (`D-058`).

- **Language.** English is mandatory for every repository artifact: documentation, code, comments, issues, pull requests, reviews, commit messages, changelogs, release notes, error messages, CLI output, configuration descriptions, decision records, and future UI text. The only exception is direct chat with the user, which uses the user's language. A German chat gets German replies, but files stay English.
- **Writing style.**
  - Clear, precise, professional English.
  - Never use em dashes (Unicode U+2014). Use commas, colons, semicolons, parentheses, or separate sentences instead.
  - No marketing language or vague claims. Explain important decisions and their tradeoffs.
  - Distinguish confirmed facts from proposals, and label unresolved decisions.
  - Keep documents useful rather than long.
- **Forward-looking architecture (`D-033`).** Design for the documented V1 to V3 evolution. Anticipate subsystem boundaries, extensibility, and compatibility in every implementation step, and record the rationale. Keep structures understandable (KISS), distinguish future contracts from implemented behavior, and preserve milestone experiment gates.
- **Deterministic correctness.** Follow the determinism rules (`docs/ENGINEERING.md`, section 6) and the fail-closed rules (section 7.3). Unexpected input must surface as a finding or an internal error, never as silent success.
- **Dependencies.** Minimize them. Every runtime dependency, and every tool that affects build output, needs an accepted entry in `docs/DECISIONS.md` that is evaluated against `docs/ENGINEERING.md` (section 3). Prefer purpose-built code when a library does not fit, with understandable structures and documented architectural rationale.
- **Performance.** Respect the budgets in `docs/ENGINEERING.md` (section 4). Avoid quadratic algorithms over files or nodes. Measure before optimizing.
- **Repository safety.** Never run code from analyzed projects in tools or tests. Commit only fictional fixtures, never third-party project code.
- **No UI work.** Frameshift is CLI-only (`D-004`). Do not build GUI, web, desktop, or terminal UI frontends unless the decision register changes.
- **Documentation synchronization.** Mandatory, see the rules at the top of this file. When implementing something specified, change the specification to describe actual behavior, and keep marking everything else as planned. Record decisions in `docs/DECISIONS.md`.
- **Conventional Commits.** Commit messages and pull request titles follow `<type>(<optional scope>): <description>`, for example `feat(analyzer): detect static route dependencies`.
  - Types: `feat`, `fix`, `perf`, `refactor`, `docs`, `test`, `build`, `ci`, `style`, `chore`, `revert`.
  - Mark breaking changes with `!` after the type or scope, or with a `BREAKING CHANGE:` footer.
  - Release Please derives versions and changelogs from these messages (`docs/RELEASES.md`).
- **Small commits.** As soon as a step stands on its own (a fix with its test, a rule with its fixtures, a documentation update), commit it with its own message. Do not collect a large change into one commit. Each commit should pass the relevant checks.
- **Pull requests and squash merges.**
  - Changes normally reach `main` through pull requests, merged by squash. Owner-authorized one-run direct commit and push exceptions, including the interrupted-run reconciliation, are recorded in `D-010`. Direct pushes to `main` are otherwise prohibited.
  - The squash commit uses the pull request title, so the title must be a valid Conventional Commit, including `!` for breaking changes.
  - Keep unrelated changes in separate branches and pull requests.
  - Push branches, open pull requests, or create issues only when the task calls for it or the user authorizes it.
- **Tests and validation.** Add proportionate tests that cover behavior and error boundaries, and a regression test with every fix. Run the relevant checks before committing once they exist. For documentation-only changes, check links and the absence of em dashes.
- **Releases and CI/CD.** Versions change only through Release Please. Never edit version numbers by hand, and never create tags or releases manually. The CI, Release, and reusable Package workflows exist. Release PRs use a repository-scoped GitHub App and are active, with environment-secret authentication verified on 2026-10-19 (`D-066`). M1 is accepted (`D-063`); publication remains gated until the owner sets `FRAMESHIFT_M1_RELEASE_READY=true` (`D-051`).
- **Publication and license.** Frameshift-owned code is `AGPL-3.0-or-later` (`D-066`); preserve third-party notices. Public visibility does not authorize mirrors, uploads of analyzed code or private evaluation data, or telemetry. Follow the publication checklist and separate release gate (`D-012`, `docs/SECURITY.md` sections 10 and 11).
- **Maintaining these instructions.** Keep this file compact. When real code exists, add entries for actual modules, invariants, and verified commands, and remove statements that become false. Do not add speculative paths or implementation details.
- **Code Comments.** Keep implementation comments concise and explain why, not what. Public API documentation must still describe its contract.
