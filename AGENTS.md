# Agent Guidance

These instructions are binding for every agent working on Frameshift, whatever the tool or vendor.

- **Before starting any work,** read this file completely, then work through the documentation in `docs/` and look for everything relevant to your task: specifications, decisions, conventions, limits, and open questions. Do not start from assumptions when the documentation answers the question. If documents contradict each other or the code, report it and resolve it rather than picking one silently.
- **Keep the documentation and this file current at all times.** Whenever a change affects anything described in `docs/`, `README.md`, or `AGENTS.md` (behavior, commands, architecture, conventions, decisions, limits, file locations), update the affected documents in the same change. Outdated documentation counts as a defect.
- **At the end of every run,** check whether your changes made any statement here or in `docs/` outdated, or whether information important for future work is missing, and fix it in the same run.
- Record only what is true for the repository as it is. Never describe planned code, files, or commands as if they already exist. Keep this file compact.

## Orientation

- **Identity.** The project is named Frameshift, with exactly this capitalization. The CLI executable and command is `frameshift`. Do not introduce other names, temporary branding, or package identities. Naming conventions are in `docs/ENGINEERING.md` (section 8).
- **Purpose.** A deterministic, rule-based engine that analyzes software projects and migrates them between frameworks while preserving behavior, with transparent reporting. The first migration path is Next.js (App Router) to Astro with Preact islands, as static output (`docs/MIGRATION_SPEC.md`). The product is a CLI. The engine is independent of it.
- **Current state: M0, M1, and M2 complete; M3 in progress.** A Cargo workspace, immutable source-text primitives, parser-directed JavaScript trivia, string, numeric, punctuation, template, identifier, and regular-expression literal scanners, complete regular-expression literal validation (including Annex B), identifier classification from generated Unicode 18.0.0 tables, character reference decoding with generated WHATWG and XHTML tables, a JavaScript parser with an arena tree for complete Script and Module source text (all statements, functions, classes, and modules, with sloppy mode, Annex B, and all early errors) with explicit JSX, TypeScript, TSX, and declaration-file dialects (the complete JSX specification grammar, and the TypeScript grammar of the pinned 6.0.3 compiler with structured type nodes, declarations, and extensions), a deterministic span edit core with provenance and tests, an Astro component printer with React JSX conversion and multi-source provenance, a development-only E2 driver with three fictional fixtures and golden files (`D-048`), a development-only E1 measurement harness with generated corpora and a directory mode for an approved real-world sample kept outside the repository (`D-043`), a development-only coverage-guided fuzzer (`D-044`), and a development-only processor-time helper in Go (`D-046`) exist. - **Architectural invariants (binding for future implementation).**
  - All migration logic lives in the engine. The CLI only parses arguments, calls the engine, renders results, and maps exit codes.
  - Analysis is read-only, planning is a pure function, execution writes only to staging and the output location, and verification runs external tools only with explicit authorization.
  - Source repositories are untrusted. Never modify them, never execute their code without authorization, never write outside the output location.
  - Fail closed. Anything not positively handled by a rule is `unknown` or `unsupported`, never reported as migrated. No percentage claims behavioral equivalence.
  - Determinism. The same input, options, and versions produce byte-identical plans, output, and reports, except for the report's `run` section.
  - No network access and no LLM in normal operation.

## Working Practices

- **Deterministic collections (`D-060`).** The root `clippy.toml` disallows `HashMap` and `HashSet` everywhere. Iterate only ordered collections or sorted vectors; assign identities before parallel work with `KeyTable` and collect results with `DenseSlots`, which reject duplicates, foreign identities, and missing results. A lookup-only hash table needs a justified `#[expect(clippy::disallowed_types)]`. Contracts are in IMPLEMENTATION.md section 20.

- **Limits (`D-061`).** Every resource limit is an explicit size or count. `RunLimits` holds the discovery input bounds; `Budget` charges are all-or-nothing and must be made in canonical order by one owner. A new limit field must appear in `frameshift_engine::limits::Limits::entries` (the compiler enforces it), and new relations between limits belong in `validate`. Contracts and defaults are in IMPLEMENTATION.md section 21.

- **Product fixtures (`D-062`).** Follow the root `fixtures/` layout in TESTING.md section 4: human-written `fixture.json` (schema `schemas/fixture.schema.json`) and `labels.json`, a byte-exact `source/`, and `expected/` goldens that change only through an explicitly ignored update test. The discovery cases exist; fixture sources contain `.gitignore` files, so add fixture files with `git add -f`.

- **Discovery and snapshot (`D-064`, `D-065`, `D-067`).** Only `frameshift-input` touches the source filesystem. Never follow links or reparse points; discovery opens only `.gitignore` files, and later stages read file content only through `Snapshot::read`, which opens each admitted file at most once and treats any change after listing as a run-stopping error. Keep built-in ignores and environment files closed, charge budgets in canonical order in the walker alone, and report every skipped entry or reached limit with an FS1xxx finding (MIGRATION_REPORTING.md section 8.2). Contracts are in IMPLEMENTATION.md sections 22 to 24.

- **JSON (`D-068`).** Parse `package.json` and `package-lock.json` with `JsonDialect::Json`, and `tsconfig.json`, `jsconfig.json`, and `bun.lock` with `JsonDialect::Jsonc`. Keep numbers as exact text (no floating point), report `duplicate_keys()` as findings, and treat every `JsonError` as an unanalyzed file. Contracts are in IMPLEMENTATION.md section 25.

- **CSS (`D-077`, `D-078`).** Use `parse_css` through the syntax facade for generic stylesheet structure. Keep tokenizer and parser limits explicit, and prohibit transformation of the whole file when `has_errors()` is true. A clean generic tree does not validate selectors, property values, or individual at-rule grammars. EOF closure preserves an absent closer; descriptor rescanning is bounded by the original value segment. The Sass parser starts separately under `D-079`; full conformance remains planned. Contracts are in IMPLEMENTATION.md sections 33 and 34.

- **Sass (`D-079` to `D-081`).** Use `parse_sass` through the syntax facade with an explicit `SassSyntax`. Preserve source spelling and comments; never evaluate Sass or load imports. This is an in-progress parser, not a full Sass validator. Inspect `unchecked_syntax()` for retained grammars, and never authorize transformations from any result until full conformance is established. Indented `=` and `+` mixin shorthand reuse the directive kinds without a directive-name child; long forms retain that child. Selectors are structured with Dart Sass's evaluation-time grammars; a selector with interpolation, an include-site context, or no accepted grammar keeps `Selector` evidence and stays raw text in the last case, never a syntax error. Keep the remaining grammar gaps in IMPLEMENTATION.md section 35 explicit.

- **YAML (`D-071`).** Use `parse_yaml` through the syntax facade. Preserve scalar text, tags, and graph references; never expand aliases or execute tag constructors. The UTF-8 API retains every document and complex key, while consumers validate their own schemas. Collection nesting is bounded by `yaml.max-depth` with an implementation ceiling of 128, and `yaml.max-nodes` bounds the flat arena. Conformance commands and evidence are in IMPLEMENTATION.md section 27.

- **Package model (`D-069`, `D-070`).** Read package files only through `load_package` or `Snapshot::read`. Interpret ranges only with `VersionRange` (node-semver 7.8.5 semantics, never loose) and exact versions with `Version::parse`; a specifier that only loose ranges accept is invalid. Reject lockfiles of unread format versions or with structural deviations as a whole, report every problem with the FS1010, FS1020 to FS1029, or FS2001 to FS2003 codes, and never put package names or values in finding prose. Package fixtures name only fictional packages, because the public repository's manifests are scanned for advisories. Contracts are in IMPLEMENTATION.md sections 26 and 28. Pnpm format 9.0 is read from full YAML 1.2 syntax (`D-071`); ambiguous YAML mappings, schema mismatches, and missing referenced snapshots reject the whole lockfile. Local `link:` references are retained without guessed versions or filesystem reads. A `yarn.lock` is classic when its leading comments carry `# yarn lockfile v1` and Berry when it is YAML with `__metadata` version 4, 5, 6, 8, 9, or 10 (`D-072`); resolve manifest declarations with `Lockfile::resolve_declared`, because Yarn looks them up by range.

- **Workspaces (`D-073`).** Load workspaces with `load_workspace` and resolve the analyzed package with `Workspace::select`, never by reading member lockfiles; the run root is the workspace root, and nothing above it is read. Each `WorkspaceSemantics` variant reproduces one reference release; a directory is a member only when every evaluated release selects it. Never guess a pattern: extend the core grammar or a release's rules only with evidence from the reference releases (the opt-in `external_workspace_oracle` test), and reject what is not modeled (`FS1030`). Findings name paths and releases, never patterns or package names. Contracts are in IMPLEMENTATION.md section 30.

- **Next.js detection (`D-074`, `D-076`).** Framework knowledge lives in `crates/frameshift-nextjs`, not in the package or input crates. Detection follows how Next.js itself finds its configuration (regular files, as `findUp` does) and routers (`fs.existsSync`), reports what Next.js silently ignores (`FS1045`), and never reads or runs `next.config.*`. Tests and `inspect` fixtures create manifests naming `next` only at test time (fixtures through `createdAtTestTime`); never commit a manifest or lockfile that names a real framework package (`Q-014`, `D-075`). Contracts are in IMPLEMENTATION.md section 31.

- **SHA-256 (`D-058`, `D-059`).** Use `Sha256Digest`, `Sha256Hasher`, and `HashLimits` through `frameshift_engine::foundation`. They hash exact bytes, reject over-limit updates without changing state, and expose no external types. Digests serialize as `sha256:` plus 64 lowercase hex digits; hashes do not authenticate content. Future snapshot and plan formats must define framing and domain separation. Contracts are in IMPLEMENTATION.md sections 18 and 19.

- **Findings (`D-057`).** Core finding records use project, file-only, or validated `TextLocation` scopes and optional unit/feature/rule associations. Build text coordinates from the corresponding immutable `SourceText`. `FindingCollector` fails explicitly at size/count/allocation limits, preserves duplicates, and assigns IDs only through a finalized sorted list. IDs are report-local; prose and paths require escaping before rendering. Contracts are in IMPLEMENTATION.md section 17; facade tests are in `crates/frameshift-engine/tests/findings.rs`.

- **Stable unit identities (`D-056`).** `UnitKind` and `UnitId` in the core distinguish file, route/endpoint, and config subjects. Build from original source text, never a pre-encoded ID; `SourcePath` is preserved. Unit ID bytes use uppercase percent encoding with explicit serialized-size limits. Full contracts are in IMPLEMENTATION.md section 16. The `identifiers` fuzz target checks catalog grammar and unit encoding against independent models.

- **Stable catalog identifiers (`D-055`).** `FindingCode`, `RuleId`, and `FeatureId` in the core, exposed through `frameshift_engine::foundation`, validate exact catalog spelling in memory. `IdentifierLimits` bounds storage; errors never echo input. Identity syntax does not establish catalog membership or supported migrations. Contracts are in IMPLEMENTATION.md section 15; facade tests are in `crates/frameshift-engine/tests/identifiers.rs`.

- **Canonical paths (`D-054`).** `frameshift_core::{SourcePath, OutputPath, PathLimits, PathError}`, exposed through `frameshift_engine::foundation`, validate canonical root-relative UTF-8 in memory. Never normalize ambiguous input or use source paths where portable output names are required. Source names and Unicode spelling are preserved; path text needs escaping before rendering. These values do not resolve links, prove containment, or detect collisions. Native conversion and filesystem safety remain future boundaries. Contracts and limits are in IMPLEMENTATION.md section 14; public-facade tests are in `crates/frameshift-engine/tests/paths.rs`.

- **Language.** English is mandatory for every repository artifact: documentation, code, comments, issues, pull requests, reviews, commit messages, changelogs, release notes, error messages, CLI output, configuration descriptions, decision records, and future UI text. The only exception is direct chat with the user, which uses the user's language. A German chat gets German replies, but files stay English.
- **Writing style.**
  - Clear, precise, professional English.
  - Never use em dashes (Unicode U+2014). Use commas, colons, semicolons, parentheses, or separate sentences instead.
  - No marketing language or vague claims. Explain important decisions and their tradeoffs.
  - Distinguish confirmed facts from proposals, and label unresolved decisions.
  - Keep documents useful rather than long.
- **Forward-looking architecture (`D-033`).** Design for the documented V1 to V3 evolution. Anticipate subsystem boundaries, extensibility, and compatibility in every implementation step, and record the rationale. Keep structures understandable (KISS), distinguish future contracts from implemented behavior, and preserve milestone experiment gates.
- **Deterministic correctness.** Follow the determinism rules (`docs/ENGINEERING.md`, section 6) and the fail-closed rules (section 7.3). Unexpected input must surface as a finding or an internal error, never as silent success.
- **Dependencies.** Minimize them. Every runtime dependency, and every tool that affects build output, needs an accepted entry in `docs/DECISIONS.md` that is evaluated against `docs/ENGINEERING.md` (section 3). Prefer purpose-built code when a library does not fit, with understandable structures and documented architectural rationale.
- **Performance.** Respect the budgets in `docs/ENGINEERING.md` (section 4). Avoid quadratic algorithms over files or nodes. Measure before optimizing.
- **Repository safety.** Never run code from analyzed projects in tools or tests. Commit only fictional fixtures, never third-party project code.
- **No UI work.** Frameshift is CLI-only (`D-004`). Do not build GUI, web, desktop, or terminal UI frontends unless the decision register changes.
- **Documentation synchronization.** Mandatory, see the rules at the top of this file. When implementing something specified, change the specification to describe actual behavior, and keep marking everything else as planned. Record decisions in `docs/DECISIONS.md`.
- **Conventional Commits.** Commit messages and pull request titles follow `<type>(<optional scope>): <description>`, for example `feat(analyzer): detect static route dependencies`.
  - Types: `feat`, `fix`, `perf`, `refactor`, `docs`, `test`, `build`, `ci`, `style`, `chore`, `revert`.
  - Mark breaking changes with `!` after the type or scope, or with a `BREAKING CHANGE:` footer.
  - Release Please derives versions and changelogs from these messages (`docs/RELEASES.md`).
- **Small commits.** As soon as a step stands on its own (a fix with its test, a rule with its fixtures, a documentation update), commit it with its own message. Do not collect a large change into one commit. Each commit should pass the relevant checks.
- **Pull requests and squash merges.**
  - Changes normally reach `main` through pull requests, merged by squash. Owner-authorized one-run direct commit and push exceptions, including the interrupted-run reconciliation, are recorded in `D-010`. Direct pushes to `main` are otherwise prohibited.
  - The squash commit uses the pull request title, so the title must be a valid Conventional Commit, including `!` for breaking changes.
  - Keep unrelated changes in separate branches and pull requests.
  - Push branches, open pull requests, or create issues only when the task calls for it or the user authorizes it.
- **Tests and validation.** Add proportionate tests that cover behavior and error boundaries, and a regression test with every fix. Run the relevant checks before committing once they exist. For documentation-only changes, check links and the absence of em dashes.
