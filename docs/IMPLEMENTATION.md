# Implementation Status and Source Contracts

**Status: M0 in progress.** This is the authoritative map of existing code and its current contracts. The architecture and migration documents describe the remaining product design. M0 is incomplete: neither E1 nor E2 has passed.

## 1. Tooling and code map

- `rust-toolchain.toml` pins Rust 1.98.0, rustfmt, and Clippy (`D-032`).
- The root `Cargo.toml` defines an edition 2024 workspace. Packages are unpublished and use Cargo's default version 0.0.0. `Cargo.lock` is committed. No external crates are used.
- `crates/frameshift-core` is the framework-independent foundation. It currently provides immutable UTF-8 source text, byte spans, derived positions, explicit size limits, and typed text errors.
- `crates/frameshift-syntax` provides parser-directed JavaScript trivia, string, numeric, punctuation, template, identifier, and regular-expression literal scanners for E1, reserved-word classification, complete regular-expression literal validation, ECMAScript identifier character classification from pinned Unicode 18.0.0 tables, and a recursive-descent parser for complete Script and Module source text and for single expressions, backed by flat syntax-node, child, and template-part arenas (`D-039`). The parser lives in `src/parser/`: `mod.rs` (entry points, state, token helpers), `expression.rs`, `pattern.rs` (cover grammar reinterpretation), `function.rs`, `class.rs`, `statement.rs`, `module.rs`, `names.rs` (context-dependent identifier rules), `scope.rs` (transient declaration scopes), and `error.rs`. `src/value.rs` decodes the StringValues of already scanned identifiers and strings lazily for early-error comparisons. It depends only on the foundation and has no framework knowledge. `src/unicode_tables.rs` is generated; it is never edited by hand.
- `tools/frameshift-bench` is a development-only, standard-library-only binary that measures parser throughput and peak heap memory on a deterministic generated corpus (section 6, `D-040`). No product crate depends on it.
- `tools/frameshift-unicode-gen` is a development-only, standard-library-only binary that generates or checks `unicode_tables.rs` from local copies of two Unicode Character Database files (section 4.5). No product crate depends on it, and it is not part of the planned `frameshift` CLI.
- `crates/frameshift-transform` implements pure span rewriting and byte-region provenance. It depends only on the foundation.
- `crates/frameshift-engine` is the public facade for these implemented text, lexical, and syntax-tree APIs. Future CLI code will consume it rather than lower layers. It does not yet expose the project pipeline.
- `crates/frameshift-core/tests/text.rs` tests source preservation, positions, and rejected inputs. `crates/frameshift-engine/tests/rewriting.rs`, `tests/lexical.rs`, `tests/numeric.rs`, `tests/punctuator.rs`, `tests/template.rs`, `tests/unicode.rs`, `tests/identifier.rs`, `tests/regexp.rs`, `tests/parser.rs`, `tests/expressions.rs`, `tests/program.rs`, and `tests/modules.rs` test the public facade. The Unicode generator has unit tests for its input validation; the measurement harness has unit tests for its allocator, corpus generator, and options.
- `.gitattributes` fixes LF checkout endings for workspace Rust, Markdown, and TOML files and Cargo.lock. It does not normalize the analyzed text held by the library. Fixture-specific Git attributes will be specified when on-disk fixtures are added.
- There is no binary or CLI yet. The parser covers the complete JavaScript grammar of Script and Module source text (sections 4.8 to 4.12), but not JSX or TypeScript, and it has no error recovery. No standalone token stream, project discovery, migration rule, filesystem executor, CI workflow, or release configuration exists.

The workspace forbids unsafe code, except in the counting allocator of `tools/frameshift-bench` (section 6), requires public API documentation, and denies Clippy's `wildcard_enum_match_arm` lint. None of the implemented library functions access the filesystem, environment, clock, network, or external processes.

## 2. Source text and positions

`SourceText` takes ownership of a `String` or UTF-8 byte vector and keeps it immutable. It never changes encoding, BOMs, whitespace, or line endings. Invalid UTF-8 is rejected; errors contain numeric offsets rather than source content.

`Span` is a half-open byte range, with zero-based start and exclusive end. Its constructor rejects reversed ranges. Slicing and position lookup additionally validate bounds and UTF-8 scalar boundaries. EOF is a valid offset, including in an empty source.

Positions follow `D-029`: byte offsets are canonical; line and column numbers are one-based; columns count Unicode scalar values. A tab, a combining mark, or a BOM counts as one scalar, without tab expansion or grapheme grouping. LF, CRLF, CR, U+2028, and U+2029 terminate lines. CRLF is one terminator. The offset between CR and LF remains on the preceding line, and its column includes the CR. A trailing terminator creates an empty final line.

The default source limit is 16 MiB. Callers pass limits explicitly and may lower or raise it. The compact index imposes an absolute ceiling of `u32::MAX - 1` source bytes so one-based positions remain representable. Size checks precede UTF-8 validation and index allocation. Index reservation failures return a typed error.

Index construction is linear in source bytes. Line starts and checkpoints every 128 scalars support position lookup with two binary searches and a scan of at most 128 scalars, including EOF. This prevents repeated position queries on a long line from becoming quadratic.

## 3. Span rewriting

`apply_edits` takes an immutable `SourceText`, a borrowed set of edits, and explicit `EditLimits`. It returns rewritten text, a partition of its bytes into provenance regions, and a record of every applied edit. It never selects transformations or parses source. Callers must eventually obtain edits from parsed structure and verified rules, not text search.

Each edit has a half-open original-source span, UTF-8 replacement text, and an `EditOrder` pair (operation order, then edit order). Empty spans insert; empty replacements delete. All ordering pairs in one invocation must be unique, including at different offsets. The caller derives these pairs deterministically, never from worker completion order.

Edits are ordered by source offset, with insertions before nonempty replacements at the same start offset. Insertions sharing an offset are ordered by `EditOrder`. At adjacent replacement boundaries, insertions follow the preceding replacement and precede the following replacement. Insertions strictly inside a replaced range are conflicts. Overlapping nonempty ranges, including identical replacements, are conflicts. Invalid bounds, partial UTF-8 scalars, duplicate ordering pairs, and conflicts return typed errors with no partial result.

Validation is deterministic: edit count first, duplicate ordering pairs in pair order, then span validity and conflicts in source order, and final output size. All validation precedes output allocation and emission. Original text stays unchanged on success and failure. Bytes outside edited spans are copied exactly; replacements are emitted exactly as supplied. There is no newline, indentation, or escaping policy in this low-level edit core. Those belong to future rule and printer code.

The default limits are 100,000 edits and 64 MiB of output per invocation. Callers pass limits explicitly. Output size means final size after deletions and replacements. Byte arithmetic is checked for overflow. Storage is reserved fallibly before emission, including edit indexes and provenance. The algorithm sorts edits and scans the source once for emission, with O(source bytes + replacement bytes + edits * log(edits)) time.

Nonempty provenance regions cover every output byte exactly once. Copied regions refer to their exact source spans; replacement regions refer to the responsible ordering pair and consumed source span. Replacement provenance does not imply equivalence. Deletions emit no region but remain in the applied-edit list, with an empty output span. This is per-text provenance only: rule IDs, file identities, and manifest integration remain future work.

## 4. Parser-directed JavaScript lexical primitives

### 4.1 Trivia and strings

`scan_js_trivia` and `scan_js_string` take immutable `SourceText`, a caller-selected byte offset, an explicit mode (a `SourceGoal` for trivia, a `LegacyOctal` mode for strings), and explicit `LexicalLimits`. Offsets are validated before inspection. The caller must select the correct JavaScript lexical context. These functions cannot distinguish JavaScript from JSX text, JSX attributes, regular expressions, or template literal bodies, and must not be invoked to guess that context. They do not validate a file or make it eligible for transformation.

The scanner contract follows ECMAScript lexical grammar sections [12.2 to 12.4 and 12.9.4](https://tc39.es/ecma262/multipage/ecmascript-language-lexical-grammar.html), checked on 2026-10-12. Whitespace is the explicit set TAB, VT, FF, SPACE, U+00A0, U+1680, U+2000 through U+200A, U+202F, U+205F, U+3000, and U+FEFF. Line terminators are CR, LF, U+2028, and U+2029. Rust's broader Unicode whitespace predicate is not used. U+0085, U+180E, and U+200B are not consumed.

Trivia scanning consumes consecutive whitespace and `//` or `/* */` comments. It returns the complete consumed span, comments in source order with exact delimiter-inclusive spans, and a flag indicating any line terminator, including inside block comments. Line comment spans exclude their terminating line break. Block comments do not nest. EOF is accepted for a line comment, but an unclosed block comment returns an error at its opening delimiter. With `SourceGoal::Script`, the Annex B HTML-like comments of [section B.1.1](https://tc39.es/ecma262/multipage/additional-ecmascript-features-for-web-browsers.html#sec-html-like-comments) are also consumed: `<!--` anywhere (`HtmlOpen`), and `-->` (`HtmlClose`) when a line terminator precedes it within the scanned trivia, possibly inside a block comment, with only whitespace and single-line block comments in between. Both extend to the end of the line, excluding the line break. A close comment is therefore recognized only if the caller scans the complete trivia between two tokens from the end of the first; at the start of the source, `-->` is not a comment, as the grammar requires. `SourceGoal::Module` consumes neither, because module code has no HTML-like comments. A slash that does not start a comment and hashbang comments remain unconsumed. A non-trivia input produces an empty consumed span, not a syntax-validity claim.

String scanning requires a single or double quote and returns a `StringToken` with the delimiter-inclusive span of one ECMAScript string literal. Bytes are neither copied nor decoded. It accepts character escapes, `\0` without a following decimal digit, `\xHH`, `\uHHHH`, `\u{...}` up to 0x10FFFF, and escaped line continuations (including CRLF as one continuation). Unicode escapes can contain surrogate code points because the result is an original-source span, not a Rust string value. Raw U+2028 and U+2029 are legal string characters; raw CR and LF are rejected. Legacy octal escapes (`\1`, `\377`, `\0` followed by a decimal digit) and non-octal decimal escapes (`\8`, `\9`), which only sloppy code permits, return `LegacyDecimalEscape` at their backslash with `LegacyOctal::Reject`. With `LegacyOctal::Permit`, the token reports the backslash offset of the first one in `legacy_octal_escape`, so the parser can apply strict mode once it is known. Template literals use the separate scanner in section 4.4; JSX attributes and JSON strings still require future scanners.

Default limits are 100,000 retained comments per trivia invocation and 1 MiB per string, including its delimiters. `SourceText` separately bounds total source bytes. String bytes are checked before each scalar is consumed; comment count is checked before scanning another comment. Invalid starting offsets take precedence over lexical checks. Missing quotes, unclosed strings/comments, malformed escapes, exceeded limits, and allocation failures return typed errors with numeric offsets and no source snippets or partial result. String-limit errors identify the first scalar that would exceed the bound; invalid escape errors identify the backslash. Standalone scanner calls enforce local limits. The parser also applies aggregate comment, token, node, and nesting limits (section 4.12).

Both scanners are iterative and linear in consumed bytes. Trivia scanning steps over ASCII whitespace, line breaks, and comment text byte by byte and decodes only non-ASCII whitespace candidates; inside comments it recognizes U+2028 and U+2029 by their UTF-8 bytes, because no delimiter or line terminator can begin inside another UTF-8 sequence. String scans allocate no storage; trivia retains only bounded comment records and reserves storage fallibly. Original source, BOM, comments, and line endings remain unchanged. The parser selects lexical goals for the JavaScript grammar; JSX and TypeScript contexts remain unsupported. P-002 remains Proposed until full E1 evidence exists.

### 4.2 Numeric literals

`scan_js_number` scans one strict-mode ECMAScript numeric literal at a parser-selected offset, following [section 12.9.3](https://tc39.es/ecma262/multipage/ecmascript-language-lexical-grammar.html#sec-literals-numeric-literals), checked on 2026-10-12. It returns an exact span, spelling base (decimal, binary, octal, hexadecimal), value category (Number or BigInt), and a `legacy_octal` flag. Decimal fractions and signed exponents, radix prefixes, separators between digits, and integer `n` suffixes are supported. Leading signs remain separate operators. Legacy leading-zero integers, including `08`, return `LegacyLeadingZero` with `LegacyOctal::Reject`, as strict mode code requires. With `LegacyOctal::Permit`, a zero followed by octal digits only is a `LegacyOctalIntegerLiteral` (`017`, octal base) without fraction or exponent, so `07.5` ends before the dot; a zero followed by digits including 8 or 9 is a `NonOctalDecimalIntegerLiteral` (`089`, decimal base) that may take a fraction and exponent. Both set `legacy_octal`, and neither accepts separators in the integer part or a BigInt suffix. Malformed separators, missing radix/exponent digits, inappropriate BigInt suffixes, and adjacent ASCII identifier starts, backslashes, or extra decimal digits return typed errors.

The scalar directly after a literal must not be an ASCII decimal digit or an `IdentifierStartChar` (section 4.5); both return `InvalidNumericContinuation` at that scalar. A backslash also fails there, because it could only begin an escaped identifier start. Any other scalar, including continue-only identifier characters such as U+0660 or U+200D, ends the literal; the following token is the parser's concern. The earlier conservative `UnclassifiedNumericBoundary` error no longer exists.

`LexicalLimits.max_number_bytes` defaults to 1 MiB, including the radix prefix, separators, and suffix. Every consumed byte is checked; a limit error points to the first byte that would exceed the bound. Invalid starting offsets precede lexical checks, including with zero limits. Missing digits point to the expected digit offset (possibly EOF); malformed separators point to the underscore; legacy forms point to the digit after the leading zero; invalid continuations point to the following scalar. Syntax validation can inspect bounded lookahead without consuming it. No numeric value is evaluated, rounded, normalized, or allocated. This keeps the syntax layer independent of future static-evaluation semantics and preserves arbitrarily large BigInt spellings for later V1 to V3 analysis (`D-033`). The scan is iterative and linear in consumed bytes. It does not validate the surrounding expression or file, or implement the future recovery policy (`D-034`).

### 4.3 Punctuation and lexical goals

`scan_js_punctuator` recognizes the fixed ECMAScript punctuation grammar in [section 12.8](https://tc39.es/ecma262/multipage/ecmascript-language-lexical-grammar.html#sec-punctuators), with the input-element goals defined in [the lexical grammar](https://tc39.es/ecma262/multipage/ecmascript-language-lexical-grammar.html), checked on 2026-10-12. It returns a typed `PunctuatorToken` with an exact original-source span, or `None` without consumption when this scanner does not handle the input. A single internal grammar table generates the closed enum, exhaustive spelling function, and candidate list. A compile-time index derived from the same table groups the candidates by their first byte, so a scan compares at most the six spellings that begin with `>` instead of all 57. Longest-match selection is independent of table order. Scanning and lookahead are bounded by this fixed grammar; the result consumes one to four ASCII bytes and allocates nothing.

Every call requires `PunctuatorContext`; there is no guessed default. `JsLexicalGoal` exposes the four ECMAScript input-element goals. Slash and `/=` are punctuation only in `Div` and `TemplateTail`. Right brace is punctuation only in `Div` and `RegExp`. In other goals the scanner returns `None`, leaving the input to the separate template scanner (section 4.4) or the regular-expression scanner (section 4.7). Comment openings always return `None` for trivia handling. Hashbangs, legacy HTML comments, regular-expression bodies, template tails, JSX contexts, decorators, and private identifiers are not implemented by this punctuation scanner. A `None` result is not a syntax error, a valid token, or permission for a future parser to skip source bytes.

The `?.` operator is not consumed before an ASCII decimal digit: `?.3` produces `?`, leaving `.3` to numeric scanning. A dot immediately followed by a decimal digit also returns `None`. `GreaterThanMode::LongestMatch` handles ordinary operators; `Single` consumes only one `>` so a future TypeScript parser can close nested type arguments/parameters and rescan the remainder in a newly selected context. This explicit rescan contract prepares TSX ambiguity handling without guessing expression/type state (`D-033`). It does not parse TypeScript types or resolve TSX ambiguity. Invalid starting offsets produce the shared typed lexical error before inspection, including at partial UTF-8 boundaries. Valid EOF returns `None`. The parser applies aggregate token and depth limits and chooses contexts for the JavaScript grammar; JSX and TypeScript context transitions remain future parser responsibilities.

### 4.4 Template lexical components

`scan_js_template` implements the lexical components in ECMAScript [section 12.9.6](https://tc39.es/ecma262/multipage/ecmascript-language-lexical-grammar.html#sec-template-literal-lexical-components) and the tagged/untagged escape distinction in [section 13.2.8.1](https://tc39.es/ecma262/multipage/ecmascript-language-expressions.html#sec-template-literals-static-semantics-early-errors), checked on 2026-10-12. It takes immutable `SourceText`, an offset, explicit `TemplateContext`, and `LexicalLimits`. `TemplatePosition::Start` requires a backtick; `Continuation` requires the substitution-closing right brace selected by the parser in a template-tail lexical goal. There is no default or inferred context.

The result classifies exactly one `NoSubstitution`, `Head`, `Middle`, or `Tail` component. Its `span` includes both delimiters; `content_span` excludes the leading backtick/right brace and trailing backtick/`${`. Content spans may be empty. Unescaped `${` ends a head or middle; an unescaped backtick ends a no-substitution component or tail. Escaped delimiters stay inside content. Literal braces, quotes, slash sequences, and comment-looking text have no expression or trivia meaning inside a segment. The scanner never parses substitutions, counts expression braces, or manages a nested-template stack. The parser (sections 4.8 and 4.9) chooses when to resume scanning.

Character, hex, fixed-width Unicode, braced Unicode, and line-continuation escapes are recognized. `\0` is valid only without a following decimal digit. Decimal escapes, incomplete hex/Unicode escapes, and code points above 0x10FFFF are invalid. Surrogate code points are accepted as lexical spelling. Braced code points can have arbitrarily many leading zeros within the segment limit; value accumulation is capped to prevent arithmetic overflow while retaining lexical boundaries. Raw CR, LF, CRLF, U+2028, and U+2029 and escaped line continuations are preserved. `has_line_terminator` reports line breaks in the source, including continuations, without computing a cooked value.

`TemplateMode::Untagged` returns `InvalidTemplateEscape` at the first invalid escape's backslash. `Tagged` permits these spellings and sets `invalid_escape` to the first such offset in this segment, which means its ECMAScript cooked value is undefined. Later invalid escapes are still scanned correctly but do not add storage. Invalid escape prefixes leave their first nonmatching character for ordinary segment scanning, so a delimiter or another escape is not swallowed. The flag is valid tagged-template evidence, not parser recovery. An invalid escape in an untagged template remains a syntax error under `D-034`.

No bytes are copied, decoded, normalized, or evaluated. In particular, `content_span` is original spelling, not the ECMAScript raw value, which normalizes CR and CRLF. Future raw/cooked value decoding and static evaluation need separate contracts. This segment interface preserves source provenance and keeps expression grammar and value representation extensible for V1 to V3 (`D-033`, `D-035`).

`LexicalLimits.max_template_bytes` defaults to 1 MiB per segment, including delimiters. The limit is checked before each scalar is consumed, and a limit error points to the first scalar that would exceed it, including either byte of `${`. Offset validation precedes delimiter checks, which precede consumption. Invalid offsets, wrong delimiters, unclosed segments, invalid untagged escapes, and exceeded limits return typed errors without partial tokens. EOF without a segment terminator, including a dangling backslash, returns `UnterminatedTemplate` at the opening offset. If an invalid escape is recognized before EOF or a limit, untagged mode reports it first; tagged mode continues until a terminator, EOF, or the byte limit. Scanning is iterative, allocation-free, and linear in consumed bytes. Total source bytes are separately bounded by `SourceText`.

### 4.5 Pinned Unicode identifier classification

`is_js_identifier_start` and `is_js_identifier_part` implement ECMAScript's `IdentifierStartChar` (Unicode `ID_Start`, `$`, `_`) and `IdentifierPartChar` (Unicode `ID_Continue`, `$`) from [section 12.7](https://tc39.es/ecma262/multipage/ecmascript-language-lexical-grammar.html#sec-names-and-keywords), checked on 2026-10-12. Since Unicode 15.1, `ID_Continue` contains ZWNJ and ZWJ, and the specification no longer lists them separately. `UNICODE_VERSION` reports the pinned data version, `18.0.0` (`D-036`). Rust's own Unicode predicates are never used for identifiers, because their properties and version differ.

The data comes from `DerivedCoreProperties-18.0.0.txt` of the Unicode Character Database. `tools/frameshift-unicode-gen` accepts only that version. It also reads `PropertyValueAliases-18.0.0.txt` for the property value names of section 4.7. It verifies each property's declared code point total, rejects malformed, reversed, overlapping, surrogate, and out-of-range entries and data outside its property section, checks that `ID_Start` is contained in `ID_Continue`, merges adjacent ranges, and renders sorted, disjoint inclusive ranges: 695 for `ID_Start` (158,739 code points) and 814 for `ID_Continue` (162,100 code points). From `PropertyValueAliases.txt` it collects every General_Category and Script value name and alias, inside their sections only, rejecting malformed names and names repeated across lines, and renders them byte-wise sorted: 80 and 351 names. Script_Extensions uses the Script values. The generated header records each source's version, date, and byte size, and repeats Unicode's copyright and terms notice. The source files are not committed. The files used for the committed tables had the SHA-256 hashes recorded in `D-036` and `D-037`. The generated module is excluded from rustfmt, so formatter changes cannot alter it.

ASCII is classified directly. Other scalars use one binary search over static ranges, with no allocation. ECMAScript requires the latest Unicode version, so a new Unicode release needs a deliberate regeneration and decision update. The derived data is subject to Unicode's terms; `THIRD_PARTY_NOTICES.md` must cover it before any distribution ([SECURITY.md](SECURITY.md), section 11).

### 4.6 Identifier names, private names, and reserved words

`scan_js_identifier` scans one `IdentifierName`, or a `PrivateIdentifier` when the offset holds `#`, following [section 12.7](https://tc39.es/ecma262/multipage/ecmascript-language-lexical-grammar.html#sec-names-and-keywords), checked on 2026-10-12. It takes immutable `SourceText`, a parser-selected offset, and `LexicalLimits`. The caller must select JavaScript context. JSX names (which allow `-`), JSX text, and hashbangs need their own future scanners. The result holds the kind (`Name` or `PrivateName`), the exact span including `#` and escape spellings, the `name_span` without `#`, `has_escape`, and `reserved_word`.

Characters are classified with the pinned tables of section 4.5. A `\u` escape with four hexadecimal digits, or a braced code point up to U+10FFFF, contributes one code point, which must itself be permitted at its position: an escape cannot introduce a code point that would be invalid unescaped. Surrogates are never identifier characters. Any other backslash inside or directly after the name returns `InvalidIdentifierEscape` at the backslash, because no ECMAScript token can follow a name with a backslash. A name ends at the first scalar that is not an `IdentifierPartChar`, such as whitespace, punctuation, or a symbol. No Unicode normalization is applied, so canonically equivalent spellings stay distinct, as the specification requires.

`reserved_word` reports the `ReservedWord` whose spelling equals the name's StringValue after decoding escapes, so `els\u{65}` reports `Else`. `has_escape` lets the parser apply the rule that keywords cannot contain escapes. `ReservedWordClass` distinguishes words that are never identifiers, the contextual `await` and `yield`, and the strict-mode words `implements`, `interface`, `let`, `package`, `private`, `protected`, `public`, and `static`. Private names never report reserved words. Contextual keywords (`as`, `async`, `from`, `get`, `meta`, `of`, `set`, `target`) and TypeScript keywords are not reserved; the parser compares their unescaped spellings. Whether a token is a keyword, a permitted identifier, or an early error depends on strict mode, the module goal, and function context, which this scanner does not know. ASCII name characters are classified directly, other scalars through the tables. Every reserved word is lowercase ASCII and at most ten bytes long, so the candidate StringValue is packed into a 128-bit key while it is scanned and looked up by binary search in a table of keys that is derived from the reserved-word table and sorted at compile time. Classification allocates nothing.

`LexicalLimits.max_identifier_bytes` defaults to 1 MiB, including `#` and escape spellings, and is checked before each scalar is consumed. Offset validation precedes the start check, which precedes consumption. `ExpectedIdentifier` points to the scalar that cannot start the name (after `#` for private names, possibly EOF). Malformed escapes, escapes of disallowed code points, and stray backslashes point to the backslash. Limit errors point to the first scalar that would exceed the bound. Braced escapes can have arbitrarily many leading zeros within the limit, and value accumulation is capped to keep scanning linear. Scanning is iterative, allocation-free, and linear in consumed bytes. It does not validate the surrounding syntax or implement recovery (`D-034`).

### 4.7 Regular-expression literals

`scan_js_regexp` scans the lexical extent of one literal following [section 12.9.5](https://tc39.es/ecma262/multipage/ecmascript-language-lexical-grammar.html#sec-literals-regular-expression-literals), checked on 2026-10-12, at a slash that the parser selected in a regular-expression lexical goal. It returns `RegExpToken` with the exact span, the `body_span` (BodyText), and the `flags_span` (FlagText, possibly empty). `//` and `/*` return `ExpectedRegExp`, because they begin comments in every goal. Inside a class, `/` does not end the body, and a backslash escapes any non-terminator. A line terminator anywhere in the literal, including after a backslash or inside a class, returns `RegExpLineTerminator` at the terminator; EOF returns `UnterminatedRegExp` at the opening slash. Flags are the following `IdentifierPartChar`s. A backslash directly after them returns `InvalidRegExpFlag`, because flags cannot contain escapes and no token can follow the literal there. The token is evidence of extent, not of validity.

`validate_js_regexp` rescans the literal and applies `IsValidRegularExpressionLiteral` from [section 13.2.7.2](https://tc39.es/ecma262/multipage/ecmascript-language-expressions.html#sec-isvalidregularexpressionliteral) (`D-037`). Flags must be among `dgimsuvy`, each at most once, and not `u` together with `v`; errors point to the offending flag (`InvalidRegExpFlag`, `DuplicateRegExpFlag`, `IncompatibleRegExpFlags`). The pattern must then parse under the grammar of [section 22.2.1](https://tc39.es/ecma262/multipage/text-processing.html#sec-patterns) with all early errors. The result is `RegExpLiteral` with the token, typed `RegExpFlags`, and the number of capturing groups. Pattern errors are `InvalidRegExpPattern` with a closed `RegExpPatternError` reason at a pattern offset: unmatched or unterminated groups, invalid groups, modifiers, or group names, duplicate or unresolved names, too many groups, nothing to repeat, out-of-order quantifier ranges, lone syntax characters, invalid escapes, backreferences, or property escapes, negated classes with strings, invalid class ranges, unterminated nested classes, and invalid class set syntax. Scanning and validation are separate so that a future parser can still skip a literal with an invalid pattern at a known lexical boundary; the file remains `unknown` (`D-034`).

With `u` or `v`, the Unicode-mode grammar applies, and `v` adds UnicodeSets classes: nested classes, `&&` and `--` operators that cannot be mixed, `\q{...}` string alternatives, escaped reserved punctuators, the ban on unescaped class syntax characters and reserved double punctuators, and the MayContainStrings rules for negated classes and `\P`. Without either flag, the web-compatible grammar of [Annex B.1.2](https://tc39.es/ecma262/multipage/additional-ecmascript-features-for-web-browsers.html#sec-regular-expressions-patterns) applies. There, `]`, `{`, and `}` outside a quantifier are characters, but `{n}` without a preceding atom remains an error. Identity escapes accept any character except `c`, and except `k` when named groups apply. `\c` without a control letter matches a backslash, legacy octal escapes and decimal escapes beyond the group count are characters, class escapes as range endpoints make `-` a literal, and lookaheads can be quantified. As Annex B.1.2.9 requires, a pattern that contains a group name is parsed again with named groups, where `\k` must start a resolvable group reference. Without Unicode mode, classes see UTF-16 code units: an astral character is two class atoms, so `/[😀-😂]/` is out of order as in browsers, while `/[😀-😂]/u` is valid. Escaped surrogate pairs combine only in Unicode mode and in group names, which always use the Unicode-mode escape forms.

Duplicate group names are permitted only when the groups cannot both participate (section 22.2.1.4), that is, when the deepest disjunction containing both has them in different alternatives. Each name is compared only with its latest previous group, by a binary search over the open groups, which is sufficient because earlier same-named groups were already pairwise exclusive. Backreferences may precede their groups and are resolved after parsing; with several unresolved references, the first in source order is reported. Quantifier bounds are compared as digit strings, so arbitrarily long bounds cannot overflow. Class ranges compare CharacterValues, including legacy octal and control escapes.

Property escapes accept `Name=Value` for General_Category (`gc`), Script (`sc`), and Script_Extensions (`scx`), and lone General_Category values or binary properties from table 66. Binary properties of strings from table 67 are accepted only in UnicodeSets mode and never in `\P` or a negated class. General_Category and Script values come from the generated Unicode 18.0.0 tables (section 4.5), including aliases such as `punct` and `Qaai`. Tables 66 and 67 are written by hand from the specification, with compile-time assertions that every table is sorted and free of duplicates. Matching is exact and case-sensitive. `Hrkt` is accepted because PropertyValueAliases.txt lists it, although V8 rejects it.

`LexicalLimits.max_regexp_bytes` defaults to 1 MiB, including both slashes and the flags. It is checked before each scalar is consumed, and a limit error points to the first scalar that would exceed it. Offset validation precedes the opening-slash check, and lexical errors precede flag and pattern errors. Patterns are never compiled or executed, so validation cannot backtrack. The validator is iterative, with explicit stacks for open groups and nested classes, so nesting depth cannot exhaust the call stack. Its storage for open groups, nested classes, group names, and pending references is proportional to the pattern and reserved fallibly (`AllocationFailed`). Time is linear in literal bytes apart from hash lookups of group names and binary searches over properties and open groups. A standard hash map holds the names only for lookups; no result depends on its iteration order. Matching semantics, case folding, and raw or cooked value decoding are not implemented.

### 4.8 Syntax tree arena and expression grammar

The parser in `src/parser/` returns a `SyntaxTree` borrowing the immutable `SourceText`. The tree stores source spans rather than copied token text or decoded values. `NodeId` indexes a flat node arena and has a non-zero representation, so `Option<NodeId>` stays four bytes; a compile-time assertion keeps a `SyntaxNode` at most 40 bytes. Statement lists, elements, properties, parameters, arguments, declarators, class elements, and module specifiers use contiguous ranges of a shared child arena, and template parts use a separate one. Every node span and the consumed span are half-open byte ranges into the original source, and child spans nest inside their parent in source order. Statement spans include their semicolon when the source has one. `SyntaxTree::child_nodes` iterates a node's direct children in source order without allocating, skipping template segments, which are not nodes; it is the traversal that tests and future consumers use. Comments are retained in source order, and any parse error returns no partial tree.

`parse_js_expression` parses one complete expression from a caller-selected byte offset. The expression grammar is complete apart from JSX and TypeScript: identifier references; literals, including legacy octal forms where sloppy code permits them; validated regular-expression literals; templates and tagged templates; array and object literals with holes, spread, shorthand properties, computed keys, methods, getters, setters, and async and generator methods; function, async function, generator, and class expressions; arrow and async arrow functions with expression or block bodies; prefix unary, `await`, `yield` and `yield*`, update, binary, comma, conditional, and assignment expressions with all compound and logical operators; dot, computed, private (`a.#x`), and optional members; calls, optional calls, `super` calls and properties, `new`, `new.target`, `import(...)` with an optional options argument, `import.meta`, and `#name in object`. A Pratt parser applies JavaScript operator precedence and associativity and explicitly selects regexp, division, and template-tail lexical goals; inside any braces, a right brace closes the construct rather than a template substitution. No line terminator may precede `=>`, a postfix update operator, or an async arrow's parameters, and none may follow `yield` before its operand. Only a comma can continue an AssignmentExpression, such as an arrow function, a `yield` expression, a conditional, or an assignment, so `a = () => {} + 1` is an error and a line break before the `+` ends the statement. A nested `new` consumes the first argument list, as `new MemberExpression Arguments` requires. The parser rejects invalid unparenthesized unary or `await` exponentiation, unparenthesized mixing of `??` with `&&` or `||`, optional chains used as template tags or `new` constructors, arrows where only a higher-precedence operand is permitted, and private names outside a member access or the left operand of `in`. The `[~In]` grammar parameter is a parser flag that excludes the `in` operator in `for` heads until brackets, braces, parentheses, templates, or a conditional's middle operand restore it.

Destructuring follows the cover grammar. Array and object literals, parenthesized lists before `=>`, call arguments after `async`, and parameter lists are parsed as expressions first. Once `=`, `=>`, a declaration, or a `for-in`/`for-of` head decides their role, the same arena nodes are reinterpreted in place (`set_kind`), keeping IDs and spans: array and object literals become `ArrayPattern` and `ObjectPattern`, properties become `PatternProperty` or `ShorthandPatternProperty`, spread elements become `RestElement`, and `target = default` becomes `AssignmentPattern`. Assignment targets keep identifier references and may be members or parenthesized simple targets. Parameters and declared bindings become `BindingIdentifier`s and admit no members or parentheses. Rest elements must be last, without a following comma or default, and an object rest target cannot be a nested pattern. Conversion fails closed: a node kind that is not a valid target in the requested mode, such as a method, is rejected. Cover lists also record the first `yield` or `await` expression and, in scripts, the first `await` used as a name, which arrow parameters and async arrow heads reject. Shorthand initializers (`{ a = 1 }`) and duplicate `__proto__` properties are errors only in object literals that do not become patterns. They are recorded per object and checked after the complete expression or program is parsed, reporting the earliest remaining one, so a later syntax error can take precedence. Every node of a returned tree is reachable from the root.

The expression is parsed as if it were outside any function, class, or method, with an unknown source goal and unknown strictness. Constructs whose validity depends on that context fail closed with typed errors (`D-038`, `D-039`): `await` and `yield` outside async functions and generators (`ContextualKeywordRequiresContext`), words that only strict code reserves (`ReservedWordRequiresContext`), constructs that are valid only in sloppy mode (`StrictModeRequiresContext`), HTML-like comment spellings and `import.meta` (`SourceGoalRequiresContext`), `new.target` (`MetaPropertyRequiresContext`), `super` (`SuperRequiresContext`), and private names outside a class (`PrivateIdentifierRequiresContext`). Function and class bodies inside the expression have known context: a class is strict, a function with a `"use strict"` directive is strict, and `new.target` and `super` follow the enclosing function or method.

### 4.9 Program parser

`parse_js_program` parses complete source text with an explicit `SourceGoal` and returns a tree whose root is a `Program` node spanning the whole text, including a leading byte order mark (`D-039`). It covers the complete ECMAScript syntactic grammar except JSX and TypeScript, as specified in the [statements and declarations](https://tc39.es/ecma262/multipage/ecmascript-language-statements-and-declarations.html), [functions and classes](https://tc39.es/ecma262/multipage/ecmascript-language-functions-and-classes.html), and [scripts and modules](https://tc39.es/ecma262/multipage/ecmascript-language-scripts-and-modules.html) clauses of the ECMAScript 2027 draft, checked on 2026-10-12: blocks, `var`, `let`, `const`, `using`, and `await using` declarations, all control statements including `for-in`, `for-of`, and `for await`, `switch`, `try`, labels, `with`, and `debugger`; function, generator, async, and async generator declarations; classes with heritage, constructors, methods, accessors, public and private fields and methods, static members, and static blocks; and import and export declarations with import attributes. A hashbang comment at the start is retained as `CommentKind::Hashbang`, also after a byte order mark, which is an encoding signature rather than source text.

Automatic semicolon insertion follows the specification: a semicolon is inserted before `}`, at the end of the input, or after a line terminator, never in a `for` head, and the semicolon after `do ... while (...)` is always optional. `return`, `break`, `continue`, `throw`, postfix update operators, `yield`, `async`, and `=>` honor their `[no LineTerminator here]` restrictions; a line terminator after `throw` is an error. Statement-start ambiguities use bounded lookahead that restores the parser state: `let` starts a declaration before `[`, `{`, or a name, and an expression otherwise; `async` followed on the same line by `function` starts a declaration; `using` followed on the same line by a name starts a declaration, except `using of` in a `for` head unless `=` follows; `await using` follows the same rule where `await` is a keyword; an identifier followed by `:` is a label. `import` followed by `(` or `.` is an expression.

Each function, method, field initializer, and static block is a context boundary that saves and replaces the parser context: strictness, whether `return` is allowed, whether `yield` and `await` are keywords, whether `await` is reserved, whether parameters are being parsed, permission for `new.target`, `super` properties, and `super` calls, and whether `arguments` is forbidden. Arrow functions inherit the enclosing function's `new.target`, `super`, and `arguments` rules. Class field initializers do not treat `yield` or `await` as keywords; a static field initializer reserves `await` like a static block. The specification's grammar states no early error for `await` in a static field initializer, but V8 rejects it, so this is the stricter reading. Labels and the loop and `switch` depth are reset at every boundary, so `break` and `continue` never cross functions or static blocks.

The tree records `FunctionKind`, `MethodKind` (including `Constructor`), `VariableKind`, `MetaPropertyKind`, whether a `for-of` is `for await`, and strictness on `Program` and `FunctionBody` nodes. `FunctionBody.strict` is true when the body is known to be strict code; in a context-free expression, inherited strictness is unknown and reported as false. Without `from`, an export specifier's local name becomes an `Identifier` reference to a module binding; with `from`, it stays an `IdentifierName` or string.

### 4.10 Source goals, strictness, and Annex B

Module code is always strict, permits `await` at the top level, and reserves `await` everywhere else. Script code is sloppy unless a directive prologue contains `"use strict"`, spelled exactly with either quote and without escapes. A function becomes strict through its own prologue; class code is always strict. The `"use strict"` directive applies retroactively: an earlier directive with a legacy octal escape becomes an error, and the function name and parameters are validated against strict mode after the prologue, so `function eval() { "use strict" }` and `function f(a, a) { "use strict" }` are errors. A `"use strict"` directive in a function with a non-simple parameter list is an error.

Sloppy scripts support the complete web-compatibility grammar of Annex B ([section B.3](https://tc39.es/ecma262/multipage/additional-ecmascript-features-for-web-browsers.html#sec-other-additional-features), checked on 2026-10-12) as well as sloppy-mode names: HTML-like comments (section 4.1); legacy octal and non-octal decimal literals and escapes, which the scanners report with `LegacyOctal::Permit` and the parser rejects in strict code; `with`; labelled function declarations; plain function declarations as `if` clauses, wrapped in their own block scope; repeated plain function declarations in a block or `switch`; initializers in `for (var name = value in object)`; `var` redeclaring a simple catch parameter; call expressions as targets of `=`, compound assignment, update, and `for-in` or `for-of`; `let`, `static`, `implements`, `interface`, `package`, `private`, `protected`, `public`, and outside generators `yield` as names; `eval` and `arguments` as bindings and assignment targets; `delete` of a name; and duplicate parameter names in simple parameter lists of function declarations and expressions, including async and generator functions. Strict code rejects each of these with `StrictMode(StrictModeError)` or the corresponding typed error. Arrow functions and methods never permit duplicate parameters.

Where V8 rejects source text that the specification accepts, the parser rejects it as well, because no engine could load the file: `<!--` between tokens of module code returns `HtmlCommentInModule`, and the static field rule above applies. Where V8 accepts source text that the specification rejects, the parser follows the specification: `-->` at the very start of a script is not a comment, and a call expression is not an assignment target in strict code. Stage 3 proposals such as source-phase imports (which V8 accepts) and decorators are not part of the specification and are syntax errors.

### 4.11 Early errors and transient scopes

All early errors of the supported grammar are reported while parsing, using state that exists only during one parse (`D-039`). Declarations are tracked in a stack of transient scopes keyed by StringValue: script, function, and static block top levels, where functions behave like `var`; the module top level, where functions are lexical; blocks, `switch` case blocks, and `for` heads; and catch clauses, which hold the catch parameter and the handler's declarations together. A `var` declaration is recorded in every scope up to its function, so a later lexical declaration in any of them sees the conflict. This reports duplicate lexical declarations, lexical declarations that conflict with `var`, parameters, or catch parameters, `let` as a lexically bound name, and the Annex B relaxations in sloppy code. Labels are a per-function stack: nested duplicates, undefined `break` and `continue` targets, `continue` to a label that does not name a loop, unlabelled `break` outside loops and `switch`, and `continue` outside loops are errors. Private names are collected per class; a reference may precede its declaration and is resolved when the class body ends, unresolved names move to the enclosing class, and names unresolved at the outermost class are errors. Duplicate private names are errors, except a getter and setter pair with the same placement. Classes also reject duplicate constructors, special-method constructors, a field named `constructor`, a static member named `prototype`, `#constructor`, `delete` of a private member, `arguments` in field initializers and static blocks, and `super()` outside derived-class constructors. Modules reject duplicate exported names compared by StringValue, export names with unpaired surrogates, local export names that are strings or reserved words, exported local bindings that the module's top level does not declare, and duplicate import attribute keys. The semantic layer (M4) will build its own scope graph from the tree; the parser's scopes are discarded.

### 4.12 Limits and stack use

`ParseLimits` defaults to 100,000 syntax nodes, 200,000 consumed tokens, and 256 nested parser calls, in addition to lexical byte and comment limits. Child-arena entries are bounded by the node limit. Comments, nodes, child ranges, template parts, bound names, labels, class scopes, and pending expression-only errors reserve fallibly; the scope maps use the standard hash map only for lookups, and no result depends on their iteration order. Reaching a configured bound or failing storage reservation returns a typed parse error. The parser is recursive descent; the depth bound is checked before each nested expression, `new`, statement, function, arrow function, method, and class, and pattern conversion and declared-name collection follow nesting that parsing already bounded. Parsing is linear in tokens and nodes apart from the O(n log n) duplicate-parameter check, hash lookups, and `var` declarations, which visit at most the bounded scope depth. The parser keeps no token stream. Its grammar peeks at the next token several times before consuming it, so it caches the last scanned identifier, the last scanned punctuator with its lexical goal, and the offset where the last trivia skip stopped; a repeated peek at the same offset and goal reuses the result instead of scanning again. Scans are pure functions of these inputs, and a skip always stops before a non-trivia character, so the caches cannot change a result. Child lists are collected in buffers that are reused once their list has been appended to the child arena, so after the first lists of a nesting level, a list costs no allocation. Measured on Windows x86_64, an optimized build uses at most about 1.1 KiB of stack per depth unit, about 280 KiB at the default bound, so a 1 MiB main-thread stack suffices; an unoptimized build uses up to about 15 KiB per unit, so tests that reach the bound run on a thread with an explicit 64 MiB stack. Long `else if` and conditional chains consume one depth unit per link. Full E1 still requires JSX and TypeScript syntax coverage, corpus and span review, throughput and peak-memory measurements, fuzzing, and maintainability evidence.

## 6. E1 measurement harness

`tools/frameshift-bench` implements `D-040`. It runs only in optimized builds and refuses to measure otherwise:

```text
cargo run -p frameshift-bench --release --offline --locked
cargo run -p frameshift-bench --release --offline --locked -- --seed <n> --files <n> --iterations <n>
cargo run -p frameshift-bench --offline --locked -- --print <index>
```

`--print` writes one generated file to standard output for review. The tool reads no files, starts no processes, and uses no network.

**Corpus.** `src/corpus.rs` generates fictional JavaScript with SplitMix64 and integer arithmetic only, so a seed yields byte-identical files on every platform. Every declared name is unique within its file, and each construct appears only where its goal and function context permit it: imports, exports, and top-level await in modules; `require`, `module.exports`, `var`, hashbangs, and `"use strict"` in scripts; functions of every kind, classes with private names, static blocks, and `super`, destructuring, loops, labels, `switch`, `try`, templates, regular expressions, numeric and string literal forms, comments, CRLF line endings, and files without semicolons. Nesting is bounded, so a file exceeds its target size by at most one top-level item (about 1 KB on average). The default corpus has 1,000 files with target sizes piecewise log-uniform from 1 KiB to 32 KiB, about one in ten a script: 10,342,331 bytes, fingerprint `7c71c5e6160d3383` for generator version 1, pinned by a unit test. **Measurements.** `src/measure.rs` times `SourceText::new` plus `parse_js_program`, and the parse alone, after one warm-up pass, and reports the minimum and median of the measured passes. Per-file memory is the source size plus the largest heap growth while building the source text and parsing, with the tree alive. A second pass keeps every source text and tree alive at once. A scaling series parses single modules from 1 KiB to 4 MiB with unbounded node and token counts. `src/alloc.rs` is the only unsafe code: a global allocator that forwards to the system allocator and counts requested bytes with relaxed atomics.
