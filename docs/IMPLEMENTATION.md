## 2. Source text and positions

`SourceText` takes ownership of a `String` or UTF-8 byte vector and keeps it immutable. It never changes encoding, BOMs, whitespace, or line endings. Invalid UTF-8 is rejected; errors contain numeric offsets rather than source content.

`Span` is a half-open byte range, with zero-based start and exclusive end. Its constructor rejects reversed ranges. Slicing and position lookup additionally validate bounds and UTF-8 scalar boundaries. EOF is a valid offset, including in an empty source.

Positions follow `D-029`: byte offsets are canonical; line and column numbers are one-based; columns count Unicode scalar values. A tab, a combining mark, or a BOM counts as one scalar, without tab expansion or grapheme grouping. LF, CRLF, CR, U+2028, and U+2029 terminate lines. CRLF is one terminator. The offset between CR and LF remains on the preceding line, and its column includes the CR. A trailing terminator creates an empty final line.

The default source limit is 16 MiB. Callers pass limits explicitly and may lower or raise it. The compact index imposes an absolute ceiling of `u32::MAX - 1` source bytes so one-based positions remain representable. Size checks precede UTF-8 validation and index allocation. Index reservation failures return a typed error.

Index construction is linear in source bytes. Line starts and checkpoints every 128 scalars support position lookup with two binary searches and a scan of at most 128 scalars, including EOF. This prevents repeated position queries on a long line from becoming quadratic.

## 3. Span rewriting

`apply_edits` takes an immutable `SourceText`, a borrowed set of edits, and explicit `EditLimits`. It returns rewritten text, a partition of its bytes into provenance regions, and a record of every applied edit. It never selects transformations or parses source. Callers must eventually obtain edits from parsed structure and verified rules, not text search.

Each edit has a half-open original-source span, UTF-8 replacement text, and an `EditOrder` pair (operation order, then edit order). Empty spans insert; empty replacements delete. All ordering pairs in one invocation must be unique, including at different offsets. The caller derives these pairs deterministically, never from worker completion order.

Edits are ordered by source offset, with insertions before nonempty replacements at the same start offset. Insertions sharing an offset are ordered by `EditOrder`. At adjacent replacement boundaries, insertions follow the preceding replacement and precede the following replacement. Insertions strictly inside a replaced range are conflicts. Overlapping nonempty ranges, including identical replacements, are conflicts. Invalid bounds, partial UTF-8 scalars, duplicate ordering pairs, and conflicts return typed errors with no partial result.

Validation is deterministic: edit count first, duplicate ordering pairs in pair order, then span validity and conflicts in source order, and final output size. All validation precedes output allocation and emission. Original text stays unchanged on success and failure. Bytes outside edited spans are copied exactly; replacements are emitted exactly as supplied. There is no newline, indentation, or escaping policy in this low-level edit core. Those belong to future rule and printer code.

The default limits are 100,000 edits and 64 MiB of output per invocation. Callers pass limits explicitly. Output size means final size after deletions and replacements. Byte arithmetic is checked for overflow. Storage is reserved fallibly before emission, including edit indexes and provenance. The algorithm sorts edits and scans the source once for emission, with O(source bytes + replacement bytes + edits * log(edits)) time.

Nonempty provenance regions cover every output byte exactly once. Copied regions refer to their exact source spans; replacement regions refer to the responsible ordering pair and consumed source span. Replacement provenance does not imply equivalence. Deletions emit no region but remain in the applied-edit list, with an empty output span. This is per-text provenance only: rule IDs, file identities, and manifest integration remain future work.

## 4. Parser-directed JavaScript lexical primitives

### 4.1 Trivia and strings

`scan_js_trivia` and `scan_js_string` take immutable `SourceText`, a caller-selected byte offset, an explicit mode (a `SourceGoal` for trivia, a `LegacyOctal` mode for strings), and explicit `LexicalLimits`. Offsets are validated before inspection. The caller must select the correct JavaScript lexical context. These functions cannot distinguish JavaScript from JSX text, JSX attributes, regular expressions, or template literal bodies, and must not be invoked to guess that context. They do not validate a file or make it eligible for transformation.

The scanner contract follows ECMAScript lexical grammar sections [12.2 to 12.4 and 12.9.4](https://tc39.es/ecma262/multipage/ecmascript-language-lexical-grammar.html), checked on 2026-10-12. Whitespace is the explicit set TAB, VT, FF, SPACE, U+00A0, U+1680, U+2000 through U+200A, U+202F, U+205F, U+3000, and U+FEFF. Line terminators are CR, LF, U+2028, and U+2029. Rust's broader Unicode whitespace predicate is not used. U+0085, U+180E, and U+200B are not consumed.

Trivia scanning consumes consecutive whitespace and `//` or `/* */` comments. It returns the complete consumed span, comments in source order with exact delimiter-inclusive spans, and a flag indicating any line terminator, including inside block comments. Line comment spans exclude their terminating line break. Block comments do not nest. EOF is accepted for a line comment, but an unclosed block comment returns an error at its opening delimiter. With `SourceGoal::Script`, the Annex B HTML-like comments of [section B.1.1](https://tc39.es/ecma262/multipage/additional-ecmascript-features-for-web-browsers.html#sec-html-like-comments) are also consumed: `<!--` anywhere (`HtmlOpen`), and `-->` (`HtmlClose`) when a line terminator precedes it within the scanned trivia, possibly inside a block comment, with only whitespace and single-line block comments in between. Both extend to the end of the line, excluding the line break. A close comment is therefore recognized only if the caller scans the complete trivia between two tokens from the end of the first; at the start of the source, `-->` is not a comment, as the grammar requires. `SourceGoal::Module` consumes neither, because module code has no HTML-like comments. A slash that does not start a comment and hashbang comments remain unconsumed. A non-trivia input produces an empty consumed span, not a syntax-validity claim.

String scanning requires a single or double quote and returns a `StringToken` with the delimiter-inclusive span of one ECMAScript string literal. Bytes are neither copied nor decoded. It accepts character escapes, `\0` without a following decimal digit, `\xHH`, `\uHHHH`, `\u{...}` up to 0x10FFFF, and escaped line continuations (including CRLF as one continuation). Unicode escapes can contain surrogate code points because the result is an original-source span, not a Rust string value. Raw U+2028 and U+2029 are legal string characters; raw CR and LF are rejected. Legacy octal escapes (`\1`, `\377`, `\0` followed by a decimal digit) and non-octal decimal escapes (`\8`, `\9`), which only sloppy code permits, return `LegacyDecimalEscape` at their backslash with `LegacyOctal::Reject`. With `LegacyOctal::Permit`, the token reports the backslash offset of the first one in `legacy_octal_escape`, so the parser can apply strict mode once it is known. Template literals use the separate scanner in section 4.4 and JSX attribute strings the one in section 4.13; JSON strings still require a future scanner.

Default limits are 100,000 retained comments per trivia invocation and 1 MiB per string, including its delimiters. `SourceText` separately bounds total source bytes. String bytes are checked before each scalar is consumed; comment count is checked before scanning another comment. Invalid starting offsets take precedence over lexical checks. Missing quotes, unclosed strings/comments, malformed escapes, exceeded limits, and allocation failures return typed errors with numeric offsets and no source snippets or partial result. String-limit errors identify the first scalar that would exceed the bound; invalid escape errors identify the backslash. Standalone scanner calls enforce local limits. The parser also applies aggregate comment, token, node, and nesting limits (section 4.12).

Both scanners are iterative and linear in consumed bytes. Trivia scanning steps over ASCII whitespace, line breaks, and comment text byte by byte and decodes only non-ASCII whitespace candidates; inside comments it recognizes U+2028 and U+2029 by their UTF-8 bytes, because no delimiter or line terminator can begin inside another UTF-8 sequence. String scans allocate no storage; trivia retains only bounded comment records and reserves storage fallibly. Original source, BOM, comments, and line endings remain unchanged. The parser selects lexical goals for the JavaScript grammar, JSX contexts (section 4.13), and TypeScript contexts (section 4.15). E1 passed and P-002 is accepted (`D-047`).

### 4.2 Numeric literals

`scan_js_number` scans one strict-mode ECMAScript numeric literal at a parser-selected offset, following [section 12.9.3](https://tc39.es/ecma262/multipage/ecmascript-language-lexical-grammar.html#sec-literals-numeric-literals), checked on 2026-10-12. It returns an exact span, spelling base (decimal, binary, octal, hexadecimal), value category (Number or BigInt), and a `legacy_octal` flag. Decimal fractions and signed exponents, radix prefixes, separators between digits, and integer `n` suffixes are supported. Leading signs remain separate operators. Legacy leading-zero integers, including `08`, return `LegacyLeadingZero` with `LegacyOctal::Reject`, as strict mode code requires. With `LegacyOctal::Permit`, a zero followed by octal digits only is a `LegacyOctalIntegerLiteral` (`017`, octal base) without fraction or exponent, so `07.5` ends before the dot; a zero followed by digits including 8 or 9 is a `NonOctalDecimalIntegerLiteral` (`089`, decimal base) that may take a fraction and exponent. Both set `legacy_octal`, and neither accepts separators in the integer part or a BigInt suffix. Malformed separators, missing radix/exponent digits, inappropriate BigInt suffixes, and adjacent ASCII identifier starts, backslashes, or extra decimal digits return typed errors.

The scalar directly after a literal must not be an ASCII decimal digit or an `IdentifierStartChar` (section 4.5); both return `InvalidNumericContinuation` at that scalar. A backslash also fails there, because it could only begin an escaped identifier start. Any other scalar, including continue-only identifier characters such as U+0660 or U+200D, ends the literal; the following token is the parser's concern. The earlier conservative `UnclassifiedNumericBoundary` error no longer exists.

`LexicalLimits.max_number_bytes` defaults to 1 MiB, including the radix prefix, separators, and suffix. Every consumed byte is checked; a limit error points to the first byte that would exceed the bound. Invalid starting offsets precede lexical checks, including with zero limits. Missing digits point to the expected digit offset (possibly EOF); malformed separators point to the underscore; legacy forms point to the digit after the leading zero; invalid continuations point to the following scalar. Syntax validation can inspect bounded lookahead without consuming it. No numeric value is evaluated, rounded, normalized, or allocated. This keeps the syntax layer independent of future static-evaluation semantics and preserves arbitrarily large BigInt spellings for later V1 to V3 analysis (`D-033`). The scan is iterative and linear in consumed bytes. It does not validate the surrounding expression or file, or implement the future recovery policy (`D-034`).

### 4.3 Punctuation and lexical goals

`scan_js_punctuator` recognizes the fixed ECMAScript punctuation grammar in [section 12.8](https://tc39.es/ecma262/multipage/ecmascript-language-lexical-grammar.html#sec-punctuators), with the input-element goals defined in [the lexical grammar](https://tc39.es/ecma262/multipage/ecmascript-language-lexical-grammar.html), checked on 2026-10-12. It returns a typed `PunctuatorToken` with an exact original-source span, or `None` without consumption when this scanner does not handle the input. A single internal grammar table generates the closed enum, exhaustive spelling function, and candidate list. A compile-time index derived from the same table groups the candidates by their first byte, so a scan compares at most the six spellings that begin with `>` instead of all 57. Longest-match selection is independent of table order. Scanning and lookahead are bounded by this fixed grammar; the result consumes one to four ASCII bytes and allocates nothing.

Every call requires `PunctuatorContext`; there is no guessed default. `JsLexicalGoal` exposes the four ECMAScript input-element goals. Slash and `/=` are punctuation only in `Div` and `TemplateTail`. Right brace is punctuation only in `Div` and `RegExp`. In other goals the scanner returns `None`, leaving the input to the separate template scanner (section 4.4) or the regular-expression scanner (section 4.7). Comment openings always return `None` for trivia handling. Hashbangs, legacy HTML comments, regular-expression bodies, template tails, JSX contexts, decorators, and private identifiers are not implemented by this punctuation scanner. A `None` result is not a syntax error, a valid token, or permission for a future parser to skip source bytes.

The `?.` operator is not consumed before an ASCII decimal digit: `?.3` produces `?`, leaving `.3` to numeric scanning. A dot immediately followed by a decimal digit also returns `None`. `GreaterThanMode::LongestMatch` handles ordinary operators; `Single` consumes only one `>` so the TypeScript parser can close nested type arguments and type parameter lists and rescan the remainder in a newly selected context (section 4.15). This explicit rescan contract keeps TSX ambiguity handling from guessing expression or type state (`D-033`). Invalid starting offsets produce the shared typed lexical error before inspection, including at partial UTF-8 boundaries. Valid EOF returns `None`. The parser applies aggregate token and depth limits and chooses contexts for the JavaScript grammar; The parser reads JSX tag punctuation byte by byte instead (section 4.13).

### 4.4 Template lexical components

`scan_js_template` implements the lexical components in ECMAScript [section 12.9.6](https://tc39.es/ecma262/multipage/ecmascript-language-lexical-grammar.html#sec-template-literal-lexical-components) and the tagged/untagged escape distinction in [section 13.2.8.1](https://tc39.es/ecma262/multipage/ecmascript-language-expressions.html#sec-template-literals-static-semantics-early-errors), checked on 2026-10-12. It takes immutable `SourceText`, an offset, explicit `TemplateContext`, and `LexicalLimits`. `TemplatePosition::Start` requires a backtick; `Continuation` requires the substitution-closing right brace selected by the parser in a template-tail lexical goal. There is no default or inferred context.

The result classifies exactly one `NoSubstitution`, `Head`, `Middle`, or `Tail` component. Its `span` includes both delimiters; `content_span` excludes the leading backtick/right brace and trailing backtick/`${`. Content spans may be empty. Unescaped `${` ends a head or middle; an unescaped backtick ends a no-substitution component or tail. Escaped delimiters stay inside content. Literal braces, quotes, slash sequences, and comment-looking text have no expression or trivia meaning inside a segment. The scanner never parses substitutions, counts expression braces, or manages a nested-template stack. The parser (sections 4.8 and 4.9) chooses when to resume scanning.

Character, hex, fixed-width Unicode, braced Unicode, and line-continuation escapes are recognized. `\0` is valid only without a following decimal digit. Decimal escapes, incomplete hex/Unicode escapes, and code points above 0x10FFFF are invalid. Surrogate code points are accepted as lexical spelling. Braced code points can have arbitrarily many leading zeros within the segment limit; value accumulation is capped to prevent arithmetic overflow while retaining lexical boundaries. Raw CR, LF, CRLF, U+2028, and U+2029 and escaped line continuations are preserved. `has_line_terminator` reports line breaks in the source, including continuations, without computing a cooked value.

`TemplateMode::Untagged` returns `InvalidTemplateEscape` at the first invalid escape's backslash. `Tagged` permits these spellings and sets `invalid_escape` to the first such offset in this segment, which means its ECMAScript cooked value is undefined. Later invalid escapes are still scanned correctly but do not add storage. Invalid escape prefixes leave their first nonmatching character for ordinary segment scanning, so a delimiter or another escape is not swallowed. The flag is valid tagged-template evidence, not parser recovery. An invalid escape in an untagged template remains a syntax error under `D-034`.

No bytes are copied, decoded, normalized, or evaluated. In particular, `content_span` is original spelling, not the ECMAScript raw value, which normalizes CR and CRLF. Future raw/cooked value decoding and static evaluation need separate contracts. This segment interface preserves source provenance and keeps expression grammar and value representation extensible for V1 to V3 (`D-033`, `D-035`).

`LexicalLimits.max_template_bytes` defaults to 1 MiB per segment, including delimiters. The limit is checked before each scalar is consumed, and a limit error points to the first scalar that would exceed it, including either byte of `${`. Offset validation precedes delimiter checks, which precede consumption. Invalid offsets, wrong delimiters, unclosed segments, invalid untagged escapes, and exceeded limits return typed errors without partial tokens. EOF without a segment terminator, including a dangling backslash, returns `UnterminatedTemplate` at the opening offset. If an invalid escape is recognized before EOF or a limit, untagged mode reports it first; tagged mode continues until a terminator, EOF, or the byte limit. Scanning is iterative, allocation-free, and linear in consumed bytes. Total source bytes are separately bounded by `SourceText`.

### 4.5 Pinned Unicode identifier classification

`is_js_identifier_start` and `is_js_identifier_part` implement ECMAScript's `IdentifierStartChar` (Unicode `ID_Start`, `$`, `_`) and `IdentifierPartChar` (Unicode `ID_Continue`, `$`) from [section 12.7](https://tc39.es/ecma262/multipage/ecmascript-language-lexical-grammar.html#sec-names-and-keywords), checked on 2026-10-12. Since Unicode 15.1, `ID_Continue` contains ZWNJ and ZWJ, and the specification no longer lists them separately. `UNICODE_VERSION` reports the pinned data version, `18.0.0` (`D-036`). Rust's own Unicode predicates are never used for identifiers, because their properties and version differ.

The data comes from `DerivedCoreProperties-18.0.0.txt` of the Unicode Character Database. `tools/frameshift-unicode-gen` accepts only that version. It also reads `PropertyValueAliases-18.0.0.txt` for the property value names of section 4.7. It verifies each property's declared code point total, rejects malformed, reversed, overlapping, surrogate, and out-of-range entries and data outside its property section, checks that `ID_Start` is contained in `ID_Continue`, merges adjacent ranges, and renders sorted, disjoint inclusive ranges: 695 for `ID_Start` (158,739 code points) and 814 for `ID_Continue` (162,100 code points). From `PropertyValueAliases.txt` it collects every General_Category and Script value name and alias, inside their sections only, rejecting malformed names and names repeated across lines, and renders them byte-wise sorted: 80 and 351 names. Script_Extensions uses the Script values. The generated header records each source's version, date, and byte size, and repeats Unicode's copyright and terms notice. The source files are not committed. The files used for the committed tables had the SHA-256 hashes recorded in `D-036` and `D-037`. The generated module is excluded from rustfmt, so formatter changes cannot alter it.

ASCII is classified directly. Other scalars use one binary search over static ranges, with no allocation. ECMAScript requires the latest Unicode version, so a new Unicode release needs a deliberate regeneration and decision update. The derived data is subject to Unicode's terms; `THIRD_PARTY_NOTICES.md` must cover it before any distribution ([SECURITY.md](SECURITY.md), section 11).

### 4.6 Identifier names, private names, and reserved words

`scan_js_identifier` scans one `IdentifierName`, or a `PrivateIdentifier` when the offset holds `#`, following [section 12.7](https://tc39.es/ecma262/multipage/ecmascript-language-lexical-grammar.html#sec-names-and-keywords), checked on 2026-10-12. It takes immutable `SourceText`, a parser-selected offset, and `LexicalLimits`. The caller must select JavaScript context. JSX names (which allow `-`) and JSX text use the scanners of section 4.13, and the parser scans hashbangs itself. The result holds the kind (`Name` or `PrivateName`), the exact span including `#` and escape spellings, the `name_span` without `#`, `has_escape`, and `reserved_word`.

Characters are classified with the pinned tables of section 4.5. A `\u` escape with four hexadecimal digits, or a braced code point up to U+10FFFF, contributes one code point, which must itself be permitted at its position: an escape cannot introduce a code point that would be invalid unescaped. Surrogates are never identifier characters. Any other backslash inside or directly after the name returns `InvalidIdentifierEscape` at the backslash, because no ECMAScript token can follow a name with a backslash. A name ends at the first scalar that is not an `IdentifierPartChar`, such as whitespace, punctuation, or a symbol. No Unicode normalization is applied, so canonically equivalent spellings stay distinct, as the specification requires.

`reserved_word` reports the `ReservedWord` whose spelling equals the name's StringValue after decoding escapes, so `els\u{65}` reports `Else`. `has_escape` lets the parser apply the rule that keywords cannot contain escapes. `ReservedWordClass` distinguishes words that are never identifiers, the contextual `await` and `yield`, and the strict-mode words `implements`, `interface`, `let`, `package`, `private`, `protected`, `public`, and `static`. Private names never report reserved words. Contextual keywords (`as`, `async`, `from`, `get`, `meta`, `of`, `set`, `target`) and TypeScript keywords are not reserved; the parser compares their unescaped spellings. Whether a token is a keyword, a permitted identifier, or an early error depends on strict mode, the module goal, and function context, which this scanner does not know. ASCII name characters are classified directly, other scalars through the tables. Every reserved word is lowercase ASCII and at most ten bytes long, so the candidate StringValue is packed into a 128-bit key while it is scanned and looked up by binary search in a table of keys that is derived from the reserved-word table and sorted at compile time. Classification allocates nothing.

`LexicalLimits.max_identifier_bytes` defaults to 1 MiB, including `#` and escape spellings, and is checked before each scalar is consumed. Offset validation precedes the start check, which precedes consumption. `ExpectedIdentifier` points to the scalar that cannot start the name (after `#` for private names, possibly EOF). Malformed escapes, escapes of disallowed code points, and stray backslashes point to the backslash. Limit errors point to the first scalar that would exceed the bound. Braced escapes can have arbitrarily many leading zeros within the limit, and value accumulation is capped to keep scanning linear. Scanning is iterative, allocation-free, and linear in consumed bytes. It does not validate the surrounding syntax or implement recovery (`D-034`).

### 4.7 Regular-expression literals

`scan_js_regexp` scans the lexical extent of one literal following [section 12.9.5](https://tc39.es/ecma262/multipage/ecmascript-language-lexical-grammar.html#sec-literals-regular-expression-literals), checked on 2026-10-12, at a slash that the parser selected in a regular-expression lexical goal. It returns `RegExpToken` with the exact span, the `body_span` (BodyText), and the `flags_span` (FlagText, possibly empty). `//` and `/*` return `ExpectedRegExp`, because they begin comments in every goal. Inside a class, `/` does not end the body, and a backslash escapes any non-terminator. A line terminator anywhere in the literal, including after a backslash or inside a class, returns `RegExpLineTerminator` at the terminator; EOF returns `UnterminatedRegExp` at the opening slash. Flags are the following `IdentifierPartChar`s. A backslash directly after them returns `InvalidRegExpFlag`, because flags cannot contain escapes and no token can follow the literal there. The token is evidence of extent, not of validity.

`validate_js_regexp` rescans the literal and applies `IsValidRegularExpressionLiteral` from [section 13.2.7.2](https://tc39.es/ecma262/multipage/ecmascript-language-expressions.html#sec-isvalidregularexpressionliteral) (`D-037`). Flags must be among `dgimsuvy`, each at most once, and not `u` together with `v`; errors point to the offending flag (`InvalidRegExpFlag`, `DuplicateRegExpFlag`, `IncompatibleRegExpFlags`). The pattern must then parse under the grammar of [section 22.2.1](https://tc39.es/ecma262/multipage/text-processing.html#sec-patterns) with all early errors. The result is `RegExpLiteral` with the token, typed `RegExpFlags`, and the number of capturing groups. Pattern errors are `InvalidRegExpPattern` with a closed `RegExpPatternError` reason at a pattern offset: unmatched or unterminated groups, invalid groups, modifiers, or group names, duplicate or unresolved names, too many groups, nothing to repeat, out-of-order quantifier ranges, lone syntax characters, invalid escapes, backreferences, or property escapes, negated classes with strings, invalid class ranges, unterminated nested classes, and invalid class set syntax. Scanning and validation are separate so that a future parser can still skip a literal with an invalid pattern at a known lexical boundary; the file remains `unknown` (`D-034`).

With `u` or `v`, the Unicode-mode grammar applies, and `v` adds UnicodeSets classes: nested classes, `&&` and `--` operators that cannot be mixed, `\q{...}` string alternatives, escaped reserved punctuators, the ban on unescaped class syntax characters and reserved double punctuators, and the MayContainStrings rules for negated classes and `\P`. Without either flag, the web-compatible grammar of [Annex B.1.2](https://tc39.es/ecma262/multipage/additional-ecmascript-features-for-web-browsers.html#sec-regular-expressions-patterns) applies. There, `]`, `{`, and `}` outside a quantifier are characters, but `{n}` without a preceding atom remains an error. Identity escapes accept any character except `c`, and except `k` when named groups apply. `\c` without a control letter matches a backslash, legacy octal escapes and decimal escapes beyond the group count are characters, class escapes as range endpoints make `-` a literal, and lookaheads can be quantified. As Annex B.1.2.9 requires, a pattern that contains a group name is parsed again with named groups, where `\k` must start a resolvable group reference. Without Unicode mode, classes see UTF-16 code units: an astral character is two class atoms, so `/[😀-😂]/` is out of order as in browsers, while `/[😀-😂]/u` is valid. Escaped surrogate pairs combine only in Unicode mode and in group names, which always use the Unicode-mode escape forms.

Duplicate group names are permitted only when the groups cannot both participate (section 22.2.1.4), that is, when the deepest disjunction containing both has them in different alternatives. Each name is compared only with its latest previous group, by a binary search over the open groups, which is sufficient because earlier same-named groups were already pairwise exclusive. Backreferences may precede their groups and are resolved after parsing; with several unresolved references, the first in source order is reported. Quantifier bounds are compared as digit strings, so arbitrarily long bounds cannot overflow. Class ranges compare CharacterValues, including legacy octal and control escapes.

Property escapes accept `Name=Value` for General_Category (`gc`), Script (`sc`), and Script_Extensions (`scx`), and lone General_Category values or binary properties from table 66. Binary properties of strings from table 67 are accepted only in UnicodeSets mode and never in `\P` or a negated class. General_Category and Script values come from the generated Unicode 18.0.0 tables (section 4.5), including aliases such as `punct` and `Qaai`. Tables 66 and 67 are written by hand from the specification, with compile-time assertions that every table is sorted and free of duplicates. Matching is exact and case-sensitive. `Hrkt` is accepted because PropertyValueAliases.txt lists it, although V8 rejects it.

`LexicalLimits.max_regexp_bytes` defaults to 1 MiB, including both slashes and the flags. It is checked before each scalar is consumed, and a limit error points to the first scalar that would exceed it. Offset validation precedes the opening-slash check, and lexical errors precede flag and pattern errors. Patterns are never compiled or executed, so validation cannot backtrack. The validator is iterative, with explicit stacks for open groups and nested classes, so nesting depth cannot exhaust the call stack. Its storage for open groups, nested classes, group names, and pending references is proportional to the pattern and reserved fallibly (`AllocationFailed`). Time is linear in literal bytes apart from hash lookups of group names and binary searches over properties and open groups. A standard hash map holds the names only for lookups; no result depends on its iteration order. Matching semantics, case folding, and raw or cooked value decoding are not implemented.

### 4.8 Syntax tree arena and expression grammar

The parser in `src/parser/` returns a `SyntaxTree` borrowing the immutable `SourceText`. The tree stores source spans rather than copied token text or decoded values. `NodeId` indexes a flat node arena and has a non-zero representation, so `Option<NodeId>` stays four bytes; a compile-time assertion keeps a `SyntaxNode` at most 40 bytes. Statement lists, elements, properties, parameters, arguments, declarators, class elements, and module specifiers use contiguous ranges of a shared child arena, and template parts use a separate one. Every node span and the consumed span are half-open byte ranges into the original source, and child spans nest inside their parent in source order. Statement spans include their semicolon when the source has one. `SyntaxTree::child_nodes` iterates a node's direct children in source order without allocating, skipping template segments, which are not nodes; it is the traversal that tests and future consumers use. `SyntaxTree::string_literal_value` decodes the StringValue of a string literal node on request, with every escape, and returns `None` for other nodes or a value with an unpaired surrogate; the tree itself still stores no decoded values. Comments are retained in source order, and any parse error returns no partial tree.

`parse_js_expression` parses one complete expression from a caller-selected byte offset with an explicit `JsDialect` (section 4.13). The expression grammar is complete, and the JSX dialect adds JSX elements and fragments while the TypeScript dialects add assertions, `as` and `satisfies`, instantiation expressions, and non-null expressions (section 4.15): identifier references; literals, including legacy octal forms where sloppy code permits them; validated regular-expression literals; templates and tagged templates; array and object literals with holes, spread, shorthand properties, computed keys, methods, getters, setters, and async and generator methods; function, async function, generator, and class expressions; arrow and async arrow functions with expression or block bodies; prefix unary, `await`, `yield` and `yield*`, update, binary, comma, conditional, and assignment expressions with all compound and logical operators; dot, computed, private (`a.#x`), and optional members; calls, optional calls, `super` calls and properties, `new`, `new.target`, `import(...)` with an optional options argument, `import.meta`, and `#name in object`. A Pratt parser applies JavaScript operator precedence and associativity and explicitly selects regexp, division, and template-tail lexical goals; inside any braces, a right brace closes the construct rather than a template substitution. No line terminator may precede `=>`, a postfix update operator, or an async arrow's parameters, and none may follow `yield` before its operand. Only a comma can continue an AssignmentExpression, such as an arrow function, a `yield` expression, a conditional, or an assignment, so `a = () => {} + 1` is an error and a line break before the `+` ends the statement. A nested `new` consumes the first argument list, as `new MemberExpression Arguments` requires. The parser rejects invalid unparenthesized unary or `await` exponentiation, unparenthesized mixing of `??` with `&&` or `||`, optional chains used as template tags or `new` constructors, arrows where only a higher-precedence operand is permitted, and private names outside a member access or the left operand of `in`. The `[~In]` grammar parameter is a parser flag that excludes the `in` operator in `for` heads until brackets, braces, parentheses, templates, or a conditional's middle operand restore it.

Destructuring follows the cover grammar. Array and object literals, parenthesized lists before `=>`, call arguments after `async`, and parameter lists are parsed as expressions first. Once `=`, `=>`, a declaration, or a `for-in`/`for-of` head decides their role, the same arena nodes are reinterpreted in place (`set_kind`), keeping IDs and spans: array and object literals become `ArrayPattern` and `ObjectPattern`, properties become `PatternProperty` or `ShorthandPatternProperty`, spread elements become `RestElement`, and `target = default` becomes `AssignmentPattern`. Assignment targets keep identifier references and may be members or parenthesized simple targets. Parameters and declared bindings become `BindingIdentifier`s and admit no members or parentheses. Rest elements must be last, without a following comma or default, and an object rest target cannot be a nested pattern. Conversion fails closed: a node kind that is not a valid target in the requested mode, such as a method, is rejected. Cover lists also record the first `yield` or `await` expression and, in scripts, the first `await` used as a name, which arrow parameters and async arrow heads reject. Shorthand initializers (`{ a = 1 }`) and duplicate `__proto__` properties are errors only in object literals that do not become patterns. They are recorded per object and checked after the complete expression or program is parsed, reporting the earliest remaining one, so a later syntax error can take precedence. Every node of a returned tree is reachable from the root.

The expression is parsed as if it were outside any function, class, or method, with an unknown source goal and unknown strictness. Constructs whose validity depends on that context fail closed with typed errors (`D-038`, `D-039`): `await` and `yield` outside async functions and generators (`ContextualKeywordRequiresContext`), words that only strict code reserves (`ReservedWordRequiresContext`), constructs that are valid only in sloppy mode (`StrictModeRequiresContext`), HTML-like comment spellings and `import.meta` (`SourceGoalRequiresContext`), `new.target` (`MetaPropertyRequiresContext`), `super` (`SuperRequiresContext`), and private names outside a class (`PrivateIdentifierRequiresContext`). Function and class bodies inside the expression have known context: a class is strict, a function with a `"use strict"` directive is strict, and `new.target` and `super` follow the enclosing function or method.

### 4.9 Program parser

`parse_js_program` parses complete source text with an explicit `SourceGoal` and `JsDialect` and returns a tree whose root is a `Program` node spanning the whole text, including a leading byte order mark (`D-039`). It covers the complete ECMAScript syntactic grammar, plus JSX in the JSX dialect (section 4.13) and the types, declarations, and extensions of the TypeScript dialects (section 4.15), as specified in the [statements and declarations](https://tc39.es/ecma262/multipage/ecmascript-language-statements-and-declarations.html), [functions and classes](https://tc39.es/ecma262/multipage/ecmascript-language-functions-and-classes.html), and [scripts and modules](https://tc39.es/ecma262/multipage/ecmascript-language-scripts-and-modules.html) clauses of the ECMAScript 2027 draft, checked on 2026-10-12: blocks, `var`, `let`, `const`, `using`, and `await using` declarations, all control statements including `for-in`, `for-of`, and `for await`, `switch`, `try`, labels, `with`, and `debugger`; function, generator, async, and async generator declarations; classes with heritage, constructors, methods, accessors, public and private fields and methods, static members, and static blocks; and import and export declarations with import attributes. A hashbang comment at the start is retained as `CommentKind::Hashbang`, also after a byte order mark, which is an encoding signature rather than source text.

Automatic semicolon insertion follows the specification: a semicolon is inserted before `}`, at the end of the input, or after a line terminator, never in a `for` head, and the semicolon after `do ... while (...)` is always optional. `return`, `break`, `continue`, `throw`, postfix update operators, `yield`, `async`, and `=>` honor their `[no LineTerminator here]` restrictions; a line terminator after `throw` is an error. Statement-start ambiguities use bounded lookahead that restores the parser state: `let` starts a declaration before `[`, `{`, or a name, and an expression otherwise; `async` followed on the same line by `function` starts a declaration; `using` followed on the same line by a name starts a declaration, except `using of` in a `for` head unless `=` follows; `await using` follows the same rule where `await` is a keyword; an identifier followed by `:` is a label. `import` followed by `(` or `.` is an expression.

Each function, method, field initializer, and static block is a context boundary that saves and replaces the parser context: strictness, whether `return` is allowed, whether `yield` and `await` are keywords, whether `await` is reserved, whether parameters are being parsed, permission for `new.target`, `super` properties, and `super` calls, and whether `arguments` is forbidden. Arrow functions inherit the enclosing function's `new.target`, `super`, and `arguments` rules. Class field initializers do not treat `yield` or `await` as keywords; a static field initializer reserves `await` like a static block. The specification's grammar states no early error for `await` in a static field initializer, but V8 rejects it, so this is the stricter reading. Labels and the loop and `switch` depth are reset at every boundary, so `break` and `continue` never cross functions or static blocks.

The tree records `FunctionKind`, `MethodKind` (including `Constructor`), `VariableKind`, `MetaPropertyKind`, whether a `for-of` is `for await`, and strictness on `Program` and `FunctionBody` nodes. `FunctionBody.strict` is true when the body is known to be strict code; in a context-free expression, inherited strictness is unknown and reported as false. Without `from`, an export specifier's local name becomes an `Identifier` reference to a module binding; with `from`, it stays an `IdentifierName` or string.

### 4.10 Source goals, strictness, and Annex B

Module code is always strict, permits `await` at the top level, and reserves `await` everywhere else. Script code is sloppy unless a directive prologue contains `"use strict"`, spelled exactly with either quote and without escapes. A function becomes strict through its own prologue; class code is always strict. The `"use strict"` directive applies retroactively: an earlier directive with a legacy octal escape becomes an error, and the function name and parameters are validated against strict mode after the prologue, so `function eval() { "use strict" }` and `function f(a, a) { "use strict" }` are errors. A `"use strict"` directive in a function with a non-simple parameter list is an error.

Sloppy scripts support the complete web-compatibility grammar of Annex B ([section B.3](https://tc39.es/ecma262/multipage/additional-ecmascript-features-for-web-browsers.html#sec-other-additional-features), checked on 2026-10-12) as well as sloppy-mode names: HTML-like comments (section 4.1); legacy octal and non-octal decimal literals and escapes, which the scanners report with `LegacyOctal::Permit` and the parser rejects in strict code; `with`; labelled function declarations; plain function declarations as `if` clauses, wrapped in their own block scope; repeated plain function declarations in a block or `switch`; initializers in `for (var name = value in object)`; `var` redeclaring a simple catch parameter; call expressions as targets of `=`, compound assignment, update, and `for-in` or `for-of`; `let`, `static`, `implements`, `interface`, `package`, `private`, `protected`, `public`, and outside generators `yield` as names; `eval` and `arguments` as bindings and assignment targets; `delete` of a name; and duplicate parameter names in simple parameter lists of function declarations and expressions, including async and generator functions. Strict code rejects each of these with `StrictMode(StrictModeError)` or the corresponding typed error. Arrow functions and methods never permit duplicate parameters.

Where V8 rejects source text that the specification accepts, the parser rejects it as well, because no engine could load the file: `<!--` between tokens of module code returns `HtmlCommentInModule`, and the static field rule above applies. Where V8 accepts source text that the specification rejects, the parser follows the specification: `-->` at the very start of a script is not a comment, and a call expression is not an assignment target in strict code. Stage 3 proposals such as source-phase imports (which V8 accepts) and decorators are not part of the specification and are syntax errors.

### 4.11 Early errors and transient scopes

All early errors of the supported grammar are reported while parsing, using state that exists only during one parse (`D-039`). Declarations are tracked in a stack of transient scopes keyed by StringValue: script, function, and static block top levels, where functions behave like `var`; the module top level, where functions are lexical; blocks, `switch` case blocks, and `for` heads; and catch clauses, which hold the catch parameter and the handler's declarations together. A `var` declaration is recorded in every scope up to its function, so a later lexical declaration in any of them sees the conflict. This reports duplicate lexical declarations, lexical declarations that conflict with `var`, parameters, or catch parameters, `let` as a lexically bound name, and the Annex B relaxations in sloppy code. Labels are a per-function stack: nested duplicates, undefined `break` and `continue` targets, `continue` to a label that does not name a loop, unlabelled `break` outside loops and `switch`, and `continue` outside loops are errors. Private names are collected per class; a reference may precede its declaration and is resolved when the class body ends, unresolved names move to the enclosing class, and names unresolved at the outermost class are errors. Duplicate private names are errors, except a getter and setter pair with the same placement. Classes also reject duplicate constructors, special-method constructors, a field named `constructor`, a static member named `prototype`, `#constructor`, `delete` of a private member, `arguments` in field initializers and static blocks, and `super()` outside derived-class constructors. Modules reject duplicate exported names compared by StringValue, export names with unpaired surrogates, local export names that are strings or reserved words, exported local bindings that the module's top level does not declare, and duplicate import attribute keys. The semantic layer (M4) will build its own scope graph from the tree; the parser's scopes are discarded.

### 4.12 Limits and stack use

`ParseLimits` defaults to 100,000 syntax nodes, 200,000 consumed tokens, and 256 nested parser calls, in addition to lexical byte and comment limits. Child-arena entries are bounded by the node limit. Comments, nodes, child ranges, template parts, bound names, labels, class scopes, and pending expression-only errors reserve fallibly; the scope maps use the standard hash map only for lookups, and no result depends on their iteration order. Reaching a configured bound or failing storage reservation returns a typed parse error. The parser is recursive descent; the depth bound is checked before each nested expression, `new`, statement, function, arrow function, method, and class, and pattern conversion and declared-name collection follow nesting that parsing already bounded. The bound limits recursion, not tree depth: member, call, and binary chains are built in loops, so a tree can be as deep as the node limit, and consumers traverse it with explicit stacks (section 11.1). Parsing is linear in tokens and nodes apart from the O(n log n) duplicate-parameter check, hash lookups, and `var` declarations, which visit at most the bounded scope depth. The parser keeps no token stream. Its grammar peeks at the next token several times before consuming it, so it caches the last scanned identifier, the last scanned punctuator with its lexical goal, and the offset where the last trivia skip stopped; a repeated peek at the same offset and goal reuses the result instead of scanning again. Scans are pure functions of these inputs, and a skip always stops before a non-trivia character, so the caches cannot change a result. Child lists are collected in buffers that are reused once their list has been appended to the child arena, so after the first lists of a nesting level, a list costs no allocation. Measured on Windows x86_64 by recording the lowest stack address the parser reaches in 26 constructs nested past the bound, an optimized build uses at most about 1.4 KiB of stack per depth unit, about 350 KiB at the default bound, so a 1 MiB main-thread stack suffices. Calls, `for`, and `try` statements nest most deeply. The throughput increment raised the maximum from about 1.3 KiB per unit, because inlined lookahead helpers enlarge the recursive frames; an earlier figure of 1.1 KiB was measured with fewer constructs. Unoptimized builds use up to about 15 KiB per unit, so tests that reach the bound run on a thread with an explicit 64 MiB stack. Long `else if` and conditional chains consume one depth unit per link. JSX nesting needs less stack: the smallest thread stack on which an optimized build reaches the bound, searched in 64 KiB steps, is 193 KiB for nested elements, fragments, and child containers and 129 KiB for nested attribute values and spread attributes, against 321 KiB for nested parentheses, calls, and arrays. Throughput and memory of the TypeScript dialects and a real-world sample are measured (section 6, `D-043`). Together with the span comparison with the pinned compiler (section 5), the fuzzing budget run (section 7), and the accepted maintainability review (section 8), these measurements complete E1 (`D-047`); reference-hardware measurements follow before releases in M11.

### 4.13 JSX

`JsDialect` selects the language variant explicitly: `JavaScript` or `Jsx` (`D-041`). Both `parse_js_program` and `parse_js_expression` take it, and `Program` nodes record it. The parser never infers it from the content; the project layer will map file names and configuration to a dialect. With `Jsx`, a `<` at the start of a primary expression begins an element or fragment, in either source goal, following the [JSX specification](https://facebook.github.io/jsx/), checked on 2026-10-12. With `JavaScript`, such a `<` remains `ExpectedExpression`. `yield` treats `<` as the start of its operand in the JSX dialect.

Three scanners take a parser-selected offset and `LexicalLimits`. `scan_jsx_identifier` returns the span of a `JSXIdentifier`: an `IdentifierStartChar` followed by `IdentifierPartChar`s and hyphens, classified with the pinned tables of section 4.5, so `data-id` and `aria-` are names. JSX names have no escapes: a backslash at the start of, inside, or directly after a name returns `InvalidIdentifierEscape` at the backslash. Reserved words are ordinary JSX names, and `max_identifier_bytes` bounds them. `scan_jsx_string` returns a `JsxStringToken` with the quote-inclusive span and the content span of an attribute string. JSX strings have no escapes, so a backslash is an ordinary character, and they may contain line terminators; EOF returns `UnterminatedString` at the opening quote, and `max_string_bytes` bounds them. `scan_jsx_text` returns the span of text up to the next `{` or `<`, or EOF, possibly empty. The first `>` or `}` returns `InvalidJsxTextCharacter` at its offset, as the grammar requires; the new `max_jsx_text_bytes` limit, default 1 MiB, takes precedence when the text exceeds it earlier. Limit errors point to the first scalar that would exceed the bound. None of the scanners decodes, trims, or normalizes text, and character references such as `&amp;` stay part of the original spelling.

Tags are token sequences with ordinary JavaScript trivia between their tokens, including comments, which are retained, and HTML-like comments in scripts. Tag punctuation (`<`, `>`, `/`, `=`, `.`, `:`, `{`, `}`) is read byte by byte, because the JavaScript punctuator scanner would join `>` with a following `=` or `>`: `<a>=</a>` is an element with the text `=`. Children are never trivia: text runs from the end of a tag or container to the next `{` or `<`, so `// x` or `/* x */` inside an element is text. Expression containers, spread attributes, and spread children hold one AssignmentExpression parsed with the enclosing function context, in braces that restore the `in` operator and reset template-substitution tracking. An empty child container `{}` may hold only trivia; its comments are retained.

Fifteen node kinds represent the grammar. `JsxElement` holds a `JsxOpeningElement` (name, attributes, `self_closing`), the children, and a `JsxClosingElement` unless it is self-closing. `JsxFragment` holds `JsxOpeningFragment`, children, and `JsxClosingFragment`. Names are `JsxIdentifier`, `JsxNamespacedName` (`svg:rect`), or a left-nested `JsxMemberExpression` (`Menu.Item.Label`); a namespaced name cannot be part of a member chain, and attribute names cannot be members. Attributes are `JsxAttribute` with an optional value (a `JsxStringLiteral`, a `JsxExpressionContainer`, an element, or a fragment) or `JsxSpreadAttribute`. Children are `JsxText`, elements, fragments, `JsxExpressionContainer` (with no expression for `{}`), and `JsxSpreadChild`. Text and strings are represented by their original spans only. Every span is exact: elements and fragments span from `<` to their final `>`, tags span their delimiters, attributes span from their name to their value, and containers include their braces.

Errors are typed and fail closed. A closing tag must match its opening tag in form and in the structure and spelling of its name, regardless of trivia between name parts; otherwise `JsxClosingTagMismatch` points to the closing `<`. EOF among children returns `UnclosedJsxElement` at the opening `<`. A tag that continues with something other than an attribute, `/>`, or `>` returns `ExpectedJsxTagEnd`; an `=` without a valid value returns `ExpectedJsxAttributeValue`; an attribute container without an expression returns `EmptyJsxAttributeValue`. A container holding a comma expression, including a spread child such as `{...a, b}`, fails with `ExpectedClosingBrace`, as the grammar requires; Babel accepts the spread child. A `<` token directly after an element or fragment expression returns `AdjacentJsxElements`, because the reference compilers reject adjacent elements without a wrapper, although the grammar would read a comparison; `<=`, `<<`, and other operators are unaffected. Namespaced names and spread children are accepted, because target support is a question for later rules (`D-041`).

Each element or fragment is a nesting level of the parser's depth bound, in addition to the expressions in its containers. Tokens, nodes, child lists, and comments count against the limits of section 4.12. The parser does not decode character references; section 4.14 describes the decoders.

### 4.14 Character references

The parser keeps JSX text and attribute strings as original spans (section 4.13). Two decoders in `src/reference.rs` read one HTML character reference at a caller-selected offset of any `&str`, such as a JSX text span or printer output, under the two semantics a JSX-to-Astro migration meets (`D-041`). Both validate the offset like the scanners (`InvalidOffset` outside the text or inside a scalar), return `None` when no reference starts there, so the `&` is literal text, and allocate nothing.

`decode_jsx_character_reference` follows the JSX compilers Babel, TypeScript, and SWC. A reference is `&#` decimal digits `;`, `&#x` hexadecimal digits `;` (only a lowercase `x`), or `&` name `;` with one of the 253 XHTML 1.0 entity names, compared case-sensitively. The semicolon is required. Numeric values above U+10FFFF are not references, while zero and surrogate code points are, because the compilers emit them as UTF-16 code units; `JsxCharacterReference` therefore holds a `code_point` rather than a `char`, and `as_char` returns `None` for a surrogate. The name lookup reproduces Babel's search for the semicolon within ten characters, which every XHTML name satisfies.

`decode_html_character_reference` follows the character reference states of the [WHATWG HTML tokenizer](https://html.spec.whatwg.org/multipage/parsing.html#character-reference-state), checked on 2026-10-12, in an explicit `HtmlReferenceContext`. After `&` and an ASCII alphanumeric, the longest of the 2,231 WHATWG names that the text continues with matches, including the 106 legacy names without a semicolon, so `&notit;` decodes `&not` and leaves `it;`. In `Attribute` context, a match without a semicolon that is followed by `=` or an ASCII alphanumeric stays literal. `&#` with decimal digits, or `&#x` or `&#X` with hexadecimal digits, is a numeric reference with an optional semicolon; zero, surrogates, and values above U+10FFFF become U+FFFD, the 27 C1 positions that Windows-1252 assigns become those characters, and other values, including noncharacters and controls, are kept. Digit values are capped above U+10FFFF, so long runs cannot overflow. `HtmlCharacterReference` holds the span, a `Named` value of one or two characters or a `Numeric` character, and whether a semicolon ended the reference, since HTML reports a parse error for the others. The two semantics differ: `&check;` and `&amp` are HTML references but not JSX ones, `&#X41;` and `&#128;` decode differently, and `&lang;` and `&rang;` are the only names whose values differ between the tables (U+2329 and U+232A in XHTML, U+27E8 and U+27E9 in HTML).

The tables in `src/entity_tables.rs` are generated by the development-only `tools/frameshift-entity-gen` from local copies of the WHATWG `entities.json` and the W3C XHTML 1.0 entity sets `xhtml-lat1.ent`, `xhtml-symbol.ent`, and `xhtml-special.ent`; they are never edited by hand. The generator accepts only the exact layouts of these files: one JSON entry per line with code points and `\u` escapes that must agree, and first-column `<!ENTITY>` declarations with decimal values. It checks the counts (2,231 references; 96, 124, and 33 entities), unique ASCII alphanumeric names, Unicode scalar values, that every legacy HTML name also exists with a semicolon and the same value, and the ISO 8879 notice of the XHTML files, and renders byte-sorted tables in ASCII with braced escapes. Its header records each source's byte size and the WHATWG and ISO notices. Compile-time assertions in `src/reference.rs` keep both tables sorted and complete, which the binary searches rely on. The WHATWG list is declared static by the HTML Standard, and the XHTML sets are final, so regeneration is not expected; the file hashes are recorded in `D-041`. The derived data carries notice obligations into `THIRD_PARTY_NOTICES.md` before any distribution ([SECURITY.md](SECURITY.md), section 11).

### 4.15 TypeScript and TSX

`JsDialect` adds `TypeScript`, `Tsx`, and `TypeScriptDeclaration`, and `parse_js_program` and `parse_js_expression` parse them only when a caller selects one: a `Program` records the dialect, nothing infers it from a name or from the content, and mapping file names and project configuration to a dialect belongs to the project layer. Both dialects share the JavaScript grammar, its strictness handling, its scanners, its limits, and the ECMAScript early errors of section 4.9, with one exception: they report no redeclaration errors. TypeScript adds the type grammar, the declaration forms, and the extensions to expressions, functions, classes, and modules of the pinned compiler, without type checking, so a file that parses can still be rejected by the checker. In `TypeScript`, `<Shape>value` is an assertion. In `Tsx`, `<` begins JSX unless the generic arrow reading holds, and that reading follows the pinned compiler: `<T,>(value: T) => value`, `<T extends object>(value: T) => value`, and `<T = unknown>(value: T) => value` are arrows, while `<T>(value: T) => value` fails in TSX as an element whose attribute list is invalid and succeeds as an arrow in `TypeScript`. Element names, attributes, children, and the text and reference rules of section 4.13 stay unchanged, and a TSX element name may carry type arguments, as in `<Box<Item> value={item} />` and `<Box<T>>{value as T}</Box>`.

`TypeScriptDeclaration` is the dialect of declaration files such as `next-env.d.ts` (`D-043`). It is the TypeScript grammar without JSX, with the whole file in an ambient context, as the pinned compiler treats files named `.d.ts`, `.d.mts`, and `.d.cts`: every declaration behaves as if it were marked `declare`, so `export const value: string;` omits its initializer, which the `TypeScript` dialect rejects as the ECMAScript early error `MissingInitializer`. The parser never reads file names; the caller maps a declaration file to this dialect.

Every TypeScript production is a structured `TypeScriptKind` node with an exact source span in the shared arena, and optional syntax is absent rather than a synthetic span. Every start offset of the TypeScript grammar is read after the trivia in front of the first token, as in the JavaScript grammar, so no node starts on whitespace or a comment; before this rule, a parameter list after type parameters, as in `function f<T> (x: T) {}`, and the type parameter of a mapped type after `[` started on trivia. `Keyword` keeps the spelling of a primitive or `unique`/`typeof` keyword in its source span, `Reference` holds an entity name and optional type arguments, `QualifiedName` holds a dotted name, `TypeParameters` records whether its last parameter is followed by a comma, which TSX needs, `TypeParameter` holds its modifiers, name, `Constraint`, and `DefaultType`, and the remaining kinds cover parenthesized, union, intersection, conditional, and tuple types with labeled, optional, and rest elements; `keyof`, `unique`, and `readonly` operators; `infer` with an optional constraint; arrays; indexed access; literal, template literal, `typeof`, and `import()` types with attributes and qualified names; type literals with property, method, call, construct, and index signatures, including optional and definite markers; mapped types with modifiers and `as` remappings; function and constructor types, including the JSDoc-compatible form `function(string): void`; and `this` and `asserts` predicates. Assignability, inference, and compiler-option-dependent rules stay outside this layer.

Class members take their modifiers in any order, and `static` followed by a TypeScript-only modifier, as in `static readonly`, `static override`, or `declare private static readonly`, becomes a modifier node while the member keeps its static flag, which private names and `await` in static initializers depend on. Like in the compiler, `static` may be followed by a line break and the other modifiers may not. Object and mapped types end at their own right brace also inside a template substitution, as in `${value as { a: T }}`. Declarations and statements cover `type` aliases, interfaces with `extends` heritage and members, enums with initializers, namespaces and ambient modules with bodies, the `declare` modifier and ambient contexts, type-only imports, exports, and specifiers, `import x = require("...")` declarations, `export =`, and `export as namespace`, overload signatures as bodyless functions, and decorators. As in the compiler's parser, function declarations and class and object methods may omit their body, but function expressions may not; the `BodylessFunction` node that stands for the missing body spans the return type and the semicolon, or only the semicolon, and is empty where a semicolon is inserted. Expressions and bindings add `as` and `satisfies` at comparison precedence, prefix assertions, `!` in postfix position, instantiation expressions, `this` parameters, annotations with optional and definite markers, modifiers on parameters, object members, and class members including `abstract`, `public`, `private`, `protected`, `override`, `readonly`, and `static`, parameter properties, generic methods and object-literal methods, and annotations on `catch` clauses.

An instantiation expression like `const bound = call<string>` is a `TypeScriptKind::Instantiation` node whose children are the callee and the type arguments. Whether `a < b > c` compares or instantiates follows the pinned compiler. Its closing `>` is re-scanned together with a directly following `>` or `=`, so a list followed directly by `=` is no type argument list: `f<T>= x` and `"s" < b, c >= d` compare, and `f<T>== x` fails as in the compiler. Otherwise `canFollowTypeArgumentsInExpression` decides: a call, a tagged template, or a property access takes the type arguments; a follower that begins with `>`, the single-character `<`, `+`, and `-` keeps the comparison; and otherwise the type arguments are kept when the follower cannot start an expression, is a binary operator, including `=`, `in`, `instanceof`, `as`, and `satisfies`, or follows a line break, while `<=`, `<<`, `!`, and the arithmetic and shift operators instantiate or compare as the compiler decides them. A property access directly on an instantiation expression is a parse error, so `f<T>.x`, `f<T>?.x`, and `new f<T>.x` are rejected while `(f<T>).x`, `f<T>[x]`, and `f<T>(x)` stay valid, which is the rule the compiler reports as error 1477. An expression that starts with `<<` is no assertion or generic arrow function, because the compiler scans `<<` as one shift operator, while `< <T>() => T>value` with a space is an assertion. A heritage clause is not an expression, so its type arguments skip the comparison ambiguity: `class Box<T> extends Namespace.Base<T> implements Contract<T> {}` and `interface I extends First<T>, Second<U> {}` keep them before `{`, `implements`, and `,`.

The redeclaration early errors of section 4.9 are not checked in the TypeScript dialects. TypeScript declares function and method overloads, merges interfaces, namespaces, and enums, and allows ambient redeclaration, so the parser accepts `let repeated = 1; let repeated = 2;` and overload signatures with one implementation, while the JavaScript dialects reject the first. A genuinely conflicting duplicate is a checker diagnostic such as `TS2451`, not a grammar error, and the oracle's parser accepts every case of the comparison battery in section 5, so the parser records and checks no redeclaration in these dialects.

Speculation is restricted to type syntax and function heads, and bodies are parsed only after a head commits. Every consumed token in these dialects increments `ts_work`, which is bounded by the token limit, so a failed attempt cannot parse more than the limit allows, and a rollback restores the cursor, the line-break flag, the token count, the parser context, the `[~In]` flag, the template substitution depth, the conditional-type flag, the cover-grammar marks, and the lengths of the node, child, template-part, comment, bound-name, and expression-only-error lists and of the innermost class's private name references, so a retried reading neither duplicates nor loses a node. `src/parser/speculation.rs` derives the rollback and the record key below from one function that names every parser field in an exhaustive pattern, so a new field does not compile until it is classified (`D-047`): the fields that decide an outcome form the key and are restored; the position bookkeeping, cover marks, and list lengths are restored; the nesting depth, jump targets, declaration scopes, and module state are balanced by the constructs that change them, also on errors; the work counter is deliberately kept; and the lookahead caches hold pure results keyed by offset. Debug builds check at every rollback that the class and declaration scopes are balanced. That check found a namespace body that left its scope pushed and the module's export state replaced when it failed inside a function in a parameter default, which a speculation then discarded; the body now restores both on every path. No tree depended on it, because the other reading parsed the same text and failed again. The four speculations (an arrow function head, the lookahead for a function type, type arguments in an expression, and a constraint after `infer`) run at most once per position and parser state: the parser records each failure and each lookahead answer with the offset, the parser context, the `[~In]` flag, the template substitution depth, and the conditional-type flag, which together determine the outcome, and an arrow head also with its start and whether it is async. The compiler keeps a set of positions that are not arrow functions for the same reason. Without the record, nested constructs that each start a speculation were parsed once inside every failed or discarded reading and again in the next: a parenthesized expression whose content can start a binding pattern, as in `([(a)])`, because heads and the function-type lookahead parse patterns with the cover grammar, and type arguments that contain a parenthesized type, as in `f<([[f<([[a]])>]])>`, which the function-type lookahead parsed as a binding pattern including every nested `f<`. The work at least doubled per level, valid code with 15 levels reached the speculation limit, and a fuzzed 3 KB input took more than ten seconds in an instrumented build (section 7). Speculative work on such nesting now grows at most with the nesting depth times the size of the nested content, and the nesting bound limits the depth. The record lives only during one parse; on the generated TypeScript corpus, it raises the per-file heap peak from a median of 12.5 to 12.9 times the source size (maximum 18.1 to 18.8), while the whole-corpus peak stays at 12.4 times (`D-045`). The dialects are deterministic: the same source, dialect, goal, and limits produce the same tree, comments, errors, and spans.

Assignment targets follow the compiler's parser and checker together: a non-null expression wraps a simple target anywhere (`x! = y`), and `as`, `satisfies`, and angle-bracket assertions wrap one inside parentheses or as a destructuring element (`(x as T) = y`, `[x as T] = y`, `(x as T)++`), while `x as T = y` and `<T>x = y` are syntax errors because an assertion is no left-hand-side expression.

Two deliberate deviations from the pinned compiler remain. Frameshift enforces the ECMAScript early errors that make an invalid assignment, update, `for-in`, `for-of`, or destructuring target a parse error, and it applies that discipline to type syntax and to JavaScript syntax in TypeScript files alike: `f<T> = x`, `f<T> += x`, `++f<T>`, `[f<T>] = x`, `f() = 1`, `(f() as T) = y`, `this = 1`, and `a?.b = 1` are rejected at parse time, where the compiler's parser accepts most of them and its checker reports `TS2364`, `TS2365`, or `TS2356` later. Other ECMAScript early errors that the compiler leaves to its checker, such as a static member named `prototype`, are reported at parse time as well. Second, the compiler rejects a few comparisons whose right operand is an angle-bracket assertion of a tuple or object type, such as `x < <[string]>/re/g` and `x < (<[string]>/re/g)`: it first reads the `<` as type arguments of `x`, recovers from the resulting error, reaches a later `>` before a binary operator, and keeps that reading's error. Frameshift parses these inputs as the comparisons they are. The behavior depends on the compiler's error recovery and is not reproduced; such code did not occur in the real-world sample. Section 5 records how often these differences appear in the oracle comparisons.

## 6. E1 measurement harness

`tools/frameshift-bench` implements `D-040`. Measurements require optimized builds. Printing and contract checks work in debug and release builds:

```text
cargo run -p frameshift-bench --release --offline --locked
cargo run -p frameshift-bench --release --offline --locked -- --seed <n> --files <n> --iterations <n>
cargo run -p frameshift-bench --offline --locked -- --check [--seed <n>] [--files <n>]
cargo run -p frameshift-bench --offline --locked -- --print <index>
cargo run -p frameshift-bench --offline --locked -- --print-component <index>
cargo run -p frameshift-bench --offline --locked -- --print-typescript <index>
cargo run -p frameshift-bench --release --offline --locked -- --dir <path> [--iterations <n>]
```

`--print`, `--print-component`, and `--print-typescript` write one generated file of the mixed, component, or TypeScript corpus to standard output for review. `--dir` measures the files of a directory instead (below). The tool writes no files, starts no processes, and uses no network.

**Contract checks.** `--check` validates every file of all three generated corpora under its declared goal and dialect and default limits. It checks that the program and consumed spans cover all source bytes, every node is reachable exactly once, node and template spans slice the original UTF-8 text and nest in source order, no node other than the program and JSX text starts or ends with whitespace, a line terminator, or a comment, comments are ordered and match their delimiters, a fresh second parse yields identical nodes, child sequences, template parts, comments, and consumed span, and empty edits preserve every byte with complete source provenance. Traversal is iterative and linear in nodes and bytes. Failures stop at the first file and report its corpus, index, goal, dialect, and reason, with exit code 1. Success prints deterministic counts and the existing input fingerprints, without timings or heap measurements. This is an invariant check, not an oracle comparison, coverage-guided fuzzing, or migration verification. The tool still reads no files in generated mode and never executes generated source. `--check`, `--dir`, and the three print modes are mutually exclusive; conflicting modes are usage errors (exit code 2).

**Corpus.** `tools/frameshift-corpus` generates fictional JavaScript with SplitMix64 and integer arithmetic only, so a seed yields byte-identical files on every platform. Every declared name is unique within its file, and each construct appears only where its goal and function context permit it: imports, exports, and top-level await in modules; `require`, `module.exports`, `var`, hashbangs, and `"use strict"` in scripts; functions of every kind, classes with private names, static blocks, and `super`, destructuring, loops, labels, `switch`, `try`, templates, regular expressions, numeric and string literal forms, comments, CRLF line endings, and files without semicolons. Nesting is bounded, so a file exceeds its target size by at most one top-level item (about 1 KB on average). The default corpus has 1,000 files with target sizes piecewise log-uniform from 1 KiB to 32 KiB, about one in ten a script: 10,342,331 bytes, fingerprint `7c71c5e6160d3383` for generator version 1, pinned by a unit test. Before committing, 20,000 generated files (211 MB) were parsed without error, and V8 in Node.js 26.7.0 accepted all of 500 generated files with `node --check`.

**Component corpus.** `Corpus::components` generates JSX modules for the JSX dialect with the same seed, sizes, and generator, from a separately salted random sequence, so the mixed corpus keeps its bytes. About half of the top-level items are function components with destructured props that return multi-line JSX: intrinsic, component, member, and void elements, fragments, string, expression, arrow, spread, boolean, and style attributes, text with character references, expression and comment containers, `map` callbacks, and conditional elements; JSX also appears in other expressions. The default component corpus has 1,000 modules: 10,065,738 bytes, fingerprint `3b5b6cd23fac9fdb`, pinned by a unit test. Every generated component file must parse; before committing, `@babel/parser` 8.0.7 accepted 150 of them (1.4 MB) with identical JSX nodes and spans. The baseline and the throughput increment below measured the JavaScript and JSX corpora; the TypeScript corpus follows.

**Memory budget (`D-045`).** The 20x E1 gate applies to peak heap demand of the whole corpus with every source text and tree retained, not to each file. The harness reports its verdict on that peak; per-file ratios and the largest file peak remain diagnostics. The historical retained figures below do not record the whole-corpus peak separately. An all-empty corpus reports absolute heap and node counts without memory ratios, node density, a node-limit size estimate, or a memory verdict.

**Measurements.** `src/measure.rs` times `SourceText::new` plus `parse_js_program` in each file's dialect, and the parse alone, after one warm-up pass, and reports the minimum and median of the measured passes. Per-file memory is the source size plus the largest heap growth while building the source text and parsing, with the tree alive. A second pass keeps every source text and tree alive at once. A scaling series parses single modules from 1 KiB to 4 MiB with unbounded node and token counts. `src/alloc.rs` is the only unsafe code: a global allocator that forwards to the system allocator and counts requested bytes with relaxed atomics. It does not observe allocator overhead, fragmentation, or the old block of a moving reallocation, so figures are heap demand rather than resident memory.

## 7. Coverage-guided fuzzer

`tools/frameshift-fuzz` implements `D-044`. Fuzzing needs a coverage-instrumented release build in a separate target directory; replaying saved inputs works in any build:

```text
cargo build -p frameshift-fuzz --release --offline --locked --config tools/frameshift-fuzz/instrument.toml --target <host triple> --target-dir target/fuzz
target/fuzz/<host triple>/release/frameshift-fuzz targets
target/fuzz/<host triple>/release/frameshift-fuzz run --target <name> --dir <run directory> [--seconds <n>] [--executions <n>] [--seed <n>] [--max-len <n>] [--timeout <seconds>]
cargo run -p frameshift-fuzz --release --offline --locked -- replay --target <name> <file or directory>...
```

The run directory holds generated data only. A directory below the ignored `target/` or outside the repository keeps it out of commits. The tool writes nothing outside the run directory, starts no process other than its own worker, and uses no network. All inputs derive from fictional seeds.

Use the host triple from `rustc -vV` (for example `x86_64-pc-windows-msvc`). An explicit `--target` is required even for native fuzz builds: otherwise Cargo also instruments the engine's M1 host build script, which does not link the fuzz runtime and fails with unresolved coverage symbols. The explicit target keeps build scripts uninstrumented and target crates instrumented. This command correction was verified with the path fuzz increment (`D-054`).

**Instrumentation.** `instrument.toml` passes `-Cpasses=sancov-module` with `-sanitizer-coverage-level=3` and `-sanitizer-coverage-inline-8bit-counters` to the pinned stable rustc, so every basic block of every crate in the binary increments its own 8-bit counter. It also sets one code generation unit per crate, which the feasibility check showed to be required (`D-044`), and enables overflow checks and debug assertions, so silent arithmetic or invariant errors become findings. The standard library is precompiled and not instrumented. On Windows, `tools/frameshift-fuzz-sections` defines the section markers `__start___sancov_cntrs` and `__stop___sancov_cntrs` in `.SCOV$CA` and `.SCOV$CZ`, around the counters in `.SCOV$CM`; ELF and Mach-O linkers define such markers themselves. The instrumented build has about 25,000 counters. In an uninstrumented build or with `RUSTFLAGS` overriding the configuration, no counters are registered, and the worker refuses to run (exit code 2).

**Runtime and features.** Module constructors report the counter section before `main` through `__sanitizer_cov_8bit_counters_init`. `src/runtime.rs` keeps the first nonempty bounds, disables the counters if different bounds arrive, and offers two operations: clear every counter, and copy every counter into a buffer. Both are single `memset` and `memcpy` calls on the static section, from the only thread that runs instrumented code during fuzzing. `src/runtime.rs` and the marker crate are the only unsafe code of the tool. As in libFuzzer, a hit count falls into one of eight buckets (1, 2, 3, 4 to 7, 8 to 15, 16 to 31, 32 to 127, 128 or more), and each pair of counter and bucket is a feature. Merging compares words of eight counters through a bucket table. Counters wrap at 256, which can hide a bucket and weakens only the guidance.

**Worker.** The worker runs on one thread with a 64 MiB stack, far beyond what the parser's nesting bound needs, so a stack overflow points to unbounded recursion. It first executes the target's seeds and the inputs saved in `<run directory>/<target>/corpus/` in file name order, then repeatedly picks two corpus inputs, mutates one, and executes the result until its budget of wall-clock seconds or executions ends. Each execution writes the input to `<target>/current`, clears the counters, runs the target, and copies the counters, so only the code that the input reaches contributes features. An input with a new feature joins the corpus and is saved under its 64-bit FNV-1a fingerprint. The worker prints a status line about once a second and writes the slowest input to `<target>/slowest` at the end. With `--executions`, the same seed, binary, and saved inputs reproduce a run exactly.

**Mutator.** One to eight operations per input: bit flips, random or syntax-byte replacements, insertions of syntax bytes, deletions and duplications of ranges up to 64 bytes, insertions or replacements with a token from the target's dictionary, up to 300 copies of a token for deep nesting, insertions of scalars with lexical roles (no-break space, line and paragraph separators, byte order mark, joiners, identifier and astral characters), and ranges spliced from a second corpus input. Inputs are limited to the target's maximum length and may be malformed or not UTF-8.

**Supervisor.** `run` starts the executable again as a worker process and forwards its status lines, which serve as heartbeats. The run ends with exit code 0 when the budget completes, 1 with a finding, and 2 for usage or environment errors. A worker that reports a violated contract exits with code 1; a panic exits with code 101, and a stack overflow, an abort, or exhausted memory end the process abnormally; a worker without a heartbeat for the timeout (default 10 seconds) is stopped. In each case, the supervisor reads the recorded input and saves it as `<target>/findings/<violation, crash, or hang>-<fingerprint>`, with a description that names the cause, the worker seed, and the replay command. `replay` runs files, or the files of directories in name order, catches panics per input, and reports each outcome.

**Targets.** Every target uses the engine facade with default limits and documented smaller limits where needed. Text parsers reject non-UTF-8 through `SourceText` with the exact `InvalidUtf8` position. The path target checks arbitrary bytes, catalog/unit parsing requires UTF-8, the hash target hashes arbitrary binary input while parsing digests only from valid UTF-8, the collections target interprets arbitrary bytes as keys, slot operations, and charges, the gitignore target reads arbitrary bytes as a `.gitignore` file followed by paths, the json target parses valid UTF-8 as both JSON dialects, the semver target reads valid UTF-8 and each of its lines as ranges, versions, specifiers, and `packageManager` values, and the package target interprets valid UTF-8 that parses as JSON or JSONC as a manifest and as lockfiles.

## 8. E1 maintainability review

**Status: accepted by the project owner on 2026-10-13 (`D-047`), with the follow-up work at the end of this section.** The agent drafted the review at the project owner's request (`D-044`). Section 2.8 of [ENGINEERING.md](ENGINEERING.md) requires a documented review that concludes whether the arena, visitor, and pattern-matching design is maintainable and extensible to further languages. The review assesses the code at commit `c42b749` and the history of the JSX, TypeScript, and declaration-file increments, and separates observed facts from judgment.

**Arena (facts).** A `SyntaxTree` holds a flat vector of `SyntaxNode` values, each a closed `SyntaxNodeKind` and a byte span, at most 40 bytes by a compile-time assertion. `NodeId` is a non-zero 32-bit index, so `Option<NodeId>` stays four bytes. Lists of children are ranges of one shared child vector, and template parts use a second one. Trees store spans rather than token text, and comments are a separate ordered list. The parser builds the arena in source order, reinterprets cover-grammar nodes in place, and rolls back speculation by truncating the vectors. Retained trees take 9.7 to 12.4 times the source size on the generated corpora and 8.7 times on the real-world sample (section 6).

**Arena (assessment).** The layout is simple, compact, and deterministic: there are no pointers, no reference counting, and no lifetimes beyond the borrowed source, and node identity is stable within a tree. Truncation-based rollback is cheap and has been exercised by every TypeScript speculation. The cost is that nodes cannot be removed or reordered after the fact, so later rewriting must stay in the edit layer (`P-003`), which matches the planned architecture.

**Traversal (facts).** `SyntaxTree::child_nodes` is the single traversal primitive: one exhaustive match over all 101 `SyntaxNodeKind` variants, about 270 lines, returning a non-allocating iterator of direct children in source order. Every consumer in the repository (the contract tests, `tools/frameshift-corpus`, the measurement harness, and the fuzzer) traverses through it. There is no visitor trait. TypeScript productions use one generic variant, `SyntaxNodeKind::TypeScript { kind, children }`, with 60 `TypeScriptKind` values whose children are an ordered list.

**Traversal (assessment).** One traversal function suffices for the invariant checks and keeps every new kind visible in one place. Two limits will matter for the semantic layer (M4): consumers of TypeScript nodes must know the position of each child by kind, which the type system does not express, and there are no typed accessors such as "the parameters of this function". A visitor or typed accessors should be added when M4 needs them, not earlier.

**Pattern matching (facts).** Product crates deny Clippy's `wildcard_enum_match_arm`, and every match over `SyntaxNodeKind`, `TypeScriptKind`, `ParseErrorKind`, and the token kinds lists all variants. The parser uses `matches!` 88 times for fail-closed membership tests (section 7.3 of [ENGINEERING.md](ENGINEERING.md)). Twenty match arms in the library crates use `_`: most match characters, bytes, or strings, but four classify an `Option<ReservedWord>` or `Option<Punctuator>` as one of a few unary or binary operators, array delimiters, or `super` forms and otherwise fall back to another grammar path. Each fallback ends in a typed rejection for a token it does not know, but Clippy's lint does not inspect wildcards inside `Option` patterns, so this property rests on review.

**Pattern matching (assessment).** Exhaustive matches made each extension mechanical: the compiler listed every place that a new kind affected. The four `Option` wildcards are a small gap in that guarantee and should become explicit membership tests or carry a comment that explains why the fallback fails closed.

**Extension evidence (facts).** The JSX increment (`91fb5a9`) added 15 node kinds, a scanner module of 142 lines, and a parser module of 358 lines; existing parser modules changed by 9 to 58 lines each, and 663 of its 1,566 inserted lines are tests. The TypeScript increment (`e44a376`) added 60 production kinds behind one new variant, so `ast.rs` changed by 10 lines; the grammar lives in its own module of 1,804 lines, and existing parser modules changed by 8 to 86 lines each. The declaration-file dialect (`9dd3be7`) changed 26 lines of the parser. The two speculation fixes of section 4.15 changed only `parser/mod.rs` and `parser/typescript.rs`. Fuzzing ran about 7.6 million program and expression executions with the tree contracts of section 7 and found no arena or traversal defect.

**Further languages (assessment).** Nothing in the arena is generic yet: the node, kind, and tree types live in `frameshift-syntax` and name JavaScript constructs. The pattern itself (compact nodes with spans in a flat arena, shared child ranges, a closed kind enum, one exhaustive traversal function, and parser state that exists only during one parse) carries over to the planned CSS, JSONC, YAML 1.2, and Astro template parsers. Following architecture driver 7 of [ARCHITECTURE.md](ARCHITECTURE.md), shared arena primitives should be extracted when the second parser needs them. This conclusion is a judgment about the design, not a demonstration by a second implementation.

**Risks found.**

1. *Speculation state in the TypeScript dialects.* `ts_try` saves and restores ten pieces of parser state in addition to its checkpoint of five, and the speculation record keys on five pieces of state. A new parser field must be classified for both, and nothing enforces it. Both exponential defects that fuzzing exposed came from this area. Recommendation: gather the state that speculation saves and that determines its outcome into one structure, so that rollback and the record key derive from one definition, and keep fuzzing the TypeScript dialects.
2. *Module size.* `parser/expression.rs` (2,028 lines) and `parser/typescript.rs` (2,010 lines) are the largest hand-written modules, and `Parser` has 33 fields. Recommendation: split the TypeScript grammar into types, declarations, and expression extensions when it next grows.
3. *Positional TypeScript children.* See the traversal assessment. Recommendation: typed accessors when M4 consumes types.
4. *Error recovery (`D-034`).* The arena can hold partial trees, but recovery has to coexist with truncation-based rollback; this is M3 design work.
5. *Throughput headroom.* The TypeScript dialects parse at about 70 percent of the speed of JavaScript, and measurements on a reference-class laptop were inconclusive (section 6).

**Conclusion.** The arena, traversal, and pattern-matching design is maintainable: it absorbed JSX, TypeScript, TSX, and declaration files with local changes, and the compiler enforced exhaustiveness at every step. Its weakest part is the speculation state of the TypeScript grammar (risk 1). Extensibility to further languages holds at the level of the design. The project owner accepted the review, so the maintainability criterion of E1 is met.

**Follow-up (2026-10-13, `D-047`).** Risk 1: `src/parser/speculation.rs` now holds the speculation record and rollback. One function names every parser field in an exhaustive pattern without `..`, so a new field does not compile until it is classified, and the record key and the rollback both derive from its result (section 4.15). Its balance checks in debug builds found the namespace body defect described there. The `Option` wildcards: the unary and binary keyword operators, the `super` forms, and the array delimiters are now membership tests whose fallbacks fail closed, with comments that name the rejection, so no wildcard arm over an `Option` of a closed enum remains in the library crates. A development-time comparison of 634,380 parse outcomes before and after both changes found no changed tree or error: three generated corpora of 1,000 files each (seed 1), 26,000 mutations of generated JSX and TypeScript files, and the 13,292 files of the real-world sample, each parsed in all five dialects as a script, a module, and an expression, in a release build with debug assertions. Moving the speculation code shrank `parser/typescript.rs` to 1,896 lines. Risks 2 and 3 remain follow-ups for when the TypeScript grammar next grows and when M4 consumes types; risk 4 is M3 work, and risk 5 is checked on reference hardware in M11 (`D-047`).

## 9. Processor-time helper

`tools/frameshift-cputime` implements `D-046`. It is a Go module outside the Cargo workspace, built and tested with the toolchain that its `go.mod` pins (Go 1.25.5); `gofmt -l` must print nothing:

```text
go -C tools/frameshift-cputime build -trimpath -o ../../target/cputime/ .
go -C tools/frameshift-cputime test ./...
go -C tools/frameshift-cputime vet ./...
gofmt -l tools/frameshift-cputime
target/cputime/frameshift-cputime [--interval <seconds>] [--log <file>] -- <program> [<argument>...]
```

**Behavior.** The helper starts the program with inherited standard input, output, and error. It ignores interrupts itself, so the program decides how to end and the helper measures until it has. Every interval (default 5 seconds) and once more after the program ends, it adopts the program's new descendants from the operating system's process table and reads the user and kernel time of every tracked process. A row whose start time precedes its parent's belongs to an older process with a reused ID and is not adopted. With `--log`, it writes JSON Lines to a new file and refuses an existing one: a `header` record (format `frameshift-cputime`, version 1, platform, interval, and command), one `sample` record per process and sample, and an `end` record with the exit code, whether every sample succeeded, the program's own times from its exit status, and the last values of every process. The summary on standard error lists each process with its processor time and whether the value is final. The exit code is the program's, 128 plus the signal number for a program that a signal ended, or 125 when the helper cannot start or measure the program or a sample failed.

**Platforms.** On Windows, the helper reads the Toolhelp process snapshot and keeps a handle with `PROCESS_QUERY_LIMITED_INFORMATION` and `SYNCHRONIZE` access to every tracked process. The handle keeps the process object alive, so the times of an ended process stay readable and final, and its ID is not reused during the run. On Linux on amd64 and arm64, it reads `/proc/<pid>/stat` in units of `USER_HZ`, which is 100 there. An ended process disappears from `/proc` once its parent has waited for it, so its last sampled value is a lower bound by at most one interval. Other platforms, including macOS, refuse with exit code 125. On both supported platforms, a process that starts and ends within one interval is missed.

**Tests.** Seven tests cover argument parsing, the log and summary layout, the parser of `/proc` stat lines (including names with spaces and parentheses), the adoption of descendants and the rejection of reused IDs, the refusal to overwrite a log, and an end-to-end measurement in which the test binary runs as the measured program, starts a busy child, and exits with code 3. ## 10. Astro printer and JSX conversion

`crates/frameshift-emit` turns converted structure into new files (`D-048`). It performs no I/O and selects no rules; the caller decides what to convert and classifies the recorded assumptions.

**Emitted text and provenance.** `SourceId` names one source file by the caller's deterministic index, and an `Anchor` is a span in one source. `OutputBuilder` appends copied source spans and generated text, each with an anchor, under explicit `EmitLimits` (64 MiB of output and a nesting depth of 256 by default); adjacent copies of contiguous source and generated pieces with the same anchor share one region. The resulting `EmittedText` partitions its bytes into regions that are `Copied` (exact source bytes) or `Generated` (text produced for the anchored construct, with no claim of equivalence). `EmittedText::from_rewritten` converts the output of `apply_edits` (section 3), and `verify` checks the contract against the sources: contiguous nonempty regions that cover the text, valid anchors, and copied regions equal to their source bytes.

**Astro component model.** An `AstroComponent` has frontmatter items and template nodes. Frontmatter items are generated imports (default, named, or side-effect, with the specifier printed as an escaped single-quoted string), copied source spans, a generated `interface Props` with `string` members, and a generated `const { ... } = Astro.props;`. Template nodes are elements with an HTML tag or a component name, fragments, text, expressions, and slots. Attributes are valueless, quoted text, an expression, or a spread. Expressions consist of copied source pieces, nested markup, and generated identifiers or `true`. Every name in the model is a validated type: `JsIdentifier` (no escapes, no reserved, strict-mode reserved, `await`, `eval`, or `arguments`), `HtmlTagName` (lowercase ASCII letters and digits with single hyphens), `ComponentName` (an uppercase identifier or a dotted path), and `AttributeName`, so a name can never inject syntax.

**Printer.** `print_astro_component` takes explicit `PrintOptions` (an indentation of 1 to 16 spaces or a tab, and LF or CRLF), so callers pass the project's dominant style. The frontmatter is fenced by `---` and omitted when empty; a blank line separates its imports from the other items, and copied frontmatter that contains a line starting with `---` is rejected, because it would end the frontmatter. Children are placed on separate indented lines only when none of them is text and the element is not `pre`, `textarea`, `listing`, `title`, `script`, or `style`; otherwise, and inside expressions, they are printed inline, so the printer never adds whitespace next to text. Text escapes `&`, `<`, `>`, `{`, `}`, tab, CR, LF, and U+00A0 as references, attribute text escapes `&`, `"`, tab, CR, and LF, and U+0000 is rejected. Void elements print as `<br />` and reject children, empty non-void elements print as `<div></div>`, and components without children print self-closed. The file ends with a line ending.

These rules rest on the behavior of the Astro 7.3.8 compiler, observed on fictional probe pages with the `astro7-preact10` profile: whitespace that contains a line break between markup nodes is dropped as in JSX, but `pre` content is preserved; text without line breaks, character references, and quoted attribute values pass through to HTML unchanged, including `{` and `}` inside quotes; and expressions are rendered with HTML escaping.

**JSX conversion.** `convert_jsx` converts a JSX element or fragment, optionally parenthesized, into template nodes and returns them with the recorded assumptions and the copied spans. It follows React's semantics for the subset of section 9.3 of [MIGRATION_SPEC.md](MIGRATION_SPEC.md):

- Names that start with a lowercase ASCII letter are HTML elements; every other name, including member expressions, goes to the caller's `ElementResolver`, which returns a component, optionally hydrated with `client:load`, or an HTML element that stands for the component (for example `a` for `next/link`). Unresolved components, namespaced names, HTML names with uppercase letters, `svg` and `math` content, children of `script`, `style`, `textarea`, `title`, and `noscript`, and children of void elements fail.
- Text follows Babel's `cleanJSXElementLiteralChild`: lines are split at CR, LF, and CRLF, spaces and tabs are trimmed at inner line edges, empty lines are dropped, and lines are joined with a space. The 253 XHTML references are decoded (`decode_jsx_character_reference`), and the printer re-escapes the value for HTML, so a legacy spelling such as `&copy` stays literal as in React. A tab inside a line, a line or paragraph separator, a control character, a reference to a surrogate, and a reference that decodes to whitespace fail, because the JSX compilers treat them differently.
- On HTML elements, `className`, `htmlFor`, `acceptCharset`, and `httpEquiv` are renamed, 30 further camelCase props with a known HTML name are lowercased, lowercase names including `data-*` and `aria-*` pass unchanged, `key` and the `suppress...Warning` props are removed, and every other name fails, including event handlers, `ref`, `children`, and uncontrolled defaults. A valueless attribute stays valueless for the 24 HTML boolean attributes, becomes `"true"` for `data-*` and `aria-*`, and fails otherwise. Attribute strings are decoded like text and fail if they contain a line break, which compilers normalize differently. `dangerouslySetInnerHTML={{ __html: value }}` becomes `set:html={value}` and fails with children or any other value shape. `style` is copied only as an object literal with non-computed keys, non-empty string values, and keys whose CSS names React and Astro derive alike (no `ms` prefix), because React adds `px` to numbers and Astro does not.
- On components, props keep their names, `key` is removed, `ref` and `children` fail, a valueless prop becomes `name={true}`, and markup as a prop value fails (named slots come later). Children of components become their default slot.
- An expression container is copied verbatim between its braces, with the outermost JSX inside it converted in place, so comments in it are kept; an empty container is kept only when it holds a comment. A child expression that is exactly the caller's children binding becomes `<slot />`; any other use or rebinding of that name fails. Spread children fail.
- Every comment inside the converted range must lie in a copied span; a comment in a tag, for example between attributes, fails rather than being dropped.
- Where the result depends on runtime values, the conversion records an `Assumption`: a child expression that could evaluate to `true` (React renders nothing, Astro the text `true`), unless it is a literal, markup, a conditional or `&&` of such, arithmetic, or `map` with an arrow returning such; a non-literal attribute expression on an HTML element (booleans, arrays, and objects serialize differently); a spread on an HTML element; a non-literal prop or a spread of a hydrated component (Astro must serialize it); and a removed `key` expression with possible side effects.

Errors are a closed `ConvertErrorKind` with an anchor and a stable identifier; no partial markup is returned. Walks over expression trees (finding nested markup, checking the children binding, deciding child safety, and removed `key` expressions) use explicit stacks or loops, because the parser builds member, call, and binary chains without nesting, so their depth is bounded only by the node limit. Only markup nesting recurses, up to `max_depth`: in an optimized build, converting and printing 250 nested elements fit in 384 KiB of stack, comparable to the parser (section 4.12).

**Tests.** `tests/astro.rs` checks long member chains on a small stack, exact printed output for HTML attribute rules, text whitespace and references, components, links, islands, and slots, nested markup in expressions, styles, the assumptions, frontmatter printing with tab and CRLF options, generated expression pieces, and 23 fail-closed conversions, and verifies the provenance of every printed result.

### 11.1 Maintainability review of the E2 code

E2's criteria do not require a review, but the printer crate is product code that M7 builds on, so the agent reviewed it after the experiment, on 2026-10-14, at the project owner's request. Facts and judgment are separated as in section 8.

**Facts.** `frameshift-emit` has 2,928 lines in five modules and `lib.rs`: `jsx.rs` (1,357, of which about 60 are tests), `astro.rs` (662), `output.rs` (446), `html.rs` (231), and `names.rs` (204). The model is plain data with validated names, the printer is one recursive function per node kind, and the conversion is one struct with one method per JSX construct. The E2 driver's `migrate.rs` has 1,843 lines; it is hand-wired experiment code that rules replace in M7. Every match over `SyntaxNodeKind` in both is an exhaustive list, an `if let` chain, or a `matches!` membership test whose fallback rejects, as section 7.3 of [ENGINEERING.md](ENGINEERING.md) allows; no wildcard arm over a closed enum exists. The review found one class of defect: the walks over expression trees recursed once per syntax level, and the parser's nesting limit does not bound tree depth, because member, call, and binary chains are built in loops (section 4.12). A removed `key={a.b.c...}` with 20,000 members overflowed the stack, and a child expression of that length overflowed it at 256 KiB in an optimized build. The walks now use explicit stacks or loops, a regression test converts both cases on a 256 KiB thread in a debug build, and only markup nesting still recurses, bounded by `max_depth`. A new fuzz target, `astro`, converts and prints every JSX element of JSX and TSX modules with a resolver that accepts every component, and checks determinism, anchors, and provenance (section 7). Its first run on the development desktop, 900 seconds of wall-clock time on the final commit, executed 10,047,977 inputs and reached 40,370 features without a finding. Its worker's 64 MiB stack and 4,096-byte inputs cannot expose the recursion defect above, which the regression test covers. The run is a smoke run, not a budget run of one CPU-hour.

**Assessment.** The structure is maintainable and fits the planned layers: the target-independent emitted text is separate from the Astro model, the model from its printer, and React semantics from Astro syntax, so a React-islands target (M18) and the JSON and configuration printers can reuse `output.rs`, and a further source with JSX reuses `jsx.rs`. Three costs will grow with M4 to M7 and deserve attention, none of which requires an architectural change:

1. *Repeated accessors.* The conversion, the E2 driver, and several test files each wrap `SyntaxTree::node`, `children`, and slicing in their own helpers that turn `None` into an error. Typed, fallible accessors on the tree, together with the typed TypeScript children of risk 3 in section 8, should be added before M4 adds the semantic layer's consumers.
2. *Traversal depth.* Every consumer of a syntax tree must traverse iteratively; recursion is safe only over constructs whose depth the parser bounds. This is now a rule in section 4.2 of [ENGINEERING.md](ENGINEERING.md).
3. *Facade size.* The engine facade originally re-exported 132 names flat. The M1 follow-up of 2026-10-14 exposes the `foundation`, `syntax`, `transform`, and `emit` namespaces. Existing M0 root imports remain available, so development tools do not need a simultaneous migration.

**Conclusion.** No fundamental change of the architecture is needed; development can continue on the accepted designs of `P-002` and `P-003`. The three items above are scheduled follow-ups, not blockers.

## 14. Canonical source and portable output paths

Implemented under `D-053` and `D-054` in `crates/frameshift-core/src/path.rs`, available through `frameshift_engine::foundation`. The owner confirmed strict validation and PR integration after green CI through the Codex App question interface. The existing branch protection remains in force.

**Values and grammar.** `SourcePath` owns a nonempty UTF-8 string relative to the project root. `/` separates nonempty components. A leading slash, an initial ASCII letter followed by `:`, backslashes anywhere, NUL, and components exactly `.` or `..` fail with typed `PathError` values. Nothing is normalized, collapsed, decoded as a URL, case-folded, or repaired. An empty path does not represent the root. Names such as `CON.ts`, `trailing.`, names with colons or control characters, and long components remain source evidence. Input outside this grammar, including a literal POSIX backslash name or native non-UTF-8 name, must be accounted for explicitly by future discovery; these types do not silently omit it.

**Portable output names.** `OutputPath` requires the source grammar and rejects, in every component:

- Unicode controls (C0, DEL, and C1), Windows-reserved punctuation `< > : " | ? *`, and trailing ASCII spaces or dots;
- ASCII case variants of `CON`, `PRN`, `AUX`, `NUL`, `COM1` through `COM9`, `LPT1` through `LPT9`, and the corresponding superscript digits 1, 2, and 3, plus the console aliases `CONIN$` and `CONOUT$`;
- those device stems with extensions, conservatively including spaces before the first extension;
- components over 255 UTF-8 bytes, which also bounds their UTF-16 length to 255 units. This deliberately rejects some Unicode names that NTFS alone permits.

The Windows rules were checked against Microsoft's [file naming documentation](https://learn.microsoft.com/en-us/windows/win32/fileio/naming-a-file) and [console handle documentation](https://learn.microsoft.com/en-us/windows/console/console-handles) on 2026-10-14. Source spelling is preserved even after strengthening into an output path. `TryFrom<SourcePath>` validates names without reallocating; `as_source` and `into_source` expose the weaker view without a copy. The existing source value's construction limits remain in effect during conversion.

**Limits, errors, and costs.** `PathLimits` defaults to 32 KiB including separators and 256 components, both inclusive and explicitly replaceable by the caller. Byte size is checked before UTF-8 decoding (`from_bytes`) and structural checks. Within each component, count limits precede syntax checks. Output checks follow successful validation of the entire source structure; within each output component the size bound precedes characters, ending, and device name checks. Errors contain only numeric offsets/counts and fixed explanations, never input content. Validation is iterative, linear in the input, and allocates no storage. Successful constructors reserve storage fallibly and copy once. Derived cloning follows standard Rust allocation behavior. ## 19. Exact-byte SHA-256 facade

Implemented under `D-059` in `crates/frameshift-core/src/hash.rs`, available through `frameshift_engine::foundation`. The private dependency is approved in `D-058` and section 18. Workspace code adds no unsafe operations and no runtime filesystem, network, environment, clock or process access. Hashing may use the dependency's CPU feature detection and optimized backend; outputs follow the same SHA-256 algorithm.

**Values and spelling.** `Sha256Digest` stores exactly 32 bytes, with Copy, equality, hashing and total ordering over those bytes. `from_bytes` constructs a digest from raw digest bytes without rehashing; `as_bytes` borrows them. Display and Debug produce exactly `sha256:` followed by 64 lowercase hex digits, matching the existing report example. LowerHex produces only the digits. `FromStr` accepts exactly that canonical spelling: first require 71 UTF-8 bytes, then the exact prefix, then lowercase hexadecimal digits in byte order. Whitespace, uppercase digits, alternate algorithms and non-ASCII lookalikes are never repaired. Parsing uses fixed storage, and formatting writes directly to the caller's sink, which may allocate its own output storage. Error values contain fixed categories and numeric limits/offsets, never source text.

**Hashing and limits.** `Sha256Digest::hash(input, limits)` hashes all bytes exactly. BOMs, CRLF versus LF, Unicode normalization forms, NUL and non-UTF-8 bytes are meaningful input. `Sha256Hasher::new(limits)`, `update`, `bytes_hashed`, and consuming `finish` provide streaming with fixed storage. Clone forks the accepted prefix without shared mutable state. Chunk boundaries carry no meaning. `HashLimits::max_bytes` counts cumulative bytes as u64, defaults to 2^61 - 1 (SHA-256's maximum complete-byte message), and is capped at that algorithm ceiling when the configured limit is larger. Zero permits only empty input. Limits are inclusive; every failed update leaves the accepted byte count and digest state unchanged. This prevents both successful truncation and the upstream bit-length arithmetic from overflowing. Callers set smaller subsystem limits before reading or accumulating untrusted data; this primitive does not bound I/O or whole-run memory.

**Scope and future formats.** This API supplies a digest, not authentication, a signature, a snapshot store or a plan document format. A source or output file digest can cover its exact bytes. Future structured hash formats must specify domain/version tags, explicit field lengths and sorted records to distinguish different field sequences. The streaming operation intentionally gives the same result for `a` then `bc` and `ab` then `c`. No ad hoc snapshot or plan framing is introduced in M1.

## 20. Deterministic collections and lookup-only hash tables

Implemented under the owner-confirmed `D-060` in `crates/frameshift-core/src/collection.rs`, exposed through `frameshift_engine::foundation`, and in `crates/frameshift-syntax/src/lookup.rs`, without dependencies or runtime I/O.

- `KeyTable::new(keys, max_entries)` takes keys in any order. It checks the caller's inclusive count bound first, sorts in place by the key's total order with O(n log n) comparisons and no allocation, and rejects keys that compare equal with `DuplicateKey` at the sorted position of the second key. Equal keys are never merged. `find` uses a binary search; `get`, `iter`, and `as_slice` follow sorted order.
- `DenseId<K>` is the zero-based sorted position, typed by the key. It is `Copy`, ordered, and hashable for every key type, because its trait implementations do not require them of the key. Identities are local to one table and are not persistent document keys; an identity of another table with the same key type is detected only when it is out of range.
- `KeyTable::slots` reserves one empty slot per key fallibly. `DenseSlots::insert` accepts exactly one result per identity; an out-of-range identity (`UnknownId`) or an occupied slot (`OccupiedSlot`) leaves every slot unchanged and drops the rejected value. `finish` reports the first empty slot in identity order (`MissingResult`) before reserving storage, then returns a `DenseMap` with one result per identity in identity order. Results therefore do not depend on insertion or worker completion order.
- `CollectionError` carries positions and counts only, never keys.

## 21. Run limits, budgets, and the reconciled limit set

Implemented under the owner-confirmed `D-061`, amended by `D-064` and `D-065`. `crates/frameshift-core/src/limit.rs` defines `RunLimits`, `Budget`, and `BudgetExceeded`; `crates/frameshift-engine/src/limits.rs` defines `Limits`, `LimitEntry`, and `LimitsError`. No runtime I/O, environment variable, or project file changes any limit.

**Run limits.** `RunLimits` holds the inclusive input bounds that discovery applies in canonical path order (section 22), within which the snapshot store reads (section 24):

| Limit | Default | Meaning |
| --- | --- | --- |
| `max_files` | 100,000 | admitted source files |
| `max_file_bytes` | 64 MiB | bytes of one admitted file |
| `max_total_bytes` | 1 GiB | cumulative bytes of all admitted files |
| `max_directory_depth` | 255 | depth of a traversed directory; the root has depth 0 and `a/b` depth 2 |
| `max_entries` | 1,000,000 | directory entries that discovery reads, including directories, links, and ignored names (`D-064`) |

Text decoding keeps its separate 16 MiB default, so a text file between 16 and 64 MiB is admitted and then becomes an `unknown` unit with a finding. Input beyond any limit must become a finding, never silent truncation.

**Budgets.** `Budget::new(limit)` starts an inclusive cumulative counter. `charge(amount)` succeeds when the total stays within the bound; a zero charge always succeeds; a failed charge, including one whose sum would overflow `u64`, changes nothing and returns `BudgetExceeded` with the bound only. `used`, `limit`, and `remaining` report the state. A budget has one owner, who charges in canonical order: the same sizes in another order can reject a different input.

**Limit set.** `Limits` holds the run, ignore (section 23), text, path, identifier, finding, hash, parse (including lexical), JSON (section 25), YAML (section 27), package (section 26), edit, and emit limit types; its default is their defaults, `discovery()` returns the run, path, and ignore limits that discovery applies, and `snapshot()` adds the hash limits for the snapshot store (section 24). `entries()` returns all 33 configured values as `u64`, sorted by byte-wise name, with dotted lowercase names in the catalog name grammar of section 15, from `edit.max-edits` to `yaml.max-nodes`, including `ignore.max-match-work`, `ignore.max-total-bytes`, `json.max-depth`, `json.max-nodes`, `package.max-lockfile-bytes`, and `run.max-entries`. `package()` returns the text, JSON, YAML, path, and package limits that loading a package directory applies (section 26). It destructures every limit type exhaustively, so a new field fails to compile until it is listed. `validate()` checks six relations in a fixed order and reports the first violation:

1. `FileExceedsTotal`: `run.max-file-bytes` must not exceed `run.max-total-bytes`.
2. `DepthExceedsPathComponents`: `run.max-directory-depth` must be below `path.max-components`, so every file in a traversed directory has a representable component count.
3. `FileExceedsHash`: `run.max-file-bytes` must not exceed `HashLimits::effective_max_bytes`, the configured hash bound capped at 2^61 - 1.
4. `PathExceedsUnitId`: `identifier.max-bytes` must hold `UnitId::max_file_id_bytes(path.max-path-bytes)`, the longest file kind, the colon, and three bytes per path byte, which a non-ASCII path attains.
5. `TextExceedsEditOutput`: `text.max-source-bytes` must not exceed `edit.max-output-bytes`, so an empty edit set reproduces every accepted source.
6. `FilesExceedEntries`: `run.max-files` must not exceed `run.max-entries`, because every admitted file is a read entry (`D-064`).

The defaults satisfy all six relations. Other limits are independent, and exceeding them yields findings. The per-call depth of `JsxConversion` is not part of the set. Which limits become user options is decided with the configuration key set (M6); recording `entries()` in plan and report documents belongs to the reporting layer.

## 22. Read-only discovery walker

Implemented under the owner-confirmed `D-064` in `crates/frameshift-input` (`src/walk.rs`, `src/native.rs`, `src/inventory.rs`), exposed through `frameshift_engine::input`. It is the first product code that touches the source filesystem. No dependency is added; native access uses `std::fs` only. Content reading and hashing belong to the snapshot store (section 24); framework detection and the `inspect` command remain planned M2 work.

**Entry point.** `discover(root, limits, findings)` takes a native root path, `DiscoveryLimits` (run, path, and ignore limits; `Limits::discovery()` supplies them from the engine set), and the run's `FindingCollector`, and returns an `Inventory` or a `DiscoveryError`. The root is canonicalized, on Windows into a verbatim `\\?\` path so that names with trailing dots or spaces and device names such as `CON.ts` are not reinterpreted, and must be a directory. Links in the root path itself are resolved; no link below it is followed.

**Order.** For each directory, the walker lists every entry, charging `run.max-entries` per entry read; checks that the directory is still a real directory (on Unix with the device and inode recorded when it was listed); builds each child's `SourcePath`; reads the directory's `.gitignore` file (section 23); and then visits the children sorted by name bytes, with `/` appended to the names of real directories, depth first with an explicit stack. All children of a directory share its path prefix, and a traversed directory's descendants all start with its name and `/`, so this visits every descendant in byte-wise `SourcePath` order: `a.txt` precedes `a/x.txt`, and `b/c.d` precedes `b/c/d.txt`. The walker checks that admitted paths strictly increase and fails with `DiscoveryError::Internal` otherwise. Enumeration order of the operating system never affects results; unit tests feed listings in 64 shuffled orders.

**Classification.** Each child, in that order, is checked against the built-in ignores, then against the `.gitignore` levels, then by kind:

| Entry | Inventory | Finding |
| --- | --- | --- |
| Built-in ignored name | `Ignored` with `vcs`, `dependencies`, `build-output`, or `environment`; never opened or traversed | none |
| Matched by `.gitignore` | `Ignored` with `gitignore`; never traversed | none |
| Real directory within `run.max-directory-depth` | `Directory`, traversed | none |
| Real directory deeper than the limit | `NotTraversed(DepthLimit)`; incomplete | FS1009, unknown |
| Regular file within the limits | admitted | none |
| Regular file over `run.max-file-bytes` | `Oversized` with its size; accounted, not admitted | FS1004, unknown |
| File beyond `run.max-files` or `run.max-total-bytes` | discovery stops | FS1011 or FS1012, unknown |
| Symbolic link or junction | `Link` with its resolved target | FS1005 info, FS1003 unknown, FS1006 unknown, or FS1007 info |
| Other Windows reparse point | `ReparsePoint`; never opened | FS1008, unknown |
| Device file, FIFO, or socket | `Special`; never opened | FS1002, info |
| Metadata unreadable | `Uninspectable`; incomplete | FS1017, error |
| Directory unreadable | `NotTraversed(Unreadable)`; incomplete | FS1016, error |
| `.gitignore` unreadable | its directory `NotTraversed(IgnoreFileUnreadable)`; incomplete | FS1018, error |
| Name or path not representable | counted only; a directory makes the inventory incomplete | FS1001 at the parent, unknown |

**Built-in ignores.** Names are compared ASCII-case-insensitively at every depth: `.git` (directory or file), `.hg`, and `.svn` (`vcs`); `node_modules` (`dependencies`); `.next` (`build-output`); and `.env` or any name starting with `.env.` (`environment`), except names whose last dot-separated segment is `example`, `sample`, or `template`, such as `.env.example`, `.env.local.sample`, or `.Env.TEMPLATE`. `.envrc` and `.environment` are ordinary files. A `.gitignore` pattern cannot re-include a built-in name. The configured static export directory is not ignored yet, because configuration is not evaluated.

**Links.** On Unix, a link is an entry whose `lstat` type is a symbolic link. On Windows, every entry with `FILE_ATTRIBUTE_REPARSE_POINT` counts as a link: name surrogates (symbolic links and junctions) are `Link`, all others (for example cloud placeholders) are `ReparsePoint`. Listing metadata never follows a link. For a `Link`, `read_link` reads the stored target, and resolution is lexical: starting from the link's directory, `..` pops a component and fails as `Escapes` above the root, and every directory that resolution passes through or pops must be a traversed real directory of the inventory, so the lexical result equals what following the link would reach. Outcomes: `Inside` with the target path or the root (FS1005, info); `Escapes` (FS1003, unknown); `Dangling` for a missing entry, a file used as a directory, an empty target, or a trailing separator on a non-directory (FS1007, info); and `Unresolved` (FS1006, unknown) for an absolute or drive-relative target, a path through another link or reparse point, a path through an ignored, untraversed, or uninspectable entry, an unreadable target, a component that is not Unicode or a path over the limits, or an absent target while the inventory is incomplete. A link is never admitted, and its target is processed at its own path, so nothing is read twice. A linked `.gitignore` file is listed as a link and never read, as in Git.

**Unrepresentable names.** A name that is not Unicode (invalid UTF-8 on Unix, unpaired UTF-16 surrogates on Windows) or contains `/`, or whose path `SourcePath` rejects (a backslash on Unix, a drive-like first component such as `C:`, the path byte limit, or the component limit) is counted in `Inventory::unrepresentable` and reported with FS1001 at its parent directory, or with project scope for entries of the root. The explanation names the reason category and never the name. Such a directory is not traversed and makes the inventory incomplete; such a file does not.

**Limits and stopping.** The walker alone owns five budgets: `run.max-files` and `run.max-total-bytes` charged per admitted file, `run.max-entries` per entry read, `ignore.max-total-bytes` per `.gitignore` file read, and `ignore.max-match-work` per pattern matched (section 23). The first charge that would exceed a budget stops discovery: one finding names the file, directory, or `.gitignore` file at which it stopped (FS1011 to FS1015, unknown), `Inventory::stop` names the limit, and the inventory is incomplete. A directory whose entries would exceed `run.max-entries` stops discovery as a whole, independent of its listing order. A file over `run.max-file-bytes` and a directory beyond `run.max-directory-depth` exclude only themselves.

**Inventory.** `files()` returns the admitted files as a `KeyTable<SourcePath>` (`D-060`), `file_size(id)` their sizes from the listing, `entries()` every other accounted entry sorted by path with its `EntryKind`, `entry(path)` a binary-search lookup, `unrepresentable()` the count of entries without a path, `stop()` the stopping limit, and `is_complete()` whether every file below the root is accounted for. Consumers must not treat an incomplete inventory as the whole project. A recorded `Directory` had its entries listed; after a stop, the entries of the directory that was being visited are only partly classified.

**Findings.** Codes and severities are listed in section 8.2 of [MIGRATION_REPORTING.md](MIGRATION_REPORTING.md). Locations are paths (of files or directories) or project scope; prose consists of fixed text, limit values, sizes, and reason categories, never names or absolute paths. Findings are built with permissive construction limits and stored with the collector's own limits; a full collector fails discovery with `DiscoveryError::Findings`, never with silent truncation.

**Errors.** `DiscoveryError` has `Root` (the root cannot be resolved or listed, with a platform-independent `IoFailure` category), `RootNotDirectory`, `SourceChanged` (a directory or `.gitignore` file changed between listing and use), `Findings`, `Internal`, and `AllocationFailed`. None of them returns an inventory.

**Filesystem boundary and limitations.** Without directory-relative opens in std, traversal uses paths: a directory that is replaced by a link between its listing and the recheck is detected, but a swap back before the recheck is not. This needs an active local adversary that modifies the tree during the run, which is outside the threat model of a static malicious repository (SECURITY.md section 13). A `.gitignore` file is opened for reading only: on Unix the opened file must have the device and inode of the listed regular file, so a swapped-in link is rejected; on Windows it is opened with `FILE_FLAG_OPEN_REPARSE_POINT` and must not be a reparse point or directory. Windows offers no stable file identity in std, so its directory recheck compares attributes only. On Unix, opening a `.gitignore` that was swapped for a FIFO between listing and opening would block. macOS and ARM64 have not been exercised locally.

**Tests.** The input crate has 17 unit tests on Windows (16 on Linux): 12 walker tests on in-memory trees cover shuffled listings, canonical budget order, built-in ignores and environment examples, `.gitignore` levels and excluded parents, per-file, depth, entry, ignore byte, and match work limits, every link outcome, unrepresentable names, excluded and failing entries with their severities, run failures, and findings without names; three matcher tests; and link target splitting, with drive and backslash targets on Windows. Facade tests in `crates/frameshift-engine/tests/discovery.rs` create their inputs at test time below Cargo's temporary directory: an unchanged source tree (contents and link targets compared before and after) with repeatable inventories and findings without absolute paths, sparse files of exactly 64 MiB and one byte more, root errors, the engine limit bridge, real symbolic links (skipped on Windows without the symbolic link privilege), a Unix socket, non-UTF-8 and backslash names on Linux, and verbatim Windows names (`dir.` beside `dir`, `CON.ts`, an unpaired surrogate).

**Product fixtures.** The first fixtures under `D-062` are six discovery cases in `fixtures/discovery/`: `builtin-ignores`, `gitignore-semantics`, `canonical-order`, `limits`, `large-files`, and `links`. Each has a human-written `fixture.json` (described by `schemas/fixture.schema.json`), a byte-exact `source/`, and `expected/discovery.txt`. `crates/frameshift-engine/tests/discovery_fixtures.rs` copies `source/` into Cargo's temporary directory, creates the `createdAtTestTime` inputs (`.git` entries, which Git cannot store, sparse files, and symbolic links), applies the limit overrides by their canonical names, runs discovery twice, and compares a deterministic text rendering of the inventory and the numbered findings. The rendering is a test format, not a product document; the `inspect` and analysis documents replace it once they exist. Goldens change only through `cargo test -p frameshift-engine --offline --locked --test discovery_fixtures -- --ignored update_discovery_goldens`; a case whose inputs the host cannot create keeps its golden, so the `links` golden is updated on Linux or on Windows with the symbolic link privilege. Fixture files that their own `.gitignore` patterns ignore must be added with `git add -f`. The `gitignore-semantics` admitted files equal `git ls-files -o --exclude-standard` on the same tree.

## 23. `.gitignore` matching

Implemented under the owner-confirmed `D-065` in `crates/frameshift-input/src/gitignore.rs`, written from the gitignore(5) documentation and checked black-box against Git; no Git source was used. `GitignoreFile::parse(bytes)` never fails on content (only on allocation), and `decide(path, is_directory, work)` returns the effect of the last matching pattern, `Ignored` or `Included`, or `None`.

**Lines.** A leading UTF-8 byte order mark is skipped. Lines end at LF; one CR before it is removed, also on a final line without LF. A line ends at its first NUL. Empty lines and lines that start with `#` are skipped; `\#` and a leading space keep a `#` pattern. Trailing spaces are removed unless escaped with a backslash, and a final backslash that escapes nothing disables trimming. Bytes need not be UTF-8.

**Patterns.** A leading `!` negates. One trailing `/` restricts the pattern to real directories (a link is not one). A pattern with another `/` is anchored: it matches the whole path relative to the `.gitignore` file's directory, and one leading `/` is dropped. A pattern without `/` matches the last path component at any depth. Empty patterns, such as `!`, `/`, or `//`, match nothing.

**Syntax.** Matching is byte-wise and case-sensitive. A backslash makes the next byte literal; a final backslash makes the pattern match nothing. `?` matches one byte other than `/`, so `caf?` does not match the two-byte `é`. A bracket expression matches one byte other than `/`: `!` or `^` negates; `]` is literal in first position; `a-z` ranges, whose ends may be escaped, start only after a single-byte member, a reversed range is empty, and `-` is literal elsewhere; `[:alnum:]`, `[:alpha:]`, `[:blank:]`, `[:cntrl:]`, `[:digit:]`, `[:graph:]`, `[:lower:]`, `[:print:]`, `[:punct:]`, `[:space:]`, `[:upper:]`, and `[:xdigit:]` add ASCII bytes as Git's own character table defines them (`[:space:]` is tab, LF, CR, and space, without vertical tab and form feed); `[:` without `:]` makes `[` a member; an unterminated bracket or an unknown class makes the whole pattern match nothing. `*` matches bytes other than `/`. In anchored patterns, two or more asterisks that start the pattern or follow `/` and end it or precede `/` have special meanings: trailing `**` matches any bytes, `**/` matches nothing or any bytes ending with `/` (so `a/**/b` matches `a/b` and `a/x/y/b`), and `**` before an escaped `\/` requires at least one slash; any other run of asterisks acts like `*`.

**Decision and precedence.** Patterns are tried from the last; a directory-only pattern is skipped for other entries without a charge, and the first match decides. In the walker, the `.gitignore` levels apply from the deepest directory to the root, and the first level with a match decides; an ignored directory is never traversed, so nothing below it can be re-included. Only regular files named exactly `.gitignore` in traversed directories are read: not linked or special ones, not files above the root, not `.git/info/exclude`, and not `core.excludesFile`. A `.gitignore` file is read even when a pattern ignores it, as in Git.

**Work and limits.** Before each pattern is matched, `work` is charged (pattern bytes + 1) times (subject bytes + 1), where the pattern bytes exclude `!`, the trailing slash, and an anchored leading slash, and the subject is the path or its last component. A failed charge ends the decision with `BudgetExceeded` and leaves the budget unchanged. `IgnoreLimits` defaults to `max_total_bytes` 4 MiB for all `.gitignore` files of a run, about a thousand times a typical framework `.gitignore`, and `max_match_work` 2^34 (about 1.7 * 10^10), roughly 17,000 per entry at the default entry limit, where a typical evaluation charges a few hundred. The automaton has one state per token plus one, plus a loop state per `**/`; patterns of up to 255 tokens simulate in fixed stack storage, longer ones in heap vectors sized by the pattern. Matching time is proportional to the charge, without backtracking; a facade test matches `*a` repeated 2,000 times against 1,999 bytes.

**Oracle validation (2026-10-17).** Outside the repository, a scratch driver compared the matcher with `git check-ignore --no-index -v -n` (Git 2.52.0.windows.1, `core.ignorecase=false`, no global excludes): 125 hand-picked cases, now the facade table of `crates/frameshift-engine/tests/gitignore.rs`, and 42,698 decisions on random patterns over literals, all special forms, CRLF, and byte order marks against random paths, with no difference; in the 37,108 decisions of the last four seeds, 1,024 paths were ignored by their own pattern, 353 included by negation, and 3,461 ignored through a parent directory. Git's pathspec parsing treats a leading `:` in a queried path as magic, so that one generated path was replaced by `x/:`, which agrees. The walker was compared with `git ls-files -o --exclude-standard` on 1,000 random trees with nested `.gitignore` files: 13,651 admitted files and 1,748 ignored entries, identical file sets in every tree.

**Fuzzing.** The twelfth target, `gitignore` (section 7), compares decisions and work charges with an independent memoized recursive interpretation of the pattern bytes and checks atomic budget failures and repetition. A 120-second coverage-instrumented Windows smoke run executed 2,016,249 inputs with 2,585 coverage features and 962 corpus inputs without findings. This is a smoke run, not a CPU-hour budget.

**Differences from Git.** Git matches case-insensitively where `core.ignoreCase` is set (the default on Windows and macOS); Frameshift never does. Patterns from `.gitignore` files above the root, `.git/info/exclude`, and global excludes are not applied, and tracked files that match a pattern are ignored, because the Git index is never read. For bytes above 127, Git's `[:graph:]` and `[:blank:]` follow the C library's locale, which differs only in single-byte locales; Frameshift's classes are ASCII.

## 24. Snapshot store

Implemented under the owner-confirmed `D-067` in `crates/frameshift-input/src/snapshot.rs`, exposed through `frameshift_engine::input`. It is the second and last place that opens source files; discovery opens only `.gitignore` files (section 22). No dependency is added.

**Entry point.** `snapshot(root, limits, findings)` runs discovery exactly as `discover` does, with the same findings, and returns a `Snapshot` that owns the `Inventory` and a private reader with each admitted file's native location and listing identity. `SnapshotLimits` holds the `DiscoveryLimits` and the `HashLimits` of each digest; `Limits::snapshot()` supplies them from the engine set. Creating a snapshot reads no file content.

**Reading.** `read(id)` takes a `DenseId` of the inventory's file table. The first request opens the file read-only without following links (on Unix the opened file must have the device and inode of the listed regular file; on Windows it is opened with `FILE_FLAG_OPEN_REPARSE_POINT` and must not be a reparse point or directory), requires the listed size before reading, reads exactly that many bytes into storage reserved up front, and requires the size and modification time of the open handle to be unchanged afterwards. The bytes are hashed with SHA-256 under the snapshot's hash limits and retained with the digest. Every outcome is retained in a `OnceLock` per file, so each file is opened at most once per run, also when several threads read concurrently, and later requests return the same result without filesystem access. `is_read(id)` tells whether a file has been read.

**Outcomes.** `FileRead::Content` borrows a `SnapshotFile` with `bytes()` and `digest()`. `FileRead::Unreadable` carries the platform-independent failure category of a file that is still the listed regular file but cannot be opened or read; its content is not analyzed, and `report_unreadable(findings)` reports every such file read so far once with `FS1019` (error), in canonical order, without its name in the prose. It is meant to be called once, after the last read of the run. `SnapshotError` ends the run: `SourceChanged` when the entry is gone, is no longer a regular file of the listed size and identity, or changes while it is read (a directory in its place counts as a change, although Windows reports it as an access failure); `Hash` when a digest exceeds the hash limit; `UnknownFile` for an identity outside the file table; and `Findings`, `Internal`, and `AllocationFailed`.

**Identity.** `identity()` reads every file not yet read, in canonical order, and returns a `SnapshotId`, whose `Display` is the canonical `sha256:` spelling of the digest of this stream, format version 1. Integers are 8-byte big-endian, tags single bytes, and a field is its byte length as an integer followed by the bytes:

1. The field `frameshift.snapshot` and the integer 1.
2. A tag 1 if the inventory is complete, else 0; the stop tag (0 none, 1 `run.max-files`, 2 `run.max-total-bytes`, 3 `run.max-entries`, 4 `ignore.max-total-bytes`, 5 `ignore.max-match-work`); and the unrepresentable count.
3. The admitted file count, then for each file in canonical order its path as a field, its size, and either tag 1 with the 32 digest bytes or tag 2 with the failure tag (1 permission denied, 2 not found, 3 other).
4. The count of other entries, then for each entry in canonical order its path as a field and its kind: 1 directory; 2 ignored with the reason tag (1 `vcs`, 2 `dependencies`, 3 `build-output`, 4 `environment`, 5 `gitignore`) and a directory tag (1 or 0); 3 oversized with its size; 4 link with the target tag (1 the root, 2 a path followed by the path as a field, 3 escapes, 4 dangling, 5 unresolved followed by the reason tag: 1 absolute, 2 through a link, 3 untraversed, 4 unreadable, 5 unrepresentable, 6 incomplete); 5 reparse point with a directory tag; 6 special; 7 not traversed with the reason tag (1 depth limit, 2 unreadable, 3 `.gitignore` unreadable); 8 uninspectable.

Because every variable-length value is a field and every tag determines the fields that follow, two different inventories or contents never produce the same stream. Limits are not part of the identity; plans record `Limits::entries` separately. The identity names content; it does not authenticate it. A changed layout requires a new format version.

**Memory.** Retained bytes are bounded by `run.max-total-bytes` (1 GiB by default). Decoding into `SourceText` currently copies the bytes.

Facade tests in `crates/frameshift-engine/tests/snapshot.rs` create real files below Cargo's temporary directory: exact bytes including a byte order mark, CRLF, binary data, and an empty file, retained content after a later change on disk, an unchanged source tree, repeatable identities; a grown, a removed, and a directory-replaced file stopping the run; on Unix, a link swapped in for a file and a file without read permission (skipped for privileged users); identities that follow contents and ignored entries; and the engine limit bridge.

**Limitations.** Traversal and reads are path based, as in discovery. A rewrite between listing and opening that keeps the size and modification time is not detected; like the swap window of section 22, this needs an active local adversary. On Unix, opening a file that was swapped for a FIFO between listing and opening would block.

## 25. JSON and JSONC parser

Implemented under the owner-confirmed `D-068` in `crates/frameshift-syntax/src/json.rs`, exposed through `frameshift_engine::syntax`. It performs no I/O; callers parse text that the snapshot store read (section 24). No dependency is added.

**Entry point.** `parse_json(source, dialect, limits)` parses one complete document of a `SourceText` and returns a `JsonDocument` that borrows the source, or a `JsonError`. The caller selects the dialect from the file's role: `JsonDialect::Json` for `package.json` and `package-lock.json`, `JsonDialect::Jsonc` for `tsconfig.json`, `jsconfig.json`, and `bun.lock`.

**Grammar.** RFC 8259 exactly: any value at the top level; whitespace is space, tab, LF, and CR only, so a no-break space, a form feed, a line separator, or a byte order mark after the start is an error; numbers follow `-? (0 | [1-9][0-9]*) (. [0-9]+)? ([eE] [+-]? [0-9]+)?`, so `01`, `1.`, `.5`, `+1`, and `-` are errors; literals are exactly `true`, `false`, and `null`; content after the value is an error. A leading UTF-8 byte order mark is skipped and reported by `has_bom()`; spans keep the original offsets. Strings must not contain raw U+0000 to U+001F; line and paragraph separators and DEL are allowed. Escapes are the eight short escapes `\"`, `\\`, `\/`, `\b`, `\f`, `\n`, `\r`, and `\t` and `\u` with four hexadecimal digits of either case. A high surrogate escape must be followed immediately by a low surrogate escape, and every other surrogate escape is an error (`LoneSurrogate`), so every decoded value is valid UTF-8.

**JSONC.** The JSONC dialect adds `//` comments, which end before the next LF or CR, and unnested `/* */` comments, both wherever whitespace is allowed, and one optional comma after the last element of an array or member of an object. `[,]`, `{,}`, and `[1,,]` remain errors, and everything else equals the JSON dialect. In the JSON dialect, `//` and `/*` fail with `CommentNotAllowed` and a comma before `]` or `}` with `TrailingCommaNotAllowed`. Comments are skipped and not stored; their bytes stay in the source, so span edits keep them.

**Values.** `value(id)` returns a `JsonValue`: `Null`, `Bool`, `Number` with its exact source text (`text()`, `is_integer()`, and checked `as_u64()` and `as_i64()` conversions of integers without fraction or exponent; `-0` converts to `i64` 0 and not to `u64`), `String` with the decoded text, `Array`, or `Object`, with `as_*` helpers. There is no floating-point conversion. Strings without escapes borrow the source; decoded strings with escapes are stored once in a shared buffer. `span(id)` returns a value's exact span, including quotes and brackets, and `ids()` iterates over every value and key in source order; identities ascend with the values' starts.

**Objects and duplicate keys.** An object keeps every member in source order (`members()`, `member(index)`), including members whose key occurs again later in the same object; such members report `is_shadowed()`. Keys compare by their decoded text, so `"a"` and `"\u0061"` are duplicates. `get(key)` returns the value of the last member with the key, as `JSON.parse` does, by binary search in a per-object index sorted by decoded key and then by position. `duplicate_keys()` lists every shadowed member of the document in source order, so consumers report them.

**Representation and limits.** Values and keys are nodes in a flat arena of 20 bytes each, with separate element, member, and key-index arenas. Parsing is an iterative state machine with an explicit container stack, so input nesting never consumes call stack; a unit test parses 200,000 nested arrays. `JsonLimits` bounds `max_depth` (default 256; the root container has depth 1) and `max_nodes` (default 4,194,304 values and keys); both are inclusive, and exceeding either fails with `DepthLimit` or `NodeLimit` at the offending value. Both limits are part of the engine limit set as `json.max-depth` and `json.max-nodes` (section 21). The size of a document is bounded by the text limits of its `SourceText`.

**Errors.** `JsonError` has a `JsonErrorKind` and a span at character boundaries; an empty span at the end marks input that ended early. `UnexpectedCharacter` and `UnexpectedEnd` name what was expected (`JsonExpected`: a value, a key, a colon, an array or object continuation, or the end). The other kinds are `InvalidNumber`, `InvalidEscape`, `LoneSurrogate`, `ControlCharacter`, `UnterminatedString`, `UnterminatedComment`, `CommentNotAllowed`, `TrailingCommaNotAllowed`, `DepthLimit`, `NodeLimit`, and `AllocationFailed`. Messages contain offsets and limit names, never source content. A parse has no error recovery; consumers turn errors into findings.

**Tests.** Eleven unit tests in `src/json/tests.rs` cover values, spans, and identities; the byte order mark; the number grammar with exact text and conversions at the `u64` and `i64` bounds; string decoding with every escape, surrogate pairs, and unescaped separators; lone surrogates, invalid escapes, control characters, and unterminated strings; the four whitespace characters; JSONC comments and trailing commas and their rejection in JSON; every structural error with its expectation; duplicate keys, including escaped spellings, across nesting levels; binary-search lookups in a 2,000-member object; inclusive depth and node limits and 200,000 nested arrays; and repetition and JSONC acceptance of JSON documents. Facade tests in `crates/frameshift-engine/tests/json.rs` parse a fictional `package.json` with a byte order mark, a `tsconfig.json` with comments and trailing commas, and a `bun.lock`, resolve duplicate manifest keys, and bound hostile inputs. The discovery fixture harness reads `fixture.json` with this parser (`tests/support/mod.rs`), more strictly than products: it rejects duplicate keys and numbers other than nonnegative integers.

**Oracle validation (2026-10-19).** Outside the repository, a scratch driver compared the JSON dialect with `JSON.parse` of Node 26.7.0 on 100,000 generated and mutated documents (four seeds) with escapes, surrogates, duplicate and `__proto__` keys, numbers at the edges of the grammar, and random insertions and deletions: 42,738 were accepted by both with equal values (numbers compared through `Number` of the exact text, objects through the last occurrence of each key), 56,024 were rejected by both, and the 1,238 documents with unpaired surrogate escapes, which `JSON.parse` accepts, were rejected by design; there was no other difference. The JSONC dialect was compared with `Bun.JSONC.parse` of Bun 1.4.0 on 100,000 documents with comments and trailing commas (four seeds): 39,775 were accepted by both with equal values and 53,492 rejected by both; 1,338 had unpaired surrogates, and in the remaining 5,395 only Bun accepted, because it is more lenient (for example content after the value, hexadecimal numbers, or a fraction without digits). No document was accepted by Frameshift and rejected by an oracle, or accepted by both with different values.

**Fuzzing.** The thirteenth target, `json` (section 7), compares both dialects with an independent recursive-descent model over decoded characters: acceptance, every decoded value, shadowed marks, lookups, and the duplicate list. It also checks spans, repetition, JSONC acceptance of every JSON document, a canonical rewrite, and inclusive depth and node limits at the exact values. A 120-second coverage-instrumented Windows smoke run executed 7,579,278 inputs with 5,608 coverage features and 1,121 corpus inputs without findings. This is a smoke run, not a CPU-hour budget.

**Measurements (2026-10-19).** On the development desktop (section 6), a release build parsed a generated fictional `package-lock.json` of 21.7 MB with 1,047,659 values and keys in 44.4 ms (minimum of five runs), 490 MB/s. A file of this size exceeds the default text limit of 16 MiB and would be rejected before parsing; that limit is a separate decision.

**Differences from other readers.** `JSON.parse` accepts unpaired surrogate escapes; Frameshift rejects them. TypeScript's configuration reader and Bun's JSONC reader accept more than the JSONC dialect, such as other whitespace characters or content after the value; such files are rejected with an error rather than read in a guessed way.

## 26. Package model: versions, ranges, manifests, and lockfiles

Implemented under the owner-confirmed `D-069` and `D-070` in `crates/frameshift-package`, exposed through `frameshift_engine::package`. The crate depends on the foundation, syntax, and input crates, has no framework knowledge, and reads files only through the snapshot store (section 24). No dependency is added.

**Versions.** `Version::parse` accepts exact SemVer 2.0 text: no `v` or `=` prefix, no whitespace, numbers up to 2^53 - 1 (`MAX_VERSION_NUMBER`), and at most 256 bytes (`MAX_VERSION_BYTES`), as npm bounds them. `cmp_precedence` is SemVer precedence without build metadata; numeric prerelease identifiers keep their digits and compare exactly at any length. `Ord` adds the build identifiers, so it is consistent with equality.

**Ranges.** `VersionRange::parse` reproduces node-semver 7.8.5, which npm 11.11.0 bundles, in its default mode. The text is trimmed and its JavaScript whitespace runs become single spaces; it is split at `||`; each alternative then passes the same stages as in node-semver: build metadata (`+` and identifiers) is removed wherever it occurs, so `+build` alone is `*`; the hyphen form applies only to `A - B` with exactly one space around `-` and at most one space at either end, and keeps the raw text of a complete bound, so `= 1.2.3 - 2` fails as `>== 1.2.3`; up to one space after `<`, `>`, `=`, `<=`, or `>=` and before a version is removed by a backtracking-order match, and one space after `~`, `~>`, or `^`, dropping the `>`; each token desugars as a caret, a tilde, or an X-range with an operator, where an X-range with a number after an `x` (`1.x.3`) stays unchanged and fails, while carets and tildes ignore later components; the first `*` with an operator and one space before it is removed; and `>=0.0.0` becomes `*`. Desugared comparators must match `[<>]?=?v?` and an exact version with numbers up to 2^53 - 1 and at most 256 bytes, also where desugaring adds one (`1.9007199254740991` fails); X-range components are bounded to 257 digits and prerelease identifiers to node-semver's bounded patterns (at most 256 leading digits and 250 further characters). A set with a `<0.0.0-0` comparator is only that comparator, `*` disappears from sets with other comparators, duplicates are removed, null sets are dropped from ranges with other sets, and a `*` set makes the whole range `*`. `satisfies` requires every comparator of one set and, for a prerelease, a comparator of that set with a prerelease of the same major, minor, and patch numbers. `Display` prints the canonical range as node-semver's `validRange` does. `min_version` returns the exact lowest satisfying version, computed per set from its tightest lower and upper bounds and the prerelease rule; unlike node-semver's `minVersion` it never returns a higher version (`0.0.0-0.0` for `>0.0.0-0`) or none for a satisfiable range. Every stage is linear in the text. `RangeError` and `VersionError` name a kind, never the input.

**Specifiers.** `DependencySpec::parse` classifies a dependency value in a fixed order: `npm:` aliases with a range or tag target, `workspace:`, `catalog:`, local sources (`file:`, `link:`, `portal:`, a path starting with `.`, `~/`, `/`, `\`, or a drive letter, or a value with a slash or a tarball extension), Git sources (`git+`, `git:`, `github:`, `gitlab:`, `bitbucket:`, `gist:`, `user@host.tld:path`, and `owner/repo`), HTTP URLs, other protocols, ranges, tags, and invalid values. Tags consist of characters that `encodeURIComponent` keeps and contain no digit; a value that only npm's loose grammar reads as a range, such as `1.2.3beta`, is invalid.

**Manifest.** `PackageManifest::from_json` interprets a parsed `package.json` (section 25) into public fields with exact spans: `name`, `version` (text, and `parsed_version`), `private`, `type` (`module` or `commonjs`), `packageManager` (text), `engines`, `workspaces` (an array or Yarn's `packages` member), `scripts`, the four dependency maps with classified specifiers, `peerDependenciesMeta` as optional flags, npm's nested `overrides`, Yarn's `resolutions`, pnpm's `pnpm.overrides`, `exports` (targets, `null`, fallback arrays, and condition or subpath objects, which must not mix keys starting with `.` and others), `main`, `module`, `browser` (a path or a map with `false`), `bin`, `files`, and `browserslist` (a query, queries, or queries by environment). Other members are listed with their spans. Each object member that a later member with the same key shadows is skipped. A value of an unexpected type or with an invalid value, including an invalid specifier, is not used and becomes a `ManifestIssue` with its field and span; a document that is not an object fails with `ManifestError::NotAnObject`.

**Package manager.** `PackageManagerSpec::parse` accepts exactly `<name>@<version>[+<algorithm>.<hex>]` with `npm`, `pnpm`, `yarn`, or `bun`, an exact version without build metadata, a lowercase alphanumeric algorithm, and lowercase hexadecimal digits. `detect(field, present)` returns the manager, its source (field or lockfile), the selected lockfile, and every other present lockfile with a reason: a valid field decides and other managers' lockfiles are `OtherManager`; without one, lockfiles of a single manager decide and those of several managers leave the manager undetermined (`Ambiguous`); `npm-shrinkwrap.json` precedes `package-lock.json` and `bun.lock` precedes `bun.lockb` (`Superseded`).

**Lockfiles.** `Lockfile::from_json(kind, document)` reads `package-lock.json` and `npm-shrinkwrap.json` of versions 2 and 3 from `packages`, and `bun.lock` of versions 1 and 2 from `workspaces` and `packages`. Version 1 npm lockfiles, version 0 Bun lockfiles, other versions, and every other kind fail with `UnsupportedVersion`. An npm key without a `node_modules` segment is a workspace or local folder with its declarations; a key below `node_modules` is a locked package whose name is the recorded `name` (for aliases) or the path after the last `node_modules/`, resolved as `Registry` when its version is exact and its `resolved` URL absent or HTTP, as `Link` with a valid target location when `link` is set, and otherwise as `Other`. A Bun key is a path of package names (`@scope/name` stays together); the value is an array whose first element is `<name>@<resolution>` and whose first object element holds `dependencies`, `optionalDependencies`, `peerDependencies`, and `optionalPeers`; resolutions are exact versions, `workspace:` paths, or other text. Any type or key that deviates from this structure fails with `Structure` at its span. Workspaces and packages are sorted by path and key. `resolve(workspace, name)` follows the managers: npm looks for `<directory>/node_modules/<name>` from the workspace directory up to the root, skipping `node_modules` directories, and follows one link into the packages when its target is one; Bun looks for `<prefix>/<name>` from the workspace's package name or a package key down to the bare name. `resolve_from(package, name)` starts at a locked package. `out_of_sync(manifest)` lists the dependency kinds whose names and specifier texts differ from the root workspace's declarations.

**Loader.** `load_package(snapshot, directory, limits, findings)` handles one directory (`None` for the root). It reads `package.json` if discovery admitted it, decodes it under `text.max-source-bytes`, parses it as JSON, and interprets it; it parses a present `packageManager` field; it collects the admitted lockfiles of the directory, detects the manager, and reads the selected lockfile if it is an npm or Bun text lockfile within `package.max-lockfile-bytes`, decoding it under that limit and parsing `bun.lock` as JSONC. Each file is read at most once, through `Snapshot::read`; unreadable files are left to `Snapshot::report_unreadable` (`FS1019`). The result has the manifest state (absent, not analyzed, or analyzed), the valid `packageManager` value, the detection, and the lockfile state (none, not parsed, or parsed). `LoadLimits` bundles the text, JSON, path, and package limits; `Limits::package()` supplies them from the engine set. `LoadError` ends the run for snapshot failures such as a changed file, a full finding collector, internal errors, and allocation failures.

**Findings.** The codes are listed in section 8.2 of [MIGRATION_REPORTING.md](MIGRATION_REPORTING.md). Locations are text ranges where a span exists, the file otherwise, and the directory (project scope for the root) for an ambiguous manager. Prose names fields, kinds, limits, and sizes but never package names, values, or paths beyond the location.

**Limits.** `PackageLimits::max_lockfile_bytes` (`package.max-lockfile-bytes`, default 64 MiB) is the 31st entry of the limit set (section 21); it replaces the 16 MiB text limit for lockfiles only. A lockfile above it is not decoded (`FS1028`). The JSON node limit of 4,194,304 covers about 64 MiB of typical lockfile text.

**Tests.** The crate has 22 unit tests: versions (strict grammar, bounds, precedence), ranges (documented desugaring, node-semver's text rules and rejections, number and length bounds, the prerelease rule, exact minimums, comparator access), specifiers (classification and alias targets, package names), the manifest (all modeled fields with spans, issues with spans, duplicates, non-objects), the package manager (Corepack grammar, detection cases), and lockfiles (npm and Bun models and resolution, unsupported versions and structures, declarations out of sync). Six facade tests in `crates/frameshift-engine/tests/package.rs` use real directories below Cargo's temporary directory: ranges through the facade; a load that reads only `package.json` and the selected lockfile, not a foreign lockfile or source files; ignored and absent files and a subdirectory; undecodable and oversized manifests; findings that never echo a marker string from names and values; and the engine limit bridge.

## 27. YAML 1.2 syntax (`D-071`)

`frameshift_engine::syntax::parse_yaml` parses a complete UTF-8 stream from immutable `SourceText`, without I/O or new dependencies. `crates/frameshift-syntax/src/yaml.rs` defines the public model and `src/yaml/parser.rs` implements the grammar. Block and flow sequences and mappings, complex keys, all scalar styles with folding, chomping and escapes, explicit tags and tag directives, anchors, aliases, empty nodes, and document streams are represented. Original source text stays untouched.

`YamlStream` owns flat node and document arenas. `YamlNode` holds a source span, an optional decoded tag URI, an optional anchor name, and `YamlValue`: decoded scalar text with its style, sequence identities, mapping key/value identities in source order, or an alias identity. Recursive aliases are valid graph references, never expanded. Duplicate keys stay visible. No tags instantiate host-language objects; scalar schema resolution, key equality, and application validation belong to consumers. This is syntax support, not an object deserializer or YAML writer. Encodings other than the validated UTF-8 `SourceText` representation must be decoded before this API.

`YamlLimits` supplies `yaml.max-depth` (default and implementation ceiling 128 collection levels) and `yaml.max-nodes` (default 4,194,304, including keys, empty nodes, and alias occurrences). Syntax recursion is bounded by the effective depth; graph storage and destruction are flat. Source bytes are already bounded by the caller's text limit. Errors carry a category and a UTF-8-aligned span and never echo source content. The engine limit catalog now contains 33 entries.
